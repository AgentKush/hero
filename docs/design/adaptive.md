# Warden Adaptive Defence Engine — Baseline Model, Learning Lifecycle, Novelty Scoring, Feedback and Alert Budget

> Area: `adaptive-baseline` · adversarial critique verdict: **needs_rework**

## Summary
Warden's adaptive half is a per-host Bayesian-ish evidence engine built on three separated layers: (1) a raw observation store that never stores scores, only facts, so the scoring model can change without re-learning; (2) a scoring pass that recomputes novelty on demand from those facts; (3) a feedback layer that writes user verdicts back into the observation store as pseudo-observations rather than as bypass exceptions. Entities are keyed by a tokenised path (stable across app updates) with a bounded ring of content hashes and pinned signer identities, stored as 256 sharded JSONL files under %LOCALAPPDATA%\Warden\baseline\entities\ with a write-ahead journal and atomic shard compaction. Novelty is an additive evidence score in points combining rarity (exponential decay in observation count and age), signer trust tier, path trust tier, behavioural deviation (one-sided log-space z-scores for continuous channels, Good–Turing new-category surprise for categorical channels, combined by noisy-OR so correlated evidence saturates instead of summing), and a static shipped rule catalogue with per-family suppression. The hard precision guarantee is that context alone is capped at 9.9 points and can never reach the HIGH threshold of 15.0: no auto-kill ever happens on statistics alone, only on at least two independent rule families or a single dominant rule, and only at confidence ≥ 0.80. Alert fatigue is controlled by incident correlation on process-tree root, 6-hour dedup keys, per-severity token buckets with a hard ceiling of 6 toasts/hour, and Focus/fullscreen suppression via SHQueryUserNotificationState. Day one is carried by an autorun/network/signature census, Windows catalog membership as a zero-history trust source, and a signer-blind rule floor that is armed from minute zero.

### [critical] Entity identity: pathKey is primary, hash is secondary, signer is pinned
Three identities per entity. (a) pathKey = "p:" + first 16 hex chars of SHA-256(tokenisedPath) — this is the PRIMARY key and is deliberately stable across application updates, which is what stops an update storm. (b) codeIdentity = full SHA-256 of file bytes, stored in a bounded ring of the last 8 distinct hashes with per-hash first/last-seen, count, size and FileVersion. (c) signerIdentity = leaf subject CN + leaf cert SHA-256 thumbprint + root cert thumbprint + EV flag + catalog-signed flag. Path tokenisation is what makes pathKey stable: lowercase; expand 8.3 short names; resolve \Device\HarddiskVolumeN to a drive letter; strip \\?\; replace %SystemRoot%, %ProgramFiles%, %ProgramFiles(x86)%, %ProgramData%, %LOCALAPPDATA%, %APPDATA%, %USERPROFILE%, %TEMP% with tokens; collapse MSIX version churn (WindowsApps\<pkg>_<ver>_<arch>__<pub> -> WindowsApps\<pkg>_*__<pub>); collapse GUID/hex directory names to {guid}/{hex}. Collision probability at 6,000 entities over 64 bits is ~1e-12 — acceptable, and a collision is detected because the stored full path will not match.

**How:** Path from ETW Kernel-Process ImageName, or QueryFullProcessImageNameW(PROCESS_QUERY_LIMITED_INFORMATION, PROCESS_NAME_NATIVE=0). Short-name expansion via GetLongPathNameW. Device path mapping via QueryDosDeviceW over DriveInfo.GetDrives(). Hash via System.Security.Cryptography.IncrementalHash (SHA256) with an ArrayPool<byte> 1 MiB buffer. Signer leaf via new X509Certificate2(X509Certificate.CreateFromSignedFile(path)); full chain + timestamp countersignature via SignedCms from the in-box System.Security.Cryptography.Pkcs.dll (confirmed present in Microsoft.WindowsDesktop.App\10.0.11).

**False positives:** Do NOT key on hash alone — every Chrome/Discord/VS Code/dotnet SDK update would mint a brand-new entity with zero history and score as novel. Do NOT key on path alone — that is exactly the path-substitution attack. Key on path, carry hashes as attributes, and score a hash change as an event rather than as a new entity.

### [critical] On-disk layout under %LOCALAPPDATA%\Warden
Concrete tree:
%LOCALAPPDATA%\Warden\
  config.json                  (user settings; cloud lookups default false)
  baseline\
    manifest.json              (schema version, host id, counters, model epoch)
    entities\00.jsonl .. ff.jsonl   (256 shards, one entity per line, minified)
    journal.jsonl              (write-ahead log of pending deltas)
    hashcache.jsonl            (fileId -> sha256, avoids re-hashing)
    persistence.json           (current autorun snapshot)
    signers.json               (per-signer host reputation, see signer tier item)
    allowlist.jsonl            (HMAC'd, one entry per line)
    verdicts.jsonl             (append-only user feedback audit log, never pruned)
  events\YYYY-MM-DD.jsonl      (raw event log, gzipped after 3 days, deleted after 45)
  incidents\incidents.jsonl    (open + closed incidents)
  quarantine\<incidentId>\     (moved payloads + restore manifest)
Shard selection: shard = last 2 hex chars of the pathKey digest. 256 shards keeps each file ~25-30 KB at 6,000 entities, so a compaction rewrites 30 KB not 8 MB.

**How:** Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData). Create the tree with a hardened DACL at first run: DirectorySecurity ds = new(); ds.SetAccessRuleProtection(true,false); grant FileSystemRights.FullControl to new SecurityIdentifier(WellKnownSidType.LocalSystemSid,null) and BuiltinAdministratorsSid, and ReadAndExecute only to the interactive user SID; Directory.CreateDirectory(path) then new DirectoryInfo(path).SetAccessControl(ds) — System.IO.FileSystem.AccessControl.dll and System.Security.AccessControl.dll are in-box in Microsoft.NETCore.App\10.0.11 (verified on this machine).

### [high] Resource envelope: Welford sufficient statistics in log space, one observation per 10-minute window
CPU%, private commit MB, thread count and handle count are heavy-tailed, so model x' = ln(1+x) and treat x' as roughly Gaussian. Store {n, mu, m2} and update with Welford: n+=1; d = x'-mu; mu += d/n; m2 += d*(x'-mu). Variance = m2/(n-1), sigma = sqrt(variance). CRITICAL sampling rule: sampling every 2 s but recording every sample would make a 10-hour Unreal build contribute 18,000 observations while a 3-second CLI tool contributes 2, destroying comparability and letting long-lived processes wash out their own envelope. Instead emit exactly ONE envelope observation per process-run per 10-minute window, using that window's 95th percentile sample. So n is roughly "number of 10-minute activity windows", comparable across processes, and grows at most 144/day per continuously-running process. CPU% is normalised to whole-machine capacity: (delta kernel+user 100ns ticks) / (delta wallclock 100ns ticks * 24 logical processors) * 100, so 100 means all 24 threads saturated. Use PrivatePageCount (commit), not WorkingSetSize, for memory — working set is far noisier under memory pressure with 63.8 GB installed.

**How:** NtQuerySystemInformation(SystemProcessInformation=5) via P/Invoke on ntdll.dll into a pooled buffer; one call returns SYSTEM_PROCESS_INFORMATION for every process including KernelTime, UserTime, CreateTime, NumberOfThreads, HandleCount, PrivatePageCount, WorkingSetSize. On this i9-12900K with ~400 processes this is ~1.5 ms per call; at a 2 s period that is ~0.075% of one core. Logical processor count from Environment.ProcessorCount.

**False positives:** Require n >= 12 before the continuous channels contribute anything to the behaviour score — you cannot deviate from an envelope you have not learned. Also floor sigma (CPU 0.35, commit 0.20, threads 0.25, handles 0.30) so a process that has always used exactly 0.1% CPU does not produce z=400 the first time it uses 0.4%.

### [high] Categorical channels: bounded top-K plus a Bloom filter to survive eviction
Parents, children, command-line templates, remote /16 or /24 prefixes, remote ports, DNS names and loaded-module directories are categorical. Each is stored as a bounded top-K map (parents 12, children 12, cmd templates 8, nets 32, ports 16, dns 24, modules 16) sorted by decayed count. Eviction of a rare category would make it look brand-new next time, which is a false-positive factory — so each channel also carries a 512-bit, 3-hash Bloom filter of every category ever observed. Lookup outcome drives scoring: present in top-K = known (b=0); absent from top-K but present in Bloom = seen-but-rare (b scaled by 0.35); absent from both = genuinely new (full b). Bloom false-positive rate at 60 inserted items in 512 bits with k=3 is (1-e^(-3*60/512))^3 ~= 2.6%, i.e. 2.6% of genuinely-new categories get softened to seen-but-rare — a conservative failure direction that costs a little recall, not precision. Bloom filters are rebuilt from the surviving top-K during the 30-day compaction so they do not saturate. Command-line templates are normalised before hashing: lowercase, replace GUIDs, hex runs >= 8, decimal runs >= 4, absolute paths and base64 runs >= 20 with tokens, then FNV-1a 64 truncated to 32 bits.

**How:** Command line via NtQueryInformationProcess(ProcessBasicInformation) -> PEB -> RTL_USER_PROCESS_PARAMETERS.CommandLine with ReadProcessMemory, or (preferred, race-free) Security 4688 events with ProcessCommandLine once command-line auditing is enabled. TCP/UDP tables via GetExtendedTcpTable(TCP_TABLE_OWNER_PID_ALL=5) and GetExtendedUdpTable(UDP_TABLE_OWNER_PID=1) from iphlpapi.dll at 2 s. Loaded modules via ETW Kernel-Process ImageLoad, or EnumProcessModulesEx as fallback.

**False positives:** Never treat 'new remote IP' as novel on its own — CDN-backed apps hit a new address constantly. Bucket IPv4 to /16 for public addresses (a /24 is too tight for Cloudflare/Akamai/Azure) and /24 for RFC1918, IPv6 to /48. Prefer the DNS name from ETW DNS-Client over the IP entirely where available; a stable name behind rotating IPs is the correct identity.

### [high] Persistence entity: separate record type with a 6-hour snapshot diff
Persistence is modelled as its own entity class, not as a property of a binary, because the interesting event is the WRITE and because an autorun can outlive its target. Record shape in persistence.json:
{"v":2,"k":"per:5c8a91d2","typ":"run","loc":"HKCU\\SOFTWARE\\Microsoft\\Windows\\CurrentVersion\\Run","nm":"OneDrive","val":"\"%LOCALAPPDATA%\\Microsoft\\OneDrive\\OneDrive.exe\" /background","tgt":"p:3d1f…","tgtHash":"9c1b…","fs":1746032411,"ls":1756800112,"st":"known","who":"p:1a2b…","sigT":3,"score":1.2}
typ is one of run|runonce|task|service|wmi|com|winlogon|userinit|ifeo|silentexit|appinit|appcert|startupfolder|lsa|netshhelper|printmon|lsp|env|shellext|contextmenu|browserext. "who" is the entity that created or last modified it (from ETW registry/file events; unknown on the first sweep). A full sweep runs at install, at every boot + 5 minutes, every 6 hours, and immediately after any HIGH incident. The sweep is diffed against the stored snapshot; adds/modifies/removes are events. Base novelty for a NEW persistence entry is 2.0 points before the path/signer terms are added, so a benign new signed installer entry lands around 2.5-3.5 (INFO/LOW) while an unsigned %TEMP% entry lands around 5.5 (LOW) and rises to MEDIUM/HIGH once a persistence rule and a provenance rule both fire.

**How:** Registry via in-box Microsoft.Win32.Registry with RegistryView.Registry64 AND Registry32 (WOW6432Node). Scheduled tasks: parse C:\Windows\System32\Tasks\**\* XML directly (fast, no COM) and cross-check with the ITaskService COM interface (CLSID {0F87369F-A4E5-4CFC-BD3E-73E6154572DD}, IID {2FABA4C7-4DA9-4013-9697-20CC3FD40F85}) declared with [ComImport]. Services via EnumServicesStatusExW/QueryServiceConfigW in advapi32.dll, or HKLM\SYSTEM\CurrentControlSet\Services. WMI persistence (root\subscription __EventFilter/__EventConsumer/__FilterToConsumerBinding) has no in-box managed API on net10.0-windows because System.Management.dll is NOT in either shared framework on this machine — shell out: powershell.exe -NoProfile -NonInteractive -Command "Get-CimInstance -Namespace root/subscription -ClassName __FilterToConsumerBinding | ConvertTo-Json -Depth 4".

**False positives:** Scheduled Tasks are the biggest FP source on a dev box: Windows itself owns ~350 tasks, and Adobe/NVIDIA/Chrome/Edge/Steam/winget add dozens more. Suppress any task whose Author or Principal is TrustedInstaller/SYSTEM AND whose Actions point into %SystemRoot% or %ProgramFiles% AND whose target is catalog-signed. Also ignore the entire \Microsoft\Windows\ task subtree unless a task there has been MODIFIED since baseline (modification of a Microsoft task is very interesting; existence is not).

### [critical] Signer trust tiers with real numeric values
Sg in [-0.35, 1.00], contribution Cs = 1 - Sg:
  T3 Sg=1.00 — catalog-signed Windows component, OR leaf CN in {Microsoft Windows, Microsoft Windows Publisher, Microsoft Windows Hardware Compatibility Publisher} with root = Microsoft Root Certificate Authority 2010/2011.
  T2 Sg=0.80 — valid chain AND (EV code-signing cert OR the signer already owns >= 3 entities in state 'known' on this host with >= 30 days of history). The second clause is the adaptive part: NVIDIA, Epic, Blender Foundation, JetBrains all earn T2 on this machine within a month without shipping a list.
  T1 Sg=0.55 — valid Authenticode, non-EV, root in the Windows Trusted Root store.
  T0.5 Sg=0.30 — signing cert expired now but a valid RFC3161/legacy countersignature places the signing time inside validity.
  T0 Sg=0.00 — unsigned.
  T-1 Sg=-0.35 — signature PRESENT but INVALID (tampered, revoked, untrusted root, or CN/root mismatch against a pinned entry). Deliberately worse than unsigned: nobody accidentally ships a corrupt signature.
signers.json stores per-signer host reputation: {"lt":"<leafThumbprint>","cn":"OBS Project","rt":"<rootThumbprint>","known":4,"first":…,"denies":0,"tier":2}. A single user 'kill it' verdict on any binary from a non-T3 signer sets denies+=1 and freezes that signer's tier promotion; denies >= 2 demotes it to T0 permanently until the user clears it.

**How:** WinVerifyTrust in wintrust.dll with pgActionID = WINTRUST_ACTION_GENERIC_VERIFY_V2 {00AAC56B-CD44-11d0-8CC2-00C04FC295EE}, WINTRUST_DATA.dwUIChoice = WTD_UI_NONE(2), fdwRevocationChecks = WTD_REVOKE_NONE(0), dwProvFlags = WTD_CACHE_ONLY_URL_RETRIEVAL(0x1000) | WTD_SAFER_FLAG. WTD_REVOKE_NONE + CACHE_ONLY is mandatory: it guarantees zero network egress, which is a non-negotiable product constraint. Catalog membership via CryptCATAdminAcquireContext2 / CryptCATAdminCalcHashFromFileHandle2 / CryptCATAdminEnumCatalogFromHash in wintrust.dll. Cache the verdict keyed by (volumeSerial, fileId, size, lastWriteUtc) — WinVerifyTrust is ~5-40 ms per file and you will call it thousands of times during the install census.

**False positives:** A valid signature does NOT imply safe behaviour. Signer tier reduces only the CONTEXTUAL part of the score; it attenuates rule points by at most 25%, and not at all for rules tagged signerBlind. Otherwise every Microsoft-signed LOLBin (rundll32, mshta, regsvr32, certutil, msbuild, wmic, bitsadmin, installutil, forfiles, curl) becomes a blind spot.

### [critical] Path trust tiers with real numeric values and a live ACL probe
Pt in [0,1], contribution Cp = 1 - Pt:
  1.00 — %SystemRoot%\System32, \SysWOW64, \WinSxS, \servicing, and NOT writable by Users/Authenticated Users/Everyone.
  0.85 — %ProgramFiles%, %ProgramFiles(x86)%, %ProgramData%\Package Cache, %SystemRoot%\SystemApps, WindowsApps — again gated on a restrictive DACL.
  0.55 — %LOCALAPPDATA%\Programs, and any directory tree containing >= 20 entities already in state 'known' (this promotes D:\My projects, the Unreal/Blender/dotnet SDK trees and the user's toolchain automatically, with no hard-coded list).
  0.30 — %LOCALAPPDATA%\*, %APPDATA%\Roaming\*.
  0.10 — %TEMP%, %USERPROFILE%\Downloads, $Recycle.Bin, mounted ISO/removable volumes (DriveType Removable/CDRom), UNC paths.
  0.00 — pathological: no file extension, alternate data stream (contains ':' past index 2), DACL granting write to WD/AU/BU on a supposedly system path, RTL-override or other bidi control chars in the name, trailing space or dot in a directory component, path length > 200.
The ACL probe is what makes this real rather than a string match: a binary sitting in C:\Windows\System32\ in a subdirectory that Users can write to gets 0.00, not 1.00.

**How:** DACL check with in-box System.IO.FileSystem.AccessControl: new FileInfo(p).GetAccessControl(AccessControlSections.Access).GetAccessRules(true,true,typeof(SecurityIdentifier)), then test each rule's IdentityReference against WellKnownSidType.WorldSid (WD), AuthenticatedUserSid (AU), BuiltinUsersSid (BU) for FileSystemRights.WriteData|AppendData|WriteAttributes|Delete|ChangePermissions|TakeOwnership. Cache per-directory for 60 minutes. Removable/optical detection via new DriveInfo(root).DriveType. Bidi/RTL detection via System.Globalization.CharUnicodeInfo.GetUnicodeCategory == UnicodeCategory.Format on any char in the leaf name.

**False positives:** The 0.55 'earned directory' tier is essential on this machine. Without it, every fresh build output in D:\My projects\nova-hoard\bin\Release and every Unreal cooked binary is an unsigned executable in a user-writable path and would sit at Cp=0.70, generating a permanent stream of LOW alerts. With it, those trees settle at Cp=0.45 after ~20 binaries graduate.

### [high] Schema versioning, forward-compatibility and the model epoch
Two independent version numbers, which is the key structural decision. (1) "v" per record + manifest.schema — the STORAGE format. Migration is forward-only: an ordered array of (from, to, Func<JsonObject,JsonObject>) migrators in Warden.Baseline.Migrations, applied line-by-line during load; a record is rewritten on next compaction. If manifest.schema is NEWER than the running build (user downgraded), rename baseline\ to baseline.bak-<unixts>\ and re-bootstrap rather than mangling it — never crash, never partially parse. Unknown fields survive via [JsonExtensionData] Dictionary<string,JsonElement> ext. (2) manifest.epoch — the SCORING MODEL version. Because the store contains only raw observations and never a stored score, changing weights, thresholds or the rule catalogue only requires bumping epoch; nothing is re-learned and nothing is migrated. Derived state (entity st, incident severities) is recomputed lazily on next touch. manifest.json:
{"schema":3,"epoch":7,"appVer":"1.4.0","hostId":"h_<first16hex of SHA256(MachineGuid|systemVolumeSerial)>","created":1746032000,"entities":5211,"bytes":6291456,"bootCount":37,"uptimeHours":911.4,"learnState":"steady","lastCompact":1756800000,"lastPrune":1756540000}

**How:** MachineGuid from HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid (RegistryView.Registry64). Volume serial from GetVolumeInformationW on the system drive. Write manifest.json last, after shards, so a torn write leaves an older manifest pointing at newer-or-equal shards, which the migrators tolerate.

### [high] Keeping the store small: hard bounds, decay-as-compression, pruning, caps
Real numbers for this machine. Expect 4,000-8,000 distinct executables on a dev box with Unreal, Blender, BlueStacks, dotnet SDKs and node_modules present. At ~1.0-1.4 KB minified per entity that is 5-11 MB. Bounds: 8 hashes, 12 parents, 12 children, 8 cmd templates, 32 nets, 16 ports, 24 dns names, 16 module dirs, 4x64-byte Bloom filters per entity. Hour and day histograms are stored as uint16 and halved wholesale when any bucket exceeds 60,000 (which is itself a crude decay). Pruning, nightly during idle: drop entities where (lastSeen older than 120 days AND n < 5) OR (lastSeen older than 365 days), UNLESS the entity is referenced by an allowlist entry, a persistence entry, or an unresolved incident. Hard caps: 12,000 entities and 64 MB total; on breach, evict by ascending keepScore = 0.5*ln(1+n) + 0.3*(1 - daysSinceLastSeen/365) + 0.2*sigTier/3, and raise a LOW 'baseline at capacity' notice. Event logs: gzip files older than 3 days (System.IO.Compression.GZipStream, in-box), delete older than 45 days. verdicts.jsonl is NEVER pruned — it is the audit trail and it is tiny (a few hundred lines over the product's life).

**How:** Idle detection for the nightly pass: GetLastInputInfo (user idle > 10 min) AND SHQueryUserNotificationState() != QUNS_RUNNING_D3D_FULL_SCREEN AND total machine CPU < 25% for 60 s. Run the pass at ThreadPriority.Lowest with Thread.CurrentThread + a 5 ms sleep every 200 entities so it never contends with an Unreal build.

### [high] Crash-safe write path: journal + atomic shard compaction
Observations arrive at 100-2,000/minute during normal use; rewriting shards per observation is unacceptable. Path: (1) an in-memory ConcurrentDictionary<string,Entity> holds the working set, dirty-flagged; (2) each mutation appends one minified delta line to journal.jsonl and fsyncs at most once per second (batched); (3) a flush runs every 60 s OR at 200 dirty entities OR on tray-exit/SERVICE_CONTROL_SHUTDOWN, grouping dirty entities by shard and rewriting only the touched shards; (4) each shard is written to <shard>.jsonl.tmp, flushed, then swapped with File.Replace(tmp, target, backupName: null, ignoreMetadataErrors: true) which is atomic on NTFS; (5) journal.jsonl is truncated after the last shard swap. On startup, if journal.jsonl is non-empty, replay it over the loaded shards before accepting new observations. Delta line shape: {"k":"p:9f2a…","op":"obs","t":1756800112,"d":{"n":1,"hr":11,"par":"p:1a2b…","cpu":2.3,"pvt":612.0}}

**How:** FileStream with FileOptions.WriteThrough for the journal; File.Replace(String,String,String,Boolean) for the swap. Register the shutdown flush on both SystemEvents.SessionEnding and AppDomain.CurrentDomain.ProcessExit, plus a WM_QUERYENDSESSION handler on the tray window via HwndSource.AddHook, because ProcessExit has a ~2 s budget that a 256-shard rewrite can exceed.

### [medium] Hash cache keyed by file identity, with partial hashing for large binaries
SHA-256 of a 900 MB Unreal editor binary at ~2 GB/s (SHA extensions on the 12900K) is ~450 ms and evicts a lot of page cache — doing that on every process start is unacceptable. Rules: files <= 64 MB are hashed in full; files > 64 MB get a partial identity = SHA-256 over (first 1 MiB || last 1 MiB || 8-byte little-endian file size) and are marked "part":true. A partial hash is sufficient for change detection but is explicitly NOT sufficient to satisfy a hash-scoped allowlist entry, which forces a full hash on first allow. hashcache.jsonl lines: {"id":"3:0x00040000000A1B2C","sz":4821504,"mt":1755099000,"h":"3f9c…","part":false,"sig":3,"cat":true,"ts":1756800112} where id is volumeSerial:fileId. Cache invalidates when size, mtime or fileId changes, and immediately on a ReadDirectoryChangesW notification for any directory containing a cached file. Cache is capped at 20,000 lines / 4 MB, LRU-evicted.

**How:** File identity via GetFileInformationByHandleEx(handle, FileIdInfo=18, out FILE_ID_INFO) — gives VolumeSerialNumber (ulong) and FileId (128-bit); fall back to BY_HANDLE_FILE_INFORMATION from GetFileInformationByHandle on volumes that reject FileIdInfo. Directory watching via System.IO.FileSystemWatcher (which is ReadDirectoryChangesW underneath) with NotifyFilters.LastWrite|FileName|Size, InternalBufferSize=64*1024, on the parent directories of allowlisted and persistence-referenced binaries only — never a recursive watch on C:\.

**False positives:** Open the file with FileShare.ReadWrite|FileShare.Delete or you will fail to hash actively-running or actively-written binaries and mint a spurious 'cannot verify' event on every compile.

### [critical] Bootstrap / quiet period: the first-run learning window
BootstrapComplete = (uptimeHoursObserved >= 72) AND (bootSessions >= 3) AND (distinctEntitiesObserved >= 300), with a hard ceiling of 14 calendar days after which it completes regardless. On this machine 300 distinct entities is reached within roughly the first hour of ordinary use, so the binding constraints are the 72 hours and 3 boots — which is exactly right, because the point is to see at least a weekday/weekend and a couple of cold-boot autorun cascades. During bootstrap: every entity is recorded in state 'learning'; MEDIUM never produces a toast (badge only); HIGH produces a toast but auto-action is restricted to dominant rules only (r >= 9.0); the behaviour term B is globally forced to 0 because per-entity envelopes are meaningless; the rarity term R is clamped to <= 0.65 because on day 2 literally everything is rare. A second, shorter re-bootstrap (24 h, B forced to 0 for affected entities only) is triggered by a Windows feature update, a user profile change, or a restore of the machine from backup — detected by manifest.hostId mismatch or a >30% churn in %SystemRoot%\System32 hashes in one day.

**How:** uptimeHoursObserved is accumulated by the service, not read from GetTickCount64 (a machine left off for a week must not skip bootstrap). bootSessions incremented once per service start where the boot time differs: DateTime.UtcNow - TimeSpan.FromMilliseconds(Environment.TickCount64). Feature-update detection: watch HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\UBR and DisplayVersion.

**False positives:** Do not gate bootstrap on wall-clock alone. A user who installs Warden on Friday evening and does not touch the PC until Monday would otherwise exit bootstrap with a baseline built entirely from idle-time background tasks, and then alert on every single interactive application on Monday morning.

### [critical] Graduation ladder: new -> observed -> familiar -> known -> trusted
State transitions, evaluated on every observation (all counts are post-decay):
  new       : n >= 1
  observed  : n >= 3 AND boots >= 2
  familiar  : n >= 8 AND ageDays >= 3 AND distinctDays >= 3
  known     : n >= 15 AND ageDays >= 14 AND distinctDays >= 7 AND no unresolved HIGH incident AND (sigT >= 1 OR user-allowed OR pathTrust >= 0.85)
  trusted   : state==known AND sigT >= 2 AND no incident of MEDIUM+ in the last 30 days AND ageDays >= 45
Demotion is immediate and unconditional: any HIGH incident drops the entity to 'observed'; a signer change or signature-invalid transition drops it to 'observed'; a user 'kill it' verdict drops it to 'blocked'. State affects scoring only through the rarity term (via n and age) and through two explicit gates: state >= familiar suppresses the 'unknown binary' provenance rule, and state == trusted permits the entity to act as a trust anchor for the earned-directory path tier and the signer-reputation tier. State never grants immunity to signerBlind rules — a 'trusted' binary that starts reading LSASS still trips.
FAST-TRACK (this is the answer to 'first observation of an already-trusted binary'): an entity whose first observation is catalog-signed (T3) and in a path with Pt >= 0.85, OR signed by a signer already holding >= 3 'known' entities on this host, enters directly at state 'familiar' with synthetic n = 8. This means installing a new Microsoft or NVIDIA component does not produce a single alert, while a brand-new unsigned binary in %APPDATA% still starts at 'new' with n = 0.

**How:** Pure computation over the entity record; implement as a computed property EntityState Evaluate(in Entity e, in HostContext ctx) so it is always derived, never persisted authoritatively (st in the JSON is a cache for UI speed and is recomputed on epoch bump).

**False positives:** distinctDays (a 32-bit bitmask of the last 32 days, 'dmask') is more robust than n for graduation: a build script that runs an executable 400 times in one afternoon should not graduate that executable to 'known' on day one. Store dmask alongside n and require the day-diversity clause.

### [high] Time decay: half-lives per channel, applied lazily with exponential sufficient statistics
Decay is applied at most once per 24 h per entity, on next touch, using lambda = 0.5^(deltaDays / H). Half-lives H: execution count n = 90 days; hour/day histograms = 45 days; parent/child edges = 60 days; network endpoints and ports = 30 days (network behaviour churns fastest); DNS names = 30 days; command-line templates = 90 days. For the Welford envelopes the correct move is to decay the sufficient statistics but NOT the mean: n' = lambda*n, m2' = lambda*m2, mu unchanged. This is the standard exponentially-weighted-moment trick and it means a process that changes its resource profile gradually is tracked, while a step change still shows as a z-score spike because the variance has not yet widened. After decay, prune any categorical key whose decayed count < 0.5 (it stays in the Bloom filter, so it comes back as seen-but-rare rather than as new). Worked example: an entity last seen 30 days ago with n=100 decays to 100*0.5^(30/90) = 100*0.794 = 79.4; its network endpoint counts decay to 100*0.5^(30/30) = 50. Concretely this means a tool you used heavily last quarter and not since is still 'known' (n=79) but its old C2-irrelevant endpoint list has halved and a new endpoint is meaningfully more surprising than it was.

**How:** double lambda = Math.Pow(0.5, deltaDays / H); store e.dec = unix timestamp of last decay. Apply inside a single EnsureDecayed(ref Entity, DateTime now) called at the top of every read and write path so no code path can forget it.

**False positives:** Do NOT decay firstSeen/ageDays. Age is the strongest single evidence that something is not a fresh dropper, and decaying it would make long-installed software periodically re-alert.

### [critical] Version rollover: how an app update avoids an alert storm
A new hash at an existing pathKey is classified, not alerted, by a decision table:
  (A) Same leaf CN AND same root thumbprint AND WinVerifyTrust OK -> VERSION ROLLOVER. Push the hash into the ring, inherit ALL behavioural statistics unchanged, keep state, set rarity contribution R := 0 for 24 h, emit an INFO event. Zero alerts. This is the common case and it must be silent.
  (B) Same signer but path is user-writable -> rollover, but re-arm behaviour monitoring for 24 h at 0.5x the usual deviation thresholds, emit LOW.
  (C) Previously signed, now unsigned, OR different signer, OR signature now invalid -> SIGNER BREAK. Retain behavioural stats but tag sigChanged, demote state to 'observed', add a +4.0 provenance rule hit, score normally (this typically lands MEDIUM and prompts).
  (D) Previously unsigned, still unsigned -> score the file-change as a +1.5 provenance hit if the writer is unknown, 0 if the writer is a known toolchain (see the developer-build item).
Corroborating evidence that upgrades (D)/(B) toward silence, each independently sufficient: the writing process is msiexec.exe, TrustedInstaller.exe, wuauclt.exe, winget.exe, or an entity already in state 'known' whose name matches *update*/*setup*/*installer*; the FileVersion increased monotonically; a PendingFileRenameOperations entry or a .tmp/.new -> rename sequence was observed; MoTW zone identifier absent.
UPDATE BURST COALESCING is the actual anti-storm mechanism: all new hashes appearing under the same install root within a 15-minute window that share a signer collapse into ONE incident titled '<ProductName> updated (N files)'. An OBS or Unreal update that rewrites 400 DLLs produces exactly one INFO row, not 400.

**How:** Writer attribution from ETW Kernel-File (GUID {EDD08927-9CC4-4E65-B970-C2560FB5C289}) Create/SetInformation events correlated by PID, or from the Security log 4663 object-access events when file auditing is enabled. FileVersion via FileVersionInfo.GetVersionInfo(path).FileVersion (in-box). PendingFileRenameOperations at HKLM\SYSTEM\CurrentControlSet\Control\Session Manager. MoTW via the :Zone.Identifier ADS: File.Exists(path + ":Zone.Identifier").

**False positives:** This is the single highest-value FP control in the whole design. Without burst coalescing, the first Windows cumulative update after install generates thousands of events; with it, one. Test explicitly against a `winget upgrade --all` run and an Unreal Engine version bump.

### [critical] Anti-poisoning: freeze learning inside an active incident
An adaptive baseline is itself an attack surface — the classic move against behavioural EDR is to run the malicious behaviour slowly and benignly for two weeks so the envelope widens to accommodate it. Three hard interlocks: (1) While a HIGH incident is open, ALL baseline writes for every process in that process tree are frozen — observations still go to the event log for forensics, but they never widen an envelope or increment a count. (2) An entity whose file failed WinVerifyTrust with an INVALID (not merely absent) signature is never learned from at all. (3) Envelope widening is rate-limited: sigma for any channel may grow by at most 15% per 24 h. A slow-burn attacker who ramps CPU from 1% to 60% over two weeks therefore still trips, because the variance cannot track the ramp fast enough. Additionally, the very first N=12 observations of any entity are recorded with a 'provisional' flag; if the entity is later killed by user verdict, those provisional observations are struck from the record so the attacker's training data is destroyed with it.

**How:** Implement as a HashSet<int> frozenPids + HashSet<string> frozenEntityKeys checked at the entry of BaselineStore.Observe(). Sigma growth limiter: after Welford update, sigmaNew = Math.Min(sigmaNew, sigmaAtLastDailyCheckpoint * 1.15); persist the daily checkpoint in the entity as a 'sg0' field.

**False positives:** The 15%/day sigma cap can under-fit a genuinely variable workload (Unreal shader compilation). Mitigate with the busy-mode global threshold shift rather than by relaxing the cap.

### [critical] Rarity term R
R = exp(-n/6)^0.7 * exp(-ageDays/10)^0.3 = exp(-0.11667*n - 0.03*ageDays), clamped to [0,1], where n is the decayed execution count and ageDays = (now - firstSeen)/86400. Reference values: (n=0,age=0) -> 1.000; (n=1,age=0) -> 0.890; (n=3,age=1) -> 0.683; (n=8,age=5) -> 0.339; (n=15,age=14) -> 0.114; (n=30,age=60) -> 0.005; (n=200,age=365) -> ~0. The count term dominates (weight 0.7) because 'I have run this 30 times' is stronger evidence than 'this file has existed for 30 days' — a dropper can backdate a file trivially but cannot fabricate execution history in Warden's own store. Weight Wr = 3.0, so R contributes at most 3.0 points. During bootstrap R is clamped to 0.65.

**How:** Pure function; unit-test the reference table above as a regression fixture so an epoch bump cannot silently change day-one behaviour.

### [critical] Behaviour term B: one-sided log z-scores, Good-Turing categorical surprise, noisy-OR combination
CONTINUOUS channels (cpu, pvt, thr, hnd). Requires n >= 12 else the channel contributes 0. sigma = max(sqrt(m2/(n-1)), sigmaFloor) with floors cpu=0.35, pvt=0.20, thr=0.25, hnd=0.30. z = (ln(1+x) - mu)/sigma, ONE-SIDED (negative z contributes nothing — a process using less CPU than usual is not a threat). b_c = clamp01((z - 3.0)/5.0), so z=3 -> 0.0, z=5.5 -> 0.5, z=8 -> 1.0.
CATEGORICAL channels (parent, child, cmd template, remote net, remote port, dns name, module dir, session/integrity). Good-Turing style: the probability that the NEXT observation is a category never seen before is p_new = d/(n_ch + d), where d = distinct categories observed and n_ch = total observations on that channel. Surprise on actually seeing a new one is b_cat = 1 - p_new, scaled by 0.35 if the category is in the Bloom filter (seen-but-evicted), and 0 if n_ch < 10. Worked: a browser that has hit 40 distinct /16s in 60 runs has p_new = 40/100 = 0.40, so a 41st network is only b=0.60 surprising; a service that has contacted exactly one /16 in 200 runs has p_new = 1/201 = 0.005, so a new network is b=0.995 surprising. That is the correct relative behaviour and it needs no per-application tuning.
COMBINATION by noisy-OR with per-channel weights kappa: B = 1 - PROD_i (1 - b_i * kappa_i). kappa: parent 0.70, session/integrity 0.90, cmd template 0.55, remote net 0.65, remote port 0.60, dns 0.60, module dir 0.80, cpu 0.50, pvt 0.45, thr 0.40, hnd 0.35. Noisy-OR is precisely the anti-double-counting device: six correlated network signals saturate toward 1.0 instead of summing to 6.0. Weight Wb = 6.0, so B contributes at most 6.0 points — the largest contextual term, and still not enough to reach HIGH alone.

**How:** Pure function over the entity record plus the live sample. Keep it allocation-free (stackalloc for the b_i array) — it runs on every process start and every 10-minute envelope window for ~400 processes.

**False positives:** The n>=12 gate and the sigma floors together are what stop the classic 'new process does something for the first time' false positive. Also exclude the 'child' channel entirely for known shells and build tools (cmd.exe, powershell.exe, pwsh.exe, bash.exe, dotnet.exe, MSBuild.exe, node.exe, python.exe, cargo.exe) — their child set is unbounded by nature and p_new correctly approaches 1 there anyway, but the kappa should be dropped to 0.15 for them to avoid a permanent low-grade hum.

### [critical] Rule catalogue: static point values, families, dominance and signer-blindness
Rules are SHIPPED and STATIC — they are the non-adaptive half of the score, and deliberately so (see the feedback item: user clicks must not be able to erode detection globally). Each rule has {id, family, points, dominant:bool, signerBlind:bool}. Families: Provenance, Persistence, Injection, Credential, Network, Resource, Evasion, UserContext. Representative catalogue with real values:
  CRED_LSASS_READ 9.5 Credential dominant signerBlind — OpenProcess/handle to lsass.exe with PROCESS_VM_READ|PROCESS_QUERY_INFORMATION by a non-allowlisted process.
  EVA_AMSI_PATCH 9.5 Evasion dominant signerBlind — cross-process write into amsi.dll or ntdll.dll .text.
  EVA_VSS_DELETE 9.5 Evasion dominant signerBlind — vssadmin delete shadows / wmic shadowcopy delete / Win32_ShadowCopy.Delete.
  EVA_BOOT_TAMPER 9.0 Evasion dominant signerBlind — bcdedit recoveryenabled No / bootstatuspolicy ignoreallfailures / safeboot.
  CRED_BROWSER_STORE 8.5 Credential signerBlind — read of \User Data\*\Login Data, Local State, or the Chromium key blob by a process that is not the owning browser.
  INJ_HOLLOW 8.0 Injection signerBlind — private RWX commit with no backing image section plus an image-base mismatch, or CreateRemoteThread/QueueUserAPC/SetThreadContext into an unrelated process.
  CRED_DPAPI_HARVEST 7.5 Credential signerBlind — read of %APPDATA%\Microsoft\Protect\<SID>\* by a non-system process.
  RES_CLIP_CRYPTO 7.0 Resource — clipboard viewer chain registration plus a BTC/ETH/XMR address regex in process memory or written to the clipboard.
  EVA_DEFENDER_EXCLUSION 6.0 Evasion signerBlind — write to HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions\* or Set-MpPreference -ExclusionPath.
  NET_BEACON 6.0 Network — >= 8 outbound connections to the same /16 with inter-arrival median 20-3600 s and IQR/median < 0.25 (low jitter), by an entity of state < familiar.
  EVA_LOLBIN_USERPATH 6.0 Evasion — rundll32/regsvr32/mshta/msbuild/installutil/certutil/wmic executing a module or script from a Pt <= 0.30 path with a parent never seen for that LOLBin.
  PER_RUNKEY_USERPATH 5.0 Persistence — Run/RunOnce/task/service created pointing at a Pt <= 0.30 path by a non-installer parent.
  PRO_SCRIPT_FROM_DOC 5.0 Provenance — wscript/cscript/mshta/powershell spawned by outlook/winword/excel/acrord32/a browser.
  NET_UNSIGNED_TEMP_EGRESS 4.5 Network — unsigned binary under %TEMP%/Downloads opening an outbound public connection.
  PRO_SIGNER_BREAK 4.0 Provenance — a previously-signed pathKey is now unsigned or signed by a different signer.
  RES_CRYPTOMINE 4.0 Resource — >= 85% GPU or >= 60% whole-machine CPU sustained 10 min by an entity of state < familiar, AND (an outbound connection on 3333/4444/5555/7777/14444 OR a stratum+tcp string).
  UCX_SESSION_ESCALATE 3.5 UserContext — an entity historically only seen at integrity medium/interactive now running as SYSTEM in session 0.
DOMINANCE: any rule with dominant:true that fires establishes a score FLOOR of 15.0 (HIGH) regardless of everything else; context can only add to it. That is the mechanism by which a single very strong signal dominates.
SIGNER ATTENUATION: rule points are multiplied by a = 1 - 0.25*max(0, Sg), so a T3-signed binary keeps 75% of its rule points — never more attenuation than that — and rules tagged signerBlind get a = 1.0 exactly.

**How:** Handle-to-lsass detection without a driver: enumerate handles with NtQuerySystemInformation(SystemExtendedHandleInformation=64), filter ObjectTypeIndex == the Process type index, resolve the target PID via NtDuplicateObject + NtQueryInformationProcess(ProcessBasicInformation), and test GrantedAccess & (PROCESS_VM_READ 0x0010 | PROCESS_QUERY_INFORMATION 0x0400). Cross-process RWX detection: VirtualQueryEx walk for MEM_PRIVATE + PAGE_EXECUTE_READWRITE regions >= 4 KiB, correlated with the ETW Kernel-Memory or Kernel-Process image-load stream. Beacon timing from the GetExtendedTcpTable delta stream. GPU utilisation from the PDH counters \GPU Engine(*engtype_3D)\Utilization Percentage via System.Diagnostics.PerformanceCounter (in-box in Microsoft.WindowsDesktop.App\10.0.11 on this machine). Defender exclusions readable at HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions (requires SYSTEM or an elevated token).

**False positives:** CRED_LSASS_READ fires on legitimate software: Task Manager, Process Explorer, Process Hacker, WinDbg, Defender's own MsMpEng, and some backup agents. Ship a narrow, hash-and-catalog-verified exception set for the in-box Windows tools and require an explicit user allow (hash+rule scope) for third-party debuggers. Given this user runs debuggers routinely, expect exactly one prompt for WinDbg/Process Explorer in the first week and make that prompt good.

### [critical] Score aggregation: the actual formula, with anti-double-counting and the precision gate
Step 1 — contextual score:
  Cs = 1 - Sg                (range 0 .. 1.35)
  Cp = 1 - Pt                (range 0 .. 1.00)
  Cp' = (R > 0.8 && Cp > 0.8) ? Cp * 0.6 : Cp      // decorrelation: new things naturally live in untrusted paths; do not charge twice for the same fact
  S_ctx = 3.0*R + 3.5*Cs + 3.0*Cp' + 6.0*B         // max 16.725
Step 2 — rule score with family suppression:
  for each family f, sort its fired rules descending by points; F_f = r(1) + 0.25*r(2) + 0*r(3..)  // within a family, corroboration is cheap; the third indicator of injection tells you nothing new
  a = 1 - 0.25*max(0, Sg); a_f uses a unless the rule is signerBlind, in which case 1.0
  S_rules = SUM_f (F_f * a_f)
Step 3 — the precision gate (the single most important line in the engine):
  if (S_rules == 0) S_ctx = min(S_ctx, 9.9)
  This guarantees that pure statistics can never reach HIGH and therefore can never trigger an automated action. Novel + unsigned + in %TEMP% + behaving oddly maxes out at 9.9 = top of LOW.
Step 4 — total and dominance floor:
  S = S_ctx + S_rules
  if (any fired rule has dominant:true) S = max(S, 15.0)
Step 5 — confidence, computed independently of severity:
  C = 0.35*q_ident + 0.30*q_evidence + 0.20*q_history + 0.15*q_corrob, clamped [0,1]
    q_ident   = 1.0 full hash + signature evaluated + kernel-sourced image path; 0.6 partial hash; 0.3 process exited before the image could be read
    q_evidence= 1.0 ETW-sourced; 0.7 poller-inferred; 0.5 registry-snapshot-inferred
    q_history = min(1, hostBaselineDays/14)
    q_corrob  = 1.0 if >= 2 rule families fired; 0.6 if exactly one dominant rule; 0.3 if exactly one non-dominant rule; 0.0 if none

**How:** Implement as a single pure static ScoreResult Score(in Entity e, in Observation o, ReadOnlySpan<RuleHit> hits, in HostContext ctx) returning {double points, double confidence, Severity tier, RuleHit[] contributing, string[] explain}. The explain array is not optional — every alert must be able to render 'why' as a list of term names with their point contributions, because an unexplainable alert is one the user learns to dismiss.

### [critical] Thresholds, tiers and the auto-action interlock
Severity by points S:
  S <  4.0        INFO    — event log only, no UI at all
  4.0 <= S < 10.0 LOW     — dashboard row + tray badge count; NEVER a toast
  10.0 <= S < 15.0 MEDIUM — grouped notification, dashboard prompt, NEVER an automated action
  S >= 15.0       HIGH    — toast + incident card, and eligible for automated action
AUTOMATED ACTION (suspend threads -> quarantine -> terminate) requires ALL of:
  1. S >= 15.0
  2. C >= 0.80
  3. (>= 2 distinct rule families fired) OR (a dominant rule fired)
  4. no matching, non-expired, HMAC-valid allowlist entry
  5. the target is not protected: not in {System, Registry, Memory Compression, smss, csrss, wininit, winlogon, services, lsass, lsaiso, fontdrvhost, dwm, MsMpEng, SecurityHealthService, TrustedInstaller}, not RtlSetProcessIsCritical, not a protected process (PPL), and not a service whose failure action is reboot
  6. not inside the bootstrap window, unless a dominant rule fired
If 1-4 hold but 5 fails, the action is downgraded to alert-only with an explicit 'this is a protected system process — Warden will not touch it' explanation; that is the un-brickable guarantee. If 1-3 hold but C < 0.80, it becomes a MEDIUM-style prompt with the HIGH visual treatment: 'Warden is fairly sure but wants your call.'

**How:** Protected-process check: NtQueryInformationProcess(h, ProcessProtectionInformation=61, out PS_PROTECTION) — nonzero Level means do not touch. Critical-process check: NtQueryInformationProcess(h, ProcessBreakOnTermination=29). Suspend before terminate via NtSuspendProcess so the quarantine copy is taken from a frozen process and the user can still be asked; only call TerminateProcess after the quarantine move succeeds and its restore manifest is fsynced.

### [high] Developer-build heuristic (host-specific FP suppressor)
This machine compiles binaries constantly (dotnet, cargo, node, Unreal, slot-math sims). Without a specific suppressor, every build output is an unsigned, zero-history executable in a user-writable path. Rule: if the file's lastWriteUtc is within 10 minutes of first execution AND the writing process (or an ancestor of the executing process) is an entity in state 'known' whose tokenised path matches a toolchain set {dotnet.exe, MSBuild.exe, csc.dll host, link.exe, cl.exe, cargo.exe, rustc.exe, node.exe, python.exe, UnrealBuildTool.exe, ninja.exe, cmake.exe, go.exe} AND the file lives under a directory containing >= 20 'known' entities, then apply R *= 0.4 and Pt += 0.25 (capped at 0.80). This is a contextual adjustment only — it NEVER touches rule points, so a compiled binary that then reads LSASS still scores exactly as it should. Additionally, entities matching this heuristic that are never executed again within 7 days are pruned early (they are build artefacts, not installed software) to stop the entity count from ballooning: expect ~50-300 such transients per week on this machine.

**How:** Writer attribution from the ETW Kernel-File stream, or fall back to 'nearest known toolchain ancestor in the process tree at exec time' from the parent chain already being tracked. Directory-known-count is already computed for the earned-directory path tier — reuse the same cache.

**False positives:** Bound the toolchain set to entities in state 'known' and verify the toolchain binary's own signature, otherwise dropping a file named MSBuild.exe into a temp folder becomes a universal suppression bypass.

### [critical] Feedback: verdict types and what each one actually changes
Five verdicts, each with a precisely defined model effect:
  ALLOW_ONCE — suppress for this process instance only. Writes nothing to the baseline. Used for 'I know what this is right now'.
  SNOOZE_24H — suppress this (entityKey, ruleId) pair for 24 h. Writes an allowlist entry with exp = now+86400.
  ALLOW — the default 'this is fine'. Creates an allowlist entry scoped to the TRIPLE (codeHash, pathKey, ruleId). Also injects 8 pseudo-observations into the entity at the observed values of every channel that contributed to B, and sets fb.a += 1. The pseudo-observation is the important part: feedback flows into the SAME model rather than into a bypass list, so the next slightly-different instance of the same behaviour scores lower naturally instead of needing another click.
  TRUST_PUBLISHER_AT_PATH — the explicit second option. Creates an entry scoped to (leafThumbprint, rootThumbprint, pathKey, ruleId) with a hard 365-day absolute lifetime. Offered ONLY when the binary is validly signed AND (the signer is EV OR already owns >= 1 'known' entity on this host). Never signer-only, never path-only.
  KILL — quarantine + terminate. Adds the codeHash to the blocklist; sets fb.d += 1; if the signer is not T3, signers.json denies += 1 (2 denies permanently demote that signer to T0); reduces the containing directory's earned-path bonus by 0.15 (floored at the nominal tier); strikes the entity's provisional (first 12) observations from the record; demotes state to 'blocked'.
GLOBAL LEARNING BOUNDARY: user verdicts NEVER change rule point values globally, with one bounded, auditable exception — after >= 5 ALLOW verdicts on the same ruleId across >= 3 DISTINCT entities, that rule's points are multiplied by 0.8 (floor: 60% of nominal, i.e. at most two such reductions), and the reduction is displayed in the UI as 'Warden has softened rule X because you have told it this is fine 5 times'. Rules tagged dominant or signerBlind are exempt entirely. This is what stops a single user's clicks from silently hollowing out detection.

**How:** Verdicts append to baseline\verdicts.jsonl: {"ts":…,"incident":"inc_…","k":"p:…","h":"3f9c…","rule":"NET_BEACON","verdict":"allow","scope":"hash+path+rule","ui":"toast","fgOk":true,"nonce":"…"}. Never prune this file.

### [critical] Allowlist integrity: HMAC, DPAPI, pipe ACL, foreground validation, trust rate limits
An allowlist is a persistence mechanism if an attacker can write to it, so it is defended as one. Entry shape (allowlist.jsonl, one per line):
{"id":"al_01J8…","scope":"hash+path+rule","h":"3f9c…","k":"p:9f2a…","fid":"3:0x0004…","sz":4821504,"mt":1755099000,"sig":{"lt":"8B7F…","rt":"A898…"},"rule":"NET_BEACON","cond":{"ports":[443],"maxCpu":12.0},"by":"user","ts":1756800112,"exp":1788336112,"hits":12,"lastHit":…,"revoked":false,"mac":"<base64 HMAC-SHA256>"}
Defences:
  1. mac = HMAC-SHA256 over the canonical serialisation of every field except mac, keyed by a 32-byte random key generated at install and sealed with ProtectedData.Protect(key, entropy, DataProtectionScope.LocalMachine). A line with a bad or missing MAC is IGNORED and raises a MEDIUM 'allowlist tampering detected' incident naming the affected entry. Hand-editing the file, or a stealer writing to it, therefore fails loudly.
  2. Only the Warden service writes the file. The WPF UI submits verdicts over a NamedPipeServerStream whose PipeSecurity grants ReadWrite to exactly LocalSystem + the interactive user SID and denies everything else; the UI must present a per-session nonce the service issued at UI launch.
  3. Clickjacking / synthetic-input defence: at verdict time the service verifies that GetForegroundWindow() was Warden's own HWND, that GetGUIThreadInfo reports Warden's thread as active, and that GetLastInputInfo shows real user input within the last 5 seconds. A verdict failing any check is rejected and logged as an incident.
  4. Trust rate limits: at most 5 new ALLOW entries per rolling hour and 20 per rolling day. Beyond that the dialog requires a 10-second enforced delay plus typing the application name. This defeats the 'spray 50 prompts, slip one past' pattern.
  5. No ALLOW may be created while an unresolved HIGH incident exists for a DIFFERENT entity — the classic distraction play.
  6. TRUST_PUBLISHER_AT_PATH requires the signer to be EV or to already own a 'known' entity, per the previous item.
  7. There is no auto-allow. Ever. Aging into 'known' lowers scores; it does not create allowlist entries.

**How:** System.Security.Cryptography.ProtectedData (in-box), HMACSHA256, System.IO.Pipes.NamedPipeServerStream with PipeSecurity (System.IO.Pipes.AccessControl.dll is in Microsoft.NETCore.App\10.0.11 on this machine). GetForegroundWindow/GetGUIThreadInfo/GetLastInputInfo from user32.dll. Own HWND via new WindowInteropHelper(window).Handle.

**False positives:** The MACHINE-scoped DPAPI key is readable by anything running as the user, so the HMAC is an integrity check against casual tampering and non-elevated stealers, not a cryptographic barrier against an already-SYSTEM attacker. Be honest about that in the docs. If the user later runs Warden's monitor as a service under LocalSystem with the baseline directory ACL'd to exclude Users:Write, the guarantee becomes real.

### [critical] Allowlist staleness: re-verification, path substitution, expiry, trust review
An allowlist entry must be re-proved every time it is used, not just when it is created. On every match attempt:
  1. Resolve the current file identity (volumeSerial, fileId, size, lastWriteUtc). If ANY of size/mtime/fileId differs from the stored values, the cached hash is discarded and the file is re-hashed synchronously.
  2. For hash-scoped entries: the SHA-256 must match exactly. Mismatch -> the entry does NOT apply, and Warden raises a MEDIUM 'an application you approved has changed' event with the old and new FileVersion, the signer of both, and a one-click re-approve. This is the direct answer to path substitution.
  3. For signer+path entries: WinVerifyTrust is re-run at match time (WTD_REVOKE_NONE, cache-only) and the leaf AND root thumbprints must equal the pinned values. A different cert from the same CN does not match.
  4. Expiry: ALLOW_ONCE = process lifetime; SNOOZE = 24 h; hash-scoped = revoked after 365 days with no hit (lastHit based, so software you use stays approved); signer+path = 365 days absolute from creation, no renewal-by-use.
  5. A FileSystemWatcher is registered on the parent directory of every allowlisted binary (NotifyFilters.LastWrite|FileName|Size); a notification invalidates the hash cache entry immediately rather than waiting for the next execution.
  6. Weekly 'Trust review' panel: lists entries with hits == 0 or lastHit older than 90 days, entries whose target file no longer exists, entries whose signer has since been demoted, and offers bulk revoke. Revocation is a tombstone line, not a deletion, so the audit trail survives.

**How:** GetFileInformationByHandleEx(FileIdInfo) as above; FileSystemWatcher; the same WinVerifyTrust helper. Tombstone: append {"id":"al_01J8…","revoked":true,"ts":…,"mac":"…"} and honour last-write-wins per id during load.

**False positives:** Do not re-hash a large file synchronously on the process-start hot path. If the file exceeds 64 MB, apply the entry provisionally using the partial identity, let the process run, and complete the full hash on a background worker within ~2 s; if it then mismatches, raise the incident and act. The alternative — stalling process creation for 450 ms — is worse than the risk.

### [high] Incident model: correlation keys and dedup windows
Events are never shown directly; they are folded into incidents. An event joins an OPEN incident if it matches on the correlation key (processTreeRootPid, entityKey, ruleFamily) within the merge window, OR if it shares the processTreeRootPid with an open incident of MEDIUM+ (a compromised tree produces one incident, not twenty). Merge window: 10 minutes from the last member event, extended by 10 minutes on each new member, capped at 4 hours total, after which a new incident is opened. Incident severity = max member severity; the card shows 'x N events' and the full timeline. Dedup key for identical repeats: SHA-1(entityKey | ruleId | targetKey) — the first occurrence alerts, and repeats within 6 hours only increment count and update lastSeen without re-notifying; the tray badge number changes but no new toast fires. Per-entity alert budget: any single entity may originate at most 3 distinct alerts per 24 h; further events attach to the most recent open incident regardless of family. Incident record: {"id":"inc_01J8…","open":true,"sev":"high","pts":33.1,"conf":1.0,"first":…,"last":…,"n":7,"root":"p:1a2b…","ents":["p:…"],"rules":[{"id":"CRED_BROWSER_STORE","n":2}],"action":"quarantined","restore":"quarantine\\inc_01J8…\\manifest.json"}

**How:** Process tree root resolved from the tracked parent chain, walking up until the parent is explorer.exe, services.exe, a session-0 host, or is gone; cache the root per PID with the process creation time to defeat PID reuse (always compare (pid, createTime) pairs, never pid alone).

**False positives:** PID reuse on a busy dev machine is real. Every PID reference in the correlation logic must be the tuple (pid, FILETIME createTime) or you will merge an unrelated process into an incident and mis-attribute an action.

### [high] Alert budget: per-severity token buckets and a hard global ceiling
Token buckets, checked before any toast:
  HIGH:   capacity 4, refill 1 per 15 min. On overflow, collapse into a single 'N critical detections' toast at most once per 5 min. Note: automated ACTIONS are never rate-limited — only the notifications about them are. Warden always acts; it just stops shouting.
  MEDIUM: capacity 3, refill 1 per 60 min. On overflow -> badge only, folded into the next digest.
  LOW:    no toasts at all, ever. Badge counter + dashboard row.
  INFO:   no UI.
Global hard ceiling: 6 toasts per rolling hour and 20 per rolling day across all severities. If the ceiling is hit, everything below HIGH is silently deferred to the digest and the tray icon changes state to indicate suppression, so the user can see that Warden is holding things back rather than being quiet because nothing is happening.
DIGEST: one notification at the first unlock of each day, summarising everything at LOW/MEDIUM since the last digest, grouped by entity. Max one per day.
REPEAT-DISMISSAL DEMOTION: if the same dedup signature has been shown and dismissed (not allowed, not killed — dismissed) 3 times, auto-demote that signature to LOW permanently and surface an inline 'stop telling me about this' control that creates a properly scoped allowlist entry rather than a mute. Muting without a scoped entry is forbidden — a silent mute is an invisible security hole.

**How:** Token buckets as a small struct with lastRefillUtc + double tokens, persisted in state so a service restart cannot be used to reset the budget. Digest trigger via SystemEvents.SessionSwitch (SessionSwitchReason.SessionUnlock / SessionLogon).

### [high] Quiet hours, Focus Assist, fullscreen and busy mode
Notification gating reads the shell's own notification state rather than guessing:
  QUNS_RUNNING_D3D_FULL_SCREEN (fullscreen game / Unreal PIE), QUNS_PRESENTATION_MODE, QUNS_BUSY, QUNS_QUIET_TIME -> suppress MEDIUM entirely; downgrade HIGH to a silent toast (no sound, no focus steal) but STILL perform any automated action; queue the visual for when the state returns to QUNS_ACCEPTS_NOTIFICATIONS.
  User-configurable quiet window, default 23:00-08:00 local: only HIGH may toast, and silently.
BUSY MODE (a distinct concept, and important on this machine): when a 'known' entity is consuming > 40% whole-machine CPU or > 70% GPU for more than 60 s — an Unreal cook, a Blender render, a slot-math Monte Carlo run — the machine's resource baselines are simply not the ones that were learned. In busy mode: add +1.5 to the z-threshold for all continuous channels globally (b_c = clamp01((z - 4.5)/5.0)); halve kappa for cpu/pvt/thr/hnd; and suppress RES_CRYPTOMINE for entities in state >= familiar. Categorical channels, all Credential/Injection/Evasion/Persistence rules, and every dominant rule are UNAFFECTED by busy mode — a heavy render must never become a window to steal credentials in.

**How:** SHQueryUserNotificationState() from shell32.dll returning QUERY_USER_NOTIFICATION_STATE (QUNS_NOT_PRESENT=1, QUNS_BUSY=2, QUNS_RUNNING_D3D_FULL_SCREEN=3, QUNS_PRESENTATION_MODE=4, QUNS_ACCEPTS_NOTIFICATIONS=5, QUNS_QUIET_TIME=6, QUNS_APP=7). Poll at 5 s, and re-check immediately before showing any toast. GPU load via PerformanceCounter on \GPU Engine(*)\Utilization Percentage. Toasts through the in-box System.Windows.Forms.NotifyIcon (ShowBalloonTip) since UseWindowsForms is already enabled for the tray.

**False positives:** Do not read Focus Assist state out of the CloudStore registry blobs — the format is undocumented and has changed repeatedly across Windows 11 builds. SHQueryUserNotificationState is the supported surface and it already reflects Focus Assist as QUNS_QUIET_TIME.

### [critical] Cold start #1: the signer-blind rule floor, armed from minute zero
Before any baseline exists, the dominant + signerBlind subset of the rule catalogue is fully armed and is the only thing permitted to take automated action during bootstrap: CRED_LSASS_READ, EVA_AMSI_PATCH, EVA_VSS_DELETE, EVA_BOOT_TAMPER, CRED_BROWSER_STORE, INJ_HOLLOW, CRED_DPAPI_HARVEST, EVA_DEFENDER_EXCLUSION, plus event-log clearing (wevtutil cl / EventLog 1102), RDP enablement (HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server\fDenyTSConnections -> 0), UAC disablement (EnableLUA -> 0), and Safe Mode network-service registration. These are machine-independent: they require no history, they are rare on a healthy machine, and every one of them is high-precision. This set is what makes Warden non-useless in hour one.

**How:** Handle enumeration via NtQuerySystemInformation(SystemExtendedHandleInformation=64) at 10 s during bootstrap. Registry tamper detection via RegNotifyChangeKeyValue on the specific keys (advapi32, REG_NOTIFY_CHANGE_LAST_SET, asynchronous with an event handle) rather than polling. Log-clear detection via EventLogWatcher on 'Security' with query "*[System[EventID=1102]]" — System.Diagnostics.EventLog.dll is in-box in Microsoft.WindowsDesktop.App\10.0.11 on this machine.

### [critical] Cold start #2: install-time autorun, signature and network census with a triage inbox
On first run, a background census (throttled to <= 10% of one core, ~3-6 minutes on this machine) produces the single most valuable day-one artefact: a ranked triage inbox. It enumerates and scores EVERY persistence location listed in the persistence-entity item, plus every running process and every autorun target, using the same scoring formula with R fixed at the day-one default. It then presents the TOP 20 by score, grouped by directory, with a signature verdict and a one-click quarantine/allow on each. Also produced: (a) a signature census — unsigned executables in user-writable paths (grouped by directory so a node_modules tree is one row, not 400), invalid or revoked signatures (rare and always worth a look), and name/signer mismatches (a file called chrome.exe not signed by Google LLC); (b) a network census from the current connection tables — listeners bound to 0.0.0.0 or :: on non-standard ports owned by unsigned or user-path binaries, and established outbound connections from unsigned user-path binaries. Expect on this machine roughly 350-450 scheduled tasks, 40-80 Run-key entries, 300+ services, and a triage inbox of 8-25 genuinely-worth-looking-at rows once the Microsoft/TrustedInstaller/catalog-signed suppressions apply.

**How:** Persistence enumeration APIs as listed in the persistence item. Connections via GetExtendedTcpTable / GetExtendedUdpTable. Throttle by processing in batches with Thread.Sleep and by running at ProcessPriorityClass.BelowNormal with THREAD_MODE_BACKGROUND_BEGIN (SetThreadPriority(GetCurrentThread(), 0x00010000)) so file I/O is deprioritised too.

**False positives:** Cap the inbox at 20 rows and sort by score. A 300-row 'here is everything unsigned on your PC' list on day one is the fastest possible way to teach a user to ignore the product. If more than 20 rows exceed the threshold, show 20 and a 'show N more' link.

### [high] Cold start #3: Windows catalog membership as a zero-history trust source
The most powerful day-one trust signal that needs no learning and no network: proving a file is a genuine, catalog-signed Windows component. Most of System32 is not Authenticode-signed inline — it is signed by membership in a .cat file under %SystemRoot%\System32\CatRoot. Verifying catalog membership gives T3 (Sg=1.00) for several thousand files instantly and correctly, which collapses the day-one noise floor enormously. Flip side and equally valuable: a file sitting in System32 that is NOT in any catalog and is not inline-signed is a genuinely strong day-one anomaly worth surfacing at MEDIUM.

**How:** CryptCATAdminAcquireContext2(out hCatAdmin, IntPtr.Zero, "SHA256", IntPtr.Zero, 0) -> CryptCATAdminCalcHashFromFileHandle2(hCatAdmin, hFile, ref cbHash, pbHash, 0) -> CryptCATAdminEnumCatalogFromHash(hCatAdmin, pbHash, cbHash, 0, IntPtr.Zero); a non-null catalog handle means membership. Then verify the catalog itself with WinVerifyTrust using a WINTRUST_CATALOG_INFO structure. All in wintrust.dll, zero NuGet. Cache the result in hashcache.jsonl ("cat":true).

### [medium] Cold start #4: static, history-free heuristics
Signals computable from a file alone, used to give the day-one score some texture where there is no history: Shannon entropy per PE section (a .text section above 7.2 bits/byte suggests packing; use it as a weak +1.0 provenance signal only, never alone — legitimate installers and protected commercial software are packed too); missing or blank CompanyName/ProductName version resources on a non-Microsoft-path binary; PE TimeDateStamp in the future, or newer than 7 days for something already registered as an autorun; extension/PE-type mismatch (a .txt or .jpg that is actually MZ/PE); Mark-of-the-Web present (:Zone.Identifier with ZoneId=3) on a binary that is executing or is an autorun target; double extensions (invoice.pdf.exe); RTL-override or other bidi format characters in the filename; icon spoofing (an executable whose primary icon group resembles a folder, PDF or document icon — cheap perceptual hash against a small shipped set); a subsystem of GUI with no window ever created; an image that is 100% ASCII-printable (a script renamed to .exe).

**How:** PE parsing by hand over a MemoryMappedFile — read IMAGE_DOS_HEADER.e_lfanew, IMAGE_NT_HEADERS, then IMAGE_SECTION_HEADERs; zero dependencies, ~50 lines. Version resources via FileVersionInfo.GetVersionInfo (in-box). MoTW via File.ReadAllText(path + ":Zone.Identifier"). Icons via the in-box System.Drawing.Icon.ExtractAssociatedIcon plus a 8x8 average-hash comparison.

**False positives:** Packing entropy is the classic FP generator — UPX-packed indie game tools, Themida-protected commercial software and most Electron/NSIS installers all look packed. Cap its contribution at +1.0 and require it to combine with an untrusted path or an unsigned state before it moves a tier.

### [high] Cold start #5: shipped offline priors and the LOLBin parentage set
Ship two small, fully offline data files (no network, ever, consistent with the no-egress constraint):
  (a) trust-seeds.json — ~1,200 (leaf CN, root thumbprint) pairs for widely-deployed publishers, used ONLY to grant an initial T2 rather than T1. This shortens the first week; it is not a whitelist and grants no immunity.
  (b) lolbins.json — the abused-LOLBin set with per-binary PARENTAGE and ARGUMENT expectations, e.g. rundll32.exe {expectedParents: [explorer.exe, svchost.exe, dllhost.exe, control.exe], suspiciousArgs: ["javascript:", "url.dll,FileProtocolHandler", "advpack.dll,LaunchINFSection", "shell32.dll,ShellExec_RunDLL", "comsvcs.dll,MiniDump"]}, regsvr32 {"scrobj.dll", "/i:http", "/u /n /s"}, mshta {any http/https/javascript: argument}, certutil {"-urlcache", "-decode", "-encode"}, bitsadmin {"/transfer"}, msbuild {inline task XML from a user-writable path}, wmic {"process call create", "/node:"}, curl {"-o" into a user-writable path followed by execution}. This is machine-independent knowledge and it is the reason Warden can catch signed-binary abuse on day one, before it has learned that rundll32 on this box normally has exactly six parents.
Both files are versioned and hashed; they are DATA the engine reads, not code, and they are never fetched at runtime.

**How:** Embed as compressed resources or ship alongside the exe under a directory with the same hardened DACL as the baseline; verify their SHA-256 against constants compiled into the assembly at load so a local attacker cannot neuter detection by editing lolbins.json.

**False positives:** comsvcs.dll,MiniDump is genuinely used by a few legitimate crash-reporting tools; keep it at high points but not dominant, and let the LSASS-target check upgrade it.

### [high] Cold start #6: day-one scoring defaults and honest progress UX
With no baseline: R is fixed at 0.65 for every entity (not 1.0 — on day one everything is 'new' and a 1.0 rarity on every process is meaningless and would drown the score); B is forced to 0 for continuous channels and to 0 for categorical channels with n_ch < 10; the earned-directory path tier is unavailable until 20 entities in a directory reach 'known', so it comes online around day 14; signer reputation promotion to T2 is unavailable (only EV and trust-seeds grant T2 early). Actions are alert-only except for dominant rules. UX: the dashboard shows an explicit 'Learning your PC — day 3 of 7' progress element with live counters (entities learned, publishers recognised, autoruns catalogued, persistence entries baselined), the triage inbox as the primary day-one surface, and a plain-language note that alerting gets quieter and sharper as the baseline fills. The engine must also expose a 'why did this score what it did' breakdown on every row from day one — during the learning period the explanation is the product.

**How:** manifest.learnState in {"bootstrap","warming","steady"}; expose it and the counters through the same view-model that drives the dashboard so the progress element cannot drift from reality.

## Risks
- Sensor fidelity is the binding constraint, not the model. Without ETW (which requires admin and hand-rolled P/Invoke to StartTraceW/EnableTraceEx2/OpenTraceW/ProcessTrace) the fallback NtQuerySystemInformation poller at 2 Hz will miss short-lived processes entirely — and droppers are short-lived. A polling-only build will silently under-detect the exact class of threat it is aimed at. Decide early: ship as an elevated service with real ETW, or accept a materially weaker product.
- Microsoft-Windows-Threat-Intelligence (the ETW provider that gives cross-process memory writes and remote thread creation with full fidelity) requires the consumer to be a PPL anti-malware process, which needs an Early Launch Antimalware driver and a Microsoft-issued signing certificate. Warden cannot have it. INJ_HOLLOW and the LSASS handle rules must therefore be built on handle enumeration and VirtualQueryEx polling, which are racier and can be evaded by a determined attacker. Document this honestly rather than implying EDR-grade injection detection.
- The 15%/day sigma growth cap that defeats slow-burn baseline poisoning will also under-fit genuinely variable dev workloads, producing periodic resource false positives on Unreal cooks and long Monte Carlo runs. Busy mode mitigates it; verify empirically over a real fortnight of this user's work before shipping the numbers.
- Alert fatigue is quantified nowhere in this design except by construction. The token buckets, dedup and coalescing are all guesses until measured. Instrument from day one: log every event's severity and every notification decision, and treat 'toasts per day' as a tracked product metric with a target of under 2. If the first fortnight produces more than that, the thresholds are wrong, not the user.
- The DPAPI-sealed HMAC key protects the allowlist against casual tampering and non-elevated stealers, but any code running as the user can unseal it. Against an already-SYSTEM attacker the allowlist is not defensible in user-mode at all. Do not overstate this in the UI.
- Automated kill-and-quarantine on a dev machine has a long tail of expensive mistakes: quarantining a build artefact mid-compile, a debugger, a game anti-cheat component, or a BlueStacks/root-related binary. The two-family corroboration requirement and the confidence >= 0.80 gate are the defence, but the quarantine vault must be genuinely one-click reversible including the original DACL, ADS streams and file identity, or the first false positive destroys trust permanently.
- Handle enumeration via SystemExtendedHandleInformation is expensive on a busy machine (tens of thousands of handles) and NtDuplicateObject can hang on certain pipe and device objects. Do it on a dedicated thread with a watchdog, never on the UI or the sampling thread, and cap the rate to once per 10 s.
- PID reuse will cause mis-attribution if any code path compares bare PIDs. This is a correctness bug that manifests as killing the wrong process. Every PID must be carried as (pid, creation FILETIME).
- The Good-Turing p_new estimator degrades when the top-K map is small relative to true category diversity; the Bloom filter mitigates eviction but its 2.6% false-positive rate softens some genuinely novel categories to 'seen-but-rare'. That is a deliberate recall sacrifice for precision, but it means the network novelty channel alone should never be load-bearing for an automated action.
- The shipped rule catalogue is the non-adaptive half and it will age. There is no update channel by design (no network egress). Rules will need to ship with app versions, and the bounded per-rule softening from user feedback could, over years, quietly reduce a set of rules to 60% of nominal. The UI surfacing of softened rules is the only mitigation — make it prominent in the trust review panel.
- Storing the user's SID and full file paths in the baseline is unavoidable for the model but makes %LOCALAPPDATA%\Warden a mild information-disclosure target for any infostealer that already has user-level access. The hardened DACL helps only against other users, not the same user. Consider DPAPI-sealing the whole baseline at rest as a later hardening step, accepting the load-time cost.

## Implementation notes
FRAMEWORK AVAILABILITY — verified on this exact machine, not assumed. Microsoft.NETCore.App\10.0.11 contains System.Security.AccessControl.dll, System.IO.FileSystem.AccessControl.dll, System.IO.Pipes.AccessControl.dll and System.Security.Principal.Windows.dll, so all DACL, SID and named-pipe-security work is in-box with zero NuGet. Microsoft.WindowsDesktop.App\10.0.11 contains System.Diagnostics.EventLog.dll (EventLogWatcher for Security 4688 / 1102), System.Security.Cryptography.Pkcs.dll (SignedCms for Authenticode countersignature and timestamp parsing) and System.Diagnostics.PerformanceCounter.dll (PDH-backed GPU/CPU counters). Because the project targets net10.0-windows with UseWPF+UseWindowsForms, it references the WindowsDesktop framework and gets all of these for free. System.Management.dll is NOT present in either shared framework — WMI persistence enumeration must use hand-rolled IWbemLocator/IWbemServices COM interop or shell out to powershell.exe -NoProfile -NonInteractive with Get-CimInstance | ConvertTo-Json. Do not add the System.Management NuGet package without an explicit decision.

EXISTING CODE — D:\My projects\warden\src\Warden\ already holds a WPF skeleton (App.xaml, MainWindow.xaml, Warden.csproj) with Warden.slnx at D:\My projects\warden\Warden.slnx. Suggested split: Warden.Core (no WPF dependency, holds the whole engine so it is unit-testable headlessly), Warden.Native (P/Invoke only), Warden.Service (the elevated monitor), Warden (the WPF tray + dashboard). Put every formula in Warden.Core as pure static functions over structs.

BUILD ORDER — the dependency chain matters. 1) Warden.Native P/Invoke layer plus a headless harness that dumps process/network/signature snapshots to JSONL; run it for 48 hours on this machine before writing any scoring code, because every threshold in this document is a starting estimate that must be validated against real data from this box. 2) BaselineStore (schema, journal, shards, decay, migrations) with a synthetic-event replay test. 3) Scorer as a pure function with the four worked examples as fixtures. 4) Rule engine. 5) Incident/notification layer. 6) Feedback and allowlist with the pipe and HMAC. 7) UI last. Building the UI first will bake the wrong data model in.

ELEVATION — the monitor needs SeDebugPrivilege (handle enumeration, cross-process reads), SeSecurityPrivilege (some ACL reads), and admin for ETW session creation and for reading HKLM Defender keys. Run the monitor as a Windows service under LocalSystem and the dashboard as a normal-integrity WPF app, talking over the ACL'd named pipe. Do NOT run the WPF app elevated — an elevated GUI is a UAC-fatigue and shatter-attack liability, and the foreground-window verdict validation is cleaner across the pipe anyway. Enable SeDebugPrivilege explicitly with OpenProcessToken + LookupPrivilegeValueW + AdjustTokenPrivileges; it is present but disabled by default even for SYSTEM.

ORDERING CONSTRAINTS INSIDE THE ENGINE — (a) EnsureDecayed() must run before any read or write of an entity, enforced at the single entry point of BaselineStore, not sprinkled at call sites. (b) Update classification (version rollover vs signer break) must run BEFORE scoring, because it can zero the rarity term. (c) Allowlist matching must run BEFORE the auto-action gate but AFTER scoring, so the dashboard can still show 'this would have scored 22, suppressed by your approval' — a suppressed detection that leaves no trace is how allowlists rot. (d) Quarantine must complete and its restore manifest must be fsynced before TerminateProcess is called. (e) manifest.json is written last during a flush.

COMMAND-LINE AUDITING — several rules need process command lines. Reading them from the PEB is racy and fails across integrity levels. The reliable route is Security 4688 with command line included, which requires two one-time changes that the user must approve explicitly (they are system policy changes): auditpol.exe /set /subcategory:"Process Creation" /success:enable, and HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\Audit\ProcessCreationIncludeCmdLine_Enabled = 1 (DWORD). Warden must ask before making these, explain that they increase Security log volume (budget ~200 MB/day on this machine, so also raise the Security log max size), and offer to revert them on uninstall. Do not enable them silently.

NUMBERS TO RE-VALIDATE AGAINST REAL DATA before shipping, in priority order: the 0.11667/0.03 rarity coefficients; the z-score offset of 3.0 and divisor of 5.0; the four sigma floors; the eleven kappa weights; the 9.9 context cap; the 15.0 HIGH threshold; the token bucket capacities. All of these live in one static class with a single [ModelEpoch] constant so a retune is a one-line epoch bump and requires no data migration — that is the entire point of storing raw observations rather than scores.

PERFORMANCE BUDGET — target: under 1.5% of one core averaged over an hour, under 120 MB working set, zero perceptible impact on a Unreal build. Measured components on this hardware: NtQuerySystemInformation at 2 s over ~400 processes is ~1.5 ms per call (0.075% of one core); GetExtendedTcpTable at 2 s is ~0.3 ms; SHA-256 at ~2 GB/s with SHA extensions; WinVerifyTrust at 5-40 ms per uncached file, which is why the hash/signature cache is not optional. Handle enumeration is the expensive one — 10 s period, dedicated thread, watchdog.

TESTING — build a replay harness that reads a day of events\*.jsonl and re-runs the whole pipeline offline. Every threshold change should be evaluated by replaying a captured week and reporting the delta in (toasts, prompts, auto-actions). Also build a small red-team fixture set: a benign-looking beaconing binary, a fake credential reader against a decoy file, a simulated update burst, and a slow-ramp resource poisoner, all of which must be safe to run and must produce the documented tiers.

  - **Fix:** Add `<FrameworkReference Include="Microsoft.WindowsDesktop.App" />` (or `<UseWindowsForms>true</UseWindowsForms>`) to Warden.Core and Warden.Service, and state that "no WPF dependency" means "no WPF types used", not "does not reference the desktop framework". Only System.Security.AccessControl, System.IO.FileSystem.AccessControl, System.IO.Pipes.AccessControl and System.Security.Principal.Windows are genuinely in Microsoft.NETCore.App (verified).
- **Claim:** "Run the monitor as a Windows service under LocalSystem" ... "on tray-exit/SERVICE_CONTROL_SHUTDOWN"
  - **Why wrong:** Verified: System.ServiceProcess.ServiceController.dll is absent from BOTH Microsoft.NETCore.App\10.0.11 and Microsoft.WindowsDesktop.App\10.0.11. `ServiceBase` therefore does not exist under the zero-NuGet constraint, and Microsoft.Extensions.Hosting.WindowsServices depends on that same NuGet package. The spec never acknowledges this and it is on the critical path.
  - **Fix:** Either explicitly accept the System.ServiceProcess.ServiceController NuGet package as a documented exception, or hand-roll the service host: StartServiceCtrlDispatcherW + RegisterServiceCtrlHandlerExW + SetServiceStatus via advapi32 P/Invoke in Warden.Native. Also note SERVICE_ACCEPT_PRESHUTDOWN gives a much larger flush budget than SERVICE_CONTROL_SHUTDOWN.
- **Claim:** "On-disk layout under %LOCALAPPDATA%\Warden" with `Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData)`.
  - **Why wrong:** The monitor runs as LocalSystem. From a LocalSystem service that call returns C:\Windows\System32\config\systemprofile\AppData\Local, not the user's profile. The service and the WPF UI would resolve two different roots, so the store the service writes is not the store the dashboard reads. It also breaks path tokenisation: %LOCALAPPDATA%/%APPDATA%/%TEMP%/%USERPROFILE% expand to systemprofile paths in the service, so every user-path entity would be tokenised wrongly and the entire Pt tier table would misfire.
  - **Fix:** Put the store under %ProgramData%\Warden (machine-scoped, matches the LocalSystem writer and the hardened DACL story). Resolve the interactive user's profile explicitly via WTSQueryUserToken + SHGetKnownFolderPath(FOLDERID_LocalAppData, token) for tokenisation, and cache the per-SID token map.
- **Claim:** "each shard is written to <shard>.jsonl.tmp, flushed, then swapped with File.Replace(tmp, target, backupName: null, ignoreMetadataErrors: true) which is atomic on NTFS"
  - **Why wrong:** File.Replace (ReplaceFile) requires the destination file to already exist — it throws FileNotFoundException on the first write of any of the 256 shards, and on any shard that was pruned to empty. It also fails across volumes and can fail if any reader holds the destination open. The design will crash on first run, on all 256 shards.
  - **Fix:** if (!File.Exists(target)) File.Move(tmp, target); else File.Replace(...). Wrap in a retry for ERROR_SHARING_VIOLATION. Same fix for manifest.json.
- **Claim:** "WTD_REVOKE_NONE + CACHE_ONLY is mandatory: it guarantees zero network egress, which is a non-negotiable product constraint."
  - **Why wrong:** It is not a guarantee. Chain building still triggers CryptoAPI's automatic root update (ctldl.windowsupdate.com) and AIA fetches for missing intermediates through paths WTD_CACHE_ONLY_URL_RETRIEVAL does not fully cover. Worse, the design separately builds an X509Chain to obtain the root thumbprint for the signer tier, and X509Chain by default performs online CRL/OCSP and certificate downloads. Second problem: the T-1 tier is defined as "tampered, revoked, untrusted root..." but revocation checking is explicitly disabled, so "revoked" can never be observed — an internal contradiction.
  - **Fix:** Set X509ChainPolicy.RevocationMode = NoCheck AND X509ChainPolicy.DisableCertificateDownloads = true (both available on .NET 10). Set the machine policy or accept residual egress and say so honestly. Remove "revoked" from the T-1 definition, or add an explicit opt-in revocation mode.
- **Claim:** "Signer leaf via new X509Certificate2(X509Certificate.CreateFromSignedFile(path))"
  - **Why wrong:** CreateFromSignedFile throws CryptographicException for any file without an embedded Authenticode signature — which is most of System32, i.e. exactly the files the catalog-membership item says are the common case. It also returns only the leaf; there is no chain, so the design's pinned root thumbprint and EV flag are not obtainable from it. X509Certificate2 is IDisposable and the census will create thousands of them.
  - **Fix:** Try/catch and fall through to the catalog path. Get leaf+chain from the WINTRUST_DATA after WinVerifyTrust via WTHelperProvDataFromStateData/WTHelperGetProvSignerFromChain, or parse the PKCS#7 with SignedCms. Dispose every cert and chain.
- **Claim:** "QueryFullProcessImageNameW(PROCESS_QUERY_LIMITED_INFORMATION, PROCESS_NAME_NATIVE=0)" and "Device path mapping via QueryDosDeviceW"
  - **Why wrong:** Two errors. PROCESS_QUERY_LIMITED_INFORMATION is an OpenProcess access right, not an argument to QueryFullProcessImageNameW. And PROCESS_NAME_NATIVE is 0x00000001; 0 is the Win32-path flag. As written the code either won't compile against a correct signature or, if it does, requests the native \Device\HarddiskVolumeN form — after which the QueryDosDeviceW mapping step is needed. If you pass 0 you already get the Win32 path and the mapping step is dead code.
  - **Fix:** OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION,...) then QueryFullProcessImageNameW(h, 0, buf, ref len). Keep the QueryDosDeviceW mapper only for ETW ImageName, which genuinely is a native device path.
- **Claim:** "Cp' = (R > 0.8 && Cp > 0.8) ? Cp * 0.6 : Cp  // decorrelation"
  - **Why wrong:** This creates a non-monotonicity that inverts the path signal. A new unsigned binary in %TEMP% (Pt=0.10, Cp=0.90) gets Cp'=0.54 → 1.62 points. The same binary in %APPDATA%\Roaming (Pt=0.30, Cp=0.70, no discount) gets 2.10 points. The less-trusted location scores 0.48 points LOWER. Downloads and $Recycle.Bin have the same inversion. The worked RAT example sits at %APPDATA% and would score less if moved to %TEMP%.
  - **Fix:** Make the decorrelation continuous and monotone, e.g. Cp' = Cp * (1 - 0.4 * R * Cp), or subtract a mutual-information term. Add a monotonicity unit test: for fixed R, S must be non-decreasing as Pt decreases.
- **Claim:** "Step 3 — the precision gate ... if (S_rules == 0) S_ctx = min(S_ctx, 9.9). This guarantees that pure statistics can never reach HIGH"
  - **Why wrong:** The gate is binary, so the guarantee only holds in the zero-rule case. The instant any single rule fires — including the weakest one in the catalogue, UCX_SESSION_ESCALATE at 3.5 points, which fires routinely on powershell.exe/cmd.exe/msiexec/dotnet running both interactively and as SYSTEM — the ceiling jumps from 9.9 to 16.725 + 3.5 = 20.2. So one low-value rule plus statistics produces a HIGH toast. The summary's "context alone is capped at 9.9 and can never reach the HIGH threshold" is only true for a case that essentially never occurs in an incident.
  - **Fix:** Make the cap graded rather than binary: cap S_ctx at min(9.9, 3.0 + 2.0 * S_rules) or similar, so context can only escalate in proportion to corroborating rule evidence. Add a regression fixture asserting that one 3.5-point rule at maximum context stays below 15.0.
- **Claim:** "GPU utilisation from the PDH counters \GPU Engine(*engtype_3D)\Utilization Percentage via System.Diagnostics.PerformanceCounter"
  - **Why wrong:** Three problems. (a) PerformanceCounter does not accept wildcard instance names; GPU Engine instances are literal strings like `pid_1234_luid_0x00000000_0x0000A1B2_phys_0_eng_0_engtype_3D` and must be enumerated with PerformanceCounterCategory.GetInstanceNames() and summed per PID. (b) engtype_3D is the wrong engine for the threat: GPU miners use engtype_Compute / Cuda / VideoEncode, so RES_CRYPTOMINE's GPU arm misses actual miners. (c) engtype_3D is exactly what Blender Cycles viewport, Unreal PIE and any game peg to 100%, so the counter you chose is the one that fires on legitimate work and not on the threat.
  - **Fix:** Enumerate instances, group by pid_ prefix, and sum engtype_Compute + Cuda for the mining signal while explicitly excluding engtype_3D/VideoDecode from it. Note PDH GPU counters may not be available at all in session 0.
- **Claim:** "Toasts through the in-box System.Windows.Forms.NotifyIcon (ShowBalloonTip)" while the design requires one-click quarantine/allow on the card, an inline "stop telling me about this" control, and grouped notifications.
  - **Why wrong:** NotifyIcon balloon tips have no action buttons, no inline controls, no grouping and no per-notification identity. They are also routed through the Windows notification platform, so app-level notification settings silently swallow them. The actionable UI the alert model requires needs ToastNotificationManager, which requires a Windows-version TFM (net10.0-windows10.0.26100.0) for the built-in CsWinRT projection, plus an AppUserModelID shortcut and a registered COM activator for background activation.
  - **Fix:** Change the TFM to net10.0-windows10.0.26100.0 (still zero NuGet — the projection ships with the SDK), register an AUMID, and use ToastNotificationManagerCompat-style activation. Or accept badge-only interaction and move all verdict-taking into the dashboard window, and say so.
- **Claim:** "Register the shutdown flush on both SystemEvents.SessionEnding and AppDomain.CurrentDomain.ProcessExit" and "DIGEST trigger via SystemEvents.SessionSwitch"
  - **Why wrong:** Microsoft.Win32.SystemEvents relies on a hidden top-level window receiving WM_ broadcasts in an interactive window station. In a LocalSystem service in session 0, SessionEnding does not fire and SessionSwitch is unreliable. Services receive session changes only via SERVICE_CONTROL_SESSIONCHANGE through RegisterServiceCtrlHandlerExW.
  - **Fix:** In the service use RegisterServiceCtrlHandlerExW with SERVICE_ACCEPT_SESSIONCHANGE and SERVICE_ACCEPT_PRESHUTDOWN. Keep SystemEvents only in the WPF UI process.
- **Claim:** "Defender exclusions readable at HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions (requires SYSTEM or an elevated token)" and "Registry tamper detection via RegNotifyChangeKeyValue on the specific keys"
  - **Why wrong:** Verified on this machine: opening HKLM\SOFTWARE\Microsoft\Windows Defender succeeds, but HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions returns "Requested registry access is not allowed." That subkey is ACL'd away from Administrators (and in practice from SYSTEM) as a Defender hardening measure; you generally need TrustedInstaller-level impersonation. RegNotifyChangeKeyValue cannot watch a key you cannot open. Separately, RegNotifyChangeKeyValue is one-shot (must be re-armed after every signal), tells you neither what changed nor who changed it, and the notification is torn down when the registering thread exits unless REG_NOTIFY_THREAD_AGNOSTIC (0x10000000) is passed — a classic bug when arming from thread-pool threads.
  - **Fix:** Read exclusions via Get-MpPreference / the MSFT_MpPreference CIM class, and detect changes from the Microsoft-Windows-Windows Defender/Operational log (event 5007, "configuration changed"), which is the supported and attributable signal. Add REG_NOTIFY_THREAD_AGNOSTIC and a re-arm loop everywhere RegNotifyChangeKeyValue is used.
- **Claim:** "bootSessions incremented once per service start where the boot time differs: DateTime.UtcNow - TimeSpan.FromMilliseconds(Environment.TickCount64)"
  - **Why wrong:** Environment.TickCount64 wraps GetTickCount64, which on Windows excludes time spent in sleep/hibernate. On a desktop that sleeps, the derived "boot time" drifts by the accumulated sleep duration, so consecutive service starts within one real boot session look like different boots. bootSessions inflates, and the bootstrap gate (bootSessions >= 3) completes early on a baseline built from one boot.
  - **Fix:** Read the real boot time from the System event log (6005/6013) or from SYSTEM_TIMEOFDAY_INFORMATION / the WMI LastBootUpTime, or compare a boot-scoped GUID written into a volatile registry key (HKLM\...\Volatile Environment style).
- **Claim:** "A second, shorter re-bootstrap ... triggered by a Windows feature update, a user profile change, or a restore of the machine from backup — detected by manifest.hostId mismatch or a >30% churn in %SystemRoot%\System32 hashes in one day."
  - **Why wrong:** hostId = SHA256(MachineGuid | systemVolumeSerial). None of the three listed triggers changes MachineGuid or the volume serial: a feature update preserves both, a user profile change is orthogonal, and a restore from backup restores both. So the primary detector detects none of its stated triggers. The fallback — measuring 30% hash churn across System32 daily — requires hashing several thousand System32 files every day, which contradicts the stated 1.5%-of-one-core budget and the whole point of the hash cache.
  - **Fix:** Trigger re-bootstrap on the signals the spec already watches: a change in HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\{CurrentBuild, UBR, DisplayVersion}, or the presence of a WinSxS pending-transaction / a Setup event log 1042/1074. Keep hostId only for the "this store came from a different machine" case.
- **Claim:** "At ~1.0-1.4 KB minified per entity that is 5-11 MB" and "under 120 MB working set"
  - **Why wrong:** The stated record shape does not fit in 1.4 KB. The 8-entry hash ring alone is ~130 bytes per entry (64 hex chars plus fs/ls/n/sz/fv/part and keys) = ~1.04 KB. Four 512-bit Bloom filters base64-encoded are 4 x 88 = 352 bytes. Add up to 12+12+8+32+16+24+16 = 120 categorical map entries at ~15-25 bytes each = 1.8-3.0 KB, plus sig (~200 B), path, and two histograms. A fully-populated entity is 3-5 KB, so 8,000 entities is 25-40 MB on disk, not 5-11 MB, and the 64 MB hard cap is much closer than stated. Worse, the design holds the whole working set in a ConcurrentDictionary<string,Entity> of deserialised objects (nested dictionaries, boxed strings), which is 4-8x the JSON size — 150-300 MB managed heap, blowing the 120 MB working-set target.
  - **Fix:** Re-derive the size table honestly. Store hashes as 32-byte binary base64 (44 chars, not 64) or truncate the ring to 4. Do not hold cold entities in memory: keep an LRU of the ~500 active entities and page the rest from shards on demand.
- **Claim:** "256 shards keeps each file ~25-30 KB ... so a compaction rewrites 30 KB not 8 MB"
  - **Why wrong:** At 6,000 entities there are only ~23 entities per shard. A flush triggered at "200 dirty entities" will, for randomly distributed pathKeys, touch roughly 1 - (255/256)^200 ≈ 54% of all shards — i.e. ~138 of 256 files rewritten per flush. The sharding buys far less than claimed, and 138 file creates + File.Replace calls per minute is a lot of NTFS metadata churn.
  - **Fix:** Either reduce to 16-32 shards (accepting larger rewrites but far fewer file operations), or switch to a log-structured store where the journal IS the store and compaction is periodic rather than per-flush.
- **Claim:** "Corroborating evidence that upgrades (D)/(B) toward silence, each independently sufficient: ... MoTW zone identifier absent."
  - **Why wrong:** Absence of Mark-of-the-Web is not evidence of benignity — it is the default for anything written by curl, git, npm, cargo, an installer, a script, or an attacker who simply did not set it (or ran Unblock-File). Treating its absence as independently sufficient to silence an alert makes silence attacker-controlled with zero effort. It is also silently absent for every file on a non-NTFS or network volume.
  - **Fix:** Use MoTW presence as a positive risk signal only. Never use its absence as corroborating evidence for anything. Also read it with FindFirstStreamW or GetFileAttributes on the stream rather than File.Exists(path + ":Zone.Identifier"), which returns false indistinguishably for "no stream" and "access denied".
- **Claim:** "Suppress any task whose Author or Principal is TrustedInstaller/SYSTEM AND whose Actions point into %SystemRoot% or %ProgramFiles% AND whose target is catalog-signed" and "parse C:\Windows\System32\Tasks\**\* XML directly"
  - **Why wrong:** The Author element of a task XML is a free-text string chosen by whoever registered the task — an attacker writes `<Author>Microsoft Corporation</Author>` for free. Suppressing on Author is a one-line bypass of the largest persistence surface. Separately, enumerating only the Tasks XML tree misses the standard task-hiding technique: deleting the `SD` value under HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree\<task> makes the task invisible to schtasks and ITaskService while still executing.
  - **Fix:** Suppress on Principal (the resolved SID) plus catalog-signed action target only; never on Author. Enumerate the union of the Tasks XML tree, TaskCache\Tree and TaskCache\Tasks, and treat any asymmetry between the three as a high-signal detection in its own right.
- **Claim:** "mac = HMAC-SHA256 ... keyed by a 32-byte random key ... sealed with ProtectedData.Protect(key, entropy, DataProtectionScope.LocalMachine)" and "the MACHINE-scoped DPAPI key is readable by anything running as the user"
  - **Why wrong:** Understated: LocalMachine-scoped DPAPI is unsealable by ANY process on the machine at any integrity level, including other user accounts and low-integrity sandboxes — not just "anything running as the user". The optional entropy is compiled into the assembly and is therefore public. So the allowlist HMAC is not even an integrity check against a non-elevated stealer, which is the exact threat it claims to stop.
  - **Fix:** Have the LocalSystem service hold the key in a file or registry value ACL'd to SYSTEM only (no DPAPI needed once the ACL is right), and make the service the sole MAC computer and verifier. Then the guarantee is real against user-level attackers, and the docs can say so.
- **Claim:** "NtQuerySystemInformation(SystemExtendedHandleInformation=64), filter ObjectTypeIndex == the Process type index"
  - **Why wrong:** The Process ObjectTypeIndex is not a constant — it varies across Windows builds and must be resolved at runtime. Hardcoding it (a common shortcut) silently disables CRED_LSASS_READ after any OS update, and the design has no way to notice. Additionally, NtDuplicateObject requires PROCESS_DUP_HANDLE on the *source* process, which you cannot obtain against PPL processes (MsMpEng, and lsass itself when RunAsPPL is on), so those sources are invisible.
  - **Fix:** Resolve the index once at startup by opening a known process handle and calling NtQueryObject(ObjectTypeInformation), or enumerate via NtQueryObject(ObjectTypesInformation). Add a self-test that fails loudly if the Process type index cannot be resolved, so a broken sensor is visible rather than silent.

### False-positive risks
- HEADLINE, arithmetic-verified: any per-user Electron/Squirrel app install auto-quarantines itself after bootstrap. Take %LOCALAPPDATA%\Discord\Update.exe (equally Cursor, VS Code, Slack, Teams, Postman, GitHub Desktop, Spotify, Obsidian). Signed non-EV → Sg=0.55; first seen → R=1.0; Pt=0.30 → Cp=0.70, and the R>0.8 && Cp>0.8 decorrelation does NOT apply. S_ctx = 3.0 + 1.575 + 2.10 + 0 = 6.675. It writes an HKCU Run key pointing into a Pt<=0.30 path from a non-installer parent (the Squirrel stub downloaded to %TEMP%) → PER_RUNKEY_USERPATH 5.0, Persistence. It polls its update endpoint on a fixed interval to one CDN /16 while state is still 'new' → NET_BEACON 6.0, Network. Attenuation a = 1 - 0.25*0.55 = 0.8625, neither rule is signerBlind, different families so no intra-family suppression: S_rules = 4.3125 + 5.175 = 9.4875. S = 16.16 → HIGH. Two distinct families, so gate 3 passes. Confidence with ETW: 0.35 + 0.30 + 0.20*(days/14) + 0.15 ≥ 0.80 from day 0. Result: suspend + quarantine + terminate a legitimate app the user just installed. This defeats the design's own stated safety property — "at least two independent rule families" is not a sufficient auto-action gate, because Persistence+Network is the normal signature of every modern per-user auto-updating app on Windows. Fix: require at least one Credential/Injection/Evasion rule or a dominant rule for auto-action; Persistence+Network alone must prompt.
- INJ_HOLLOW's detectable arm fires on every JIT on this machine. "Private RWX commit with no backing image section" describes node.exe/V8, every Electron app (VS Code, Discord, Slack, Cursor), BlueStacks' ART runtime, Mono/Unity, the JVM, Python with numba, and .NET dynamic methods when W^X is off. 8.0 points, signerBlind (so no attenuation for signed Chrome or signed node). One more family and it is a HIGH auto-kill of the user's editor mid-session. The image-base-mismatch conjunct narrows it only for hollowing, not for JIT. Meanwhile the OR arm (CreateRemoteThread/QueueUserAPC/SetThreadContext) is (a) admitted-undetectable without Threat-Intelligence ETW and (b) legitimately performed constantly on a gaming/dev box by the Steam overlay, Discord overlay, NVIDIA/GeForce Experience overlay, RivaTuner/MSI Afterburner, OBS game-capture hook, and debuggers.
- CRED_LSASS_READ on a developer box is not "exactly one prompt for WinDbg/Process Explorer in the first week". The same handle pattern is produced by System Informer/Process Hacker, Sysinternals tools, Visual Studio's diagnostic hub, dotnet-dump / dotnet-trace / dotnet-counters, procdump, ETW-based profilers, Defender's own MsMpEng, and any backup or telemetry agent that walks all PIDs with PROCESS_QUERY_INFORMATION|PROCESS_VM_READ. Warden itself does exactly this and must be explicitly excluded or it will detect itself. At 9.5 points and dominant:true this establishes a 15.0 floor, so a single misfire is an immediate HIGH with auto-action eligibility.
- CRED_BROWSER_STORE / CRED_DPAPI_HARVEST have no specified sensor, and the only in-box sensors are ruinous. Detecting "a read of \User Data\*\Login Data" or "a read of %APPDATA%\Microsoft\Protect\<SID>\*" requires either Kernel-File ETW (see the volume problem below) or SACL object-access auditing on the user's own profile — a system audit-policy change plus SACL modification of user data the spec never mentions. Behaviourally, the FP set includes Edge importing from Chrome on first run, browser automation run with --user-data-dir pointed at a real profile (Playwright/Puppeteer/Selenium, which this user plausibly runs), profile backup/sync tools, and any app calling CryptUnprotectData, which necessarily touches the Protect directory.
- RES_CRYPTOMINE's port list collides directly with this machine's toolchain. 5555 is ADB — BlueStacks-with-root uses network ADB on 5555 constantly. 4444 is the Selenium Grid default. 7777 is a common Unreal/game server port. The rule does not exclude loopback or RFC1918 destinations, so an ADB connection to 127.0.0.1:5555 satisfies the network conjunct. Combined with the >=60% whole-machine CPU threshold, which a slot-math Monte Carlo run, an Unreal cook or a Blender render trivially exceeds, and "state < familiar" which is true for the first 3+ days of anything newly installed, this fires. Fix: require a public, non-RFC1918 destination, require the port AND a stratum/mining-pool DNS name, and drop 4444/5555/7777 entirely in favour of the DNS-name signal.
- "path length > 200" → Pt = 0.00 (pathological) is a guaranteed permanent FP source on this exact machine. node_modules trees routinely exceed 200 characters, and Unreal's Intermediate/Build output paths exceed it as a matter of course. Every esbuild/swc/native-node binary and every Unreal intermediate executable therefore gets Cp = 1.00 (3.0 context points) forever, and is simultaneously disqualified from the earned-directory tier. Fix: raise the threshold to the real MAX_PATH-extension boundary (or drop it entirely) and key "pathological" on the bidi/ADS/trailing-dot checks, which are the ones with actual signal.
- The earned-directory tier (Pt=0.55) that worked example 1 depends on will probably never activate for build output. It requires ">= 20 entities already in state 'known'" in the tree, and 'known' requires ageDays >= 14 AND distinctDays >= 7. Build artefacts are, by the design's own developer-build heuristic, pruned after 7 days without re-execution. So D:\My projects\nova-hoard\bin\Release can never accumulate 20 'known' entities — the tier only ever promotes the *toolchain* directories, which are already %ProgramFiles%. Example 1's assumption of Pt=0.55 on day one is therefore wrong twice over: it is unavailable on day one by construction, and unreachable later. Compounding this: the Pt table has NO entry for arbitrary paths on D:/E:/F:, so the default is undefined for the drive where all of this user's work lives.
- EVA_LOLBIN_USERPATH will fire on ordinary software maintenance. Chrome, Edge, Teams, Discord and OneDrive updaters invoke rundll32/regsvr32 from %LOCALAPPDATA% (Pt=0.30, so <= 0.30 is satisfied) with parents that rotate constantly, and rundll32's parent set on this box legitimately churns through installers, Control Panel applets, printer drivers and Explorer context-menu handlers. `curl -o <user-writable path>` followed by execution is what npm postinstall, cargo build scripts and winget do routinely. `msbuild` is in the LOLBin list on a machine that runs MSBuild dozens of times a day.
- UCX_SESSION_ESCALATE (3.5, UserContext) fires on the ordinary lifecycle of powershell.exe, pwsh.exe, cmd.exe, msiexec.exe, dotnet.exe, python.exe and node.exe — all of which the user runs interactively and all of which are also run as SYSTEM by installers, scheduled tasks and services. This matters far beyond its 3.5 points because, per the precision-gate cliff, one firing rule lifts the context ceiling from 9.9 to 20.2.
- Update-burst coalescing will not coalesce the two updates that matter most. A Windows cumulative update writes files into WinSxS, System32, SysWOW64 and drivers over tens of minutes to hours, from TrustedInstaller — not "under the same install root within a 15-minute window". An Unreal Engine or Steam update writes large volumes of *unsigned* content (cooked binaries, plugin DLLs, shader caches) that share no signer. Both blow through the 15-minute / same-root / same-signer conjunction and produce exactly the storm the mechanism exists to prevent. Fix: coalesce on writer identity (TrustedInstaller/msiexec/winget/a known updater entity) with a much longer window, in addition to the install-root rule.
- Busy mode cannot engage during the period it is most needed. It triggers only when "a 'known' entity" exceeds 40% CPU / 70% GPU, and 'known' requires ageDays >= 14 AND distinctDays >= 7 AND n >= 15. For the entire bootstrap-plus-warming period — the first two weeks, when the user forms their opinion of the product — no entity is 'known', so no Unreal cook, Blender render or Monte Carlo run can put the machine into busy mode. Fix: trigger busy mode on machine-wide load regardless of which entity is causing it.
- BlueStacks-with-root is a worst-case entity for this design and is never mentioned outside the risks list: it ships kernel drivers, a hypervisor, self-signed or unusual-signer components, an ADB listener on 5555, ART JIT (private RWX), sustained CPU/GPU, and root tooling that manipulates process tokens. It will light up INJ_HOLLOW, RES_CRYPTOMINE's port arm, the listener census and the path/signer tiers simultaneously. The design needs an explicit pre-ship test against it.
- Census volume estimates are unvalidated and at least one is wrong. The spec expects "roughly 350-450 scheduled tasks"; measured on this machine (non-elevated, so if anything an undercount of hidden tasks) Get-ScheduledTask returns 219. If the triage-inbox ranking was tuned against a 350-450 baseline, its thresholds are miscalibrated. Every other census estimate in the document (40-80 Run keys, 300+ services, 8-25 inbox rows, 4,000-8,000 executables) is asserted with the same confidence and none is measured.

### Safety objections
- MACHINE-BRICKING: nothing in the design prevents quarantining a Windows system binary. The auto-action gate checks whether the *process* is protected (by name!), but the quarantine action moves the *file*, and there is no check on the file's path, catalog membership, service/driver references, or WinSxS hardlink status. A LOLBin abuse case where two non-dominant families fire — e.g. PRO_SCRIPT_FROM_DOC (5.0, Provenance) plus EVA_LOLBIN_USERPATH (6.0, Evasion) on mshta.exe or rundll32.exe, with a saturated B term — lands above 15.0 with two families and auto-quarantines C:\Windows\System32\mshta.exe. Moving a System32 file breaks its WinSxS hardlink, breaks SFC/DISM, and can break servicing for every future update. This is the single most dangerous hole in the document. Fix: a hard, non-overridable rule that Warden never moves, renames or modifies any file that is catalog-signed, resides under %SystemRoot%, is the ImagePath of a service or driver, or is hardlinked into WinSxS. For LOLBin abuse the quarantine target must be the payload (the DLL, script or INF), never the signed host binary — and the design never draws that distinction.
- The un-killable protected-process list is name-based and therefore an evasion primitive. "not in {System, Registry, Memory Compression, smss, csrss, wininit, winlogon, services, lsass, lsaiso, fontdrvhost, dwm, MsMpEng, SecurityHealthService, TrustedInstaller}" — a RAT named lsass.exe in %APPDATA% is now immune to Warden's automated action by construction. Fix: protection must be established by (image path under %SystemRoot%\System32 AND catalog-signed AND expected parent/session), or better, purely by NtQueryInformationProcess(ProcessProtectionInformation) + ProcessBreakOnTermination + the SCM's service-failure-action query, with the name list used only as a redundant belt.
- There is no circuit breaker on automated actions. The spec explicitly states "automated ACTIONS are never rate-limited — only the notifications about them are", while the notification budget caps visibility at 4 HIGH toasts and 6 total per hour. A systematic false positive — INJ_HOLLOW firing on every Electron app after a Windows update, or a rule regression after an epoch bump — can therefore quarantine and terminate dozens of applications while the user sees a single "N critical detections" toast. This is the catastrophic-failure mode of the entire product. Fix: hard-cap auto-actions at 2 per hour / 4 per day; on the third, switch globally to prompt-only, raise a distinct "Warden is acting unusually often" alert, and require explicit re-arming.
- Ordering constraint (d) "Quarantine must complete and its restore manifest must be fsynced before TerminateProcess is called" is unimplementable for the common case. The vault lives under %LOCALAPPDATA%\Warden\quarantine on C:. A malicious binary on D:/E:/F: requires a cross-volume move, which is copy-then-delete, and the delete of a currently-mapped executable image fails. So for any payload not on C: you either terminate first (violating the stated ordering and losing the frozen-process guarantee) or fail to quarantine and leave the file in place while having killed the process. Fix: per-volume vault directories so every quarantine is a same-volume rename, which also works on running images.
- Restore fidelity is asserted in the risks list but never designed. The risks section correctly says the vault "must be genuinely one-click reversible including the original DACL, ADS streams and file identity, or the first false positive destroys trust permanently" — and then no item specifies the restore manifest, how DACLs/owner/ADS/timestamps/hardlinks/reparse points are captured, or what happens when the original directory has since been deleted. Given that a false positive on a build artefact or a debugger is expected, this is the most under-specified critical path in the document.
- Defender will fight Warden in both directions, and neither is addressed. (a) Warden moving live malware into %LOCALAPPDATA%\Warden\quarantine triggers a Defender real-time scan of the destination; Defender deletes or quarantines it, and Warden's restore manifest now points at nothing — the reversibility guarantee is void. (b) Warden's own behaviour — SeDebugPrivilege, mass handle enumeration, NtDuplicateObject across processes, VirtualQueryEx/ReadProcessMemory sweeps, scanning process memory for BTC/XMR address regexes — is the exact behavioural profile of an infostealer and will be flagged by Defender, and certainly by any third-party EDR. Controlled Folder Access may also block Warden's writes outright. Fix: strip execute and rename on quarantine before the move lands, request a Defender exclusion for the vault as an explicit user-consented step, and document the AV-interaction story.
- Enabling 4688 with ProcessCreationIncludeCmdLine_Enabled has an unacknowledged data-exposure cost. It writes every process command line on the machine into the Security log — including tokens, API keys, connection strings and passwords passed as arguments, which on a developer box is routine (npm/cargo/gh/az/docker/dotnet CLI invocations). That log is readable by any local administrator and is collected by many backup and telemetry agents. The spec presents this as a volume/consent question only. Fix: state the credential-exposure risk explicitly in the consent dialog, and note that in a GPO-managed environment the auditpol change is silently reverted on the next policy refresh, which will silently disable EVA_VSS_DELETE, EVA_BOOT_TAMPER and every other command-line-dependent rule with no visible degradation.
- ALLOW injecting 8 pseudo-observations bypasses the anti-poisoning sigma limiter. The design's stated defence against slow-burn envelope widening is "sigma for any channel may grow by at most 15% per 24 h", checkpointed daily. But an ALLOW verdict writes 8 observations at the observed (extreme) values in one instant, which is a single-step variance widening that the daily checkpoint cannot rate-limit. One socially-engineered or mis-clicked ALLOW permanently widens the envelope for that entity. Fix: route pseudo-observations through the same daily sigma checkpoint, cap their combined effect at one day's allowed growth, and never let a pseudo-observation update m2 at all.
- The bounded rule-softening mechanism erodes exactly the two rules that carry RAT detection. Softening applies after 5 ALLOWs across 3 distinct entities, exempting only dominant and signerBlind rules. NET_BEACON is neither — and it is the rule most certain to accumulate ALLOWs (Docker, Steam, Epic, OneDrive, Dropbox, Discord, NVIDIA, every telemetry agent). EVA_LOLBIN_USERPATH is also neither, and will accumulate ALLOWs from browser and Teams updaters. Within a month or two both drop to 60% of nominal: NET_BEACON 6.0 → 3.6, EVA_LOLBIN_USERPATH 6.0 → 3.6. The design's own worked RAT example would then score 30.1 instead of 33.1 — still HIGH, but the marginal RAT no longer clears the bar. Fix: exempt any rule whose family is Credential, Injection, Evasion or Network from softening, or make softening scoped to (rule, signer) rather than global.
- "No ALLOW may be created while an unresolved HIGH incident exists for a DIFFERENT entity" is a self-inflicted denial of service. One stale, un-actioned HIGH — which is the expected steady state, since HIGH incidents auto-action and the user may never explicitly resolve the card — disables the allow path for the entire product. The user's escape hatch is to uninstall. Fix: scope the interlock to a short window (e.g. 15 minutes from the HIGH's last event), not to "unresolved".
- The clickjacking/synthetic-input defence is not a defence and should not be described as one. GetForegroundWindow, GetGUIThreadInfo and GetLastInputInfo are all session-local and cannot be meaningfully called from a session-0 LocalSystem service, so the checks must run in the WPF UI — the exact process an attacker running as the user would subvert — and be reported over a pipe the same attacker can write to. The per-session nonce is held in a process readable by any process running as that user. And GetLastInputInfo is updated by SendInput, so the "real user input within the last 5 seconds" test passes for synthetic input by design. Fix: delete the claim, or accept that there is no user-mode-only defence here and say so plainly in the docs alongside the DPAPI honesty note.
- There is no self-protection and no sensor-health model, so silent failure is the default. Any process running as the user can terminate the WPF tray app; anything elevated can stop the service. If the ETW session dies, is stolen by another consumer, or the audit policy is reverted by GPO, detection degrades to the polling fallback with no user-visible signal and no change in how confident the scores look — q_evidence would silently move from 1.0 to 0.7 and the product would keep asserting the same tiers. Fix: service recovery actions (restart on failure), a heartbeat between UI and service with a "Warden monitoring stopped" alert, a visible degraded-sensor state on the dashboard, and a rule that fires when Warden's own service or autorun entry is modified.
- %LOCALAPPDATA%\Warden's hardened DACL does not do what the item claims. If the directory is created by the interactive user, that user is its owner, and an owner retains WRITE_DAC implicitly — they (or any malware running as them) can simply rewrite the ACL and then read or tamper with the baseline, allowlist and verdict log. Fix: have the LocalSystem service create the tree under %ProgramData%\Warden with SYSTEM as owner, set the OWNER RIGHTS SID (S-1-3-4) to no access, and grant the interactive user read-only.

### Omissions
- Kernel-File ETW volume is the elephant in the room and is never costed. Writer attribution (the update-classification decision table, the developer-build heuristic, the persistence "who" field) all depend on Microsoft-Windows-Kernel-File Create/SetInformation events. That provider emits on essentially every file operation on the machine. During an Unreal cook or an npm install this is hundreds of thousands of events per second — orders of magnitude beyond the stated "under 1.5% of one core" budget, and enough to drop events and lose exactly the attribution you needed. The spec's performance budget carefully measures NtQuerySystemInformation (1.5 ms) and GetExtendedTcpTable (0.3 ms) while omitting the one sensor that dominates cost. Needs a measured number, aggressive keyword/filter scoping (FILE_KEYWORD_CREATE_NEW_FILE only, with a stack-walk-free session), or an explicit decision to drop writer attribution in favour of the process-tree-ancestor fallback.
- No script or document entity model. A RAT delivered as .js/.vbs/.hta/.ps1/.lnk inside a .iso or .zip — the mainstream 2024-26 delivery chain — has no PE to key on. Under this design the entity IS wscript.exe or powershell.exe: a stable, signed, System32, high-n, low-R entity. All the rarity, path-trust, signer-trust and hash-ring machinery collapses onto the interpreter, and only the cmd-template channel carries any payload identity. PRO_SCRIPT_FROM_DOC exists but scores the interpreter, not the script. Fix: make the script/argument file a first-class entity (its own pathKey, hash, MoTW, signer if any, path tier) and score the interpreter+script pair.
- No coverage of the defining RAT behaviours. For a product whose stated purpose is detecting Remote Access Trojans, there is no rule for screen capture, keylogging, webcam or microphone access, or an interactive reverse shell. Two of these are cheap and in-box: webcam/mic access is recorded per-app under HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\CapabilityAccessManager\ConsentStore\{webcam,microphone}\NonPackaged with LastUsedTimeStart/LastUsedTimeStop, which is a high-precision, zero-history, zero-cost signal that belongs in the cold-start set. Low-level keyboard hooks are enumerable indirectly, and a process with a socket handle and redirected stdio is a strong reverse-shell indicator obtainable from the handle enumeration you already do.
- No UAC-bypass detection. HKCU\Software\Classes\{ms-settings,mscfile,Folder,exefile}\shell\open\command hijacks (fodhelper, eventvwr, computerdefaults, sdclt) are the most common elevation primitive in commodity RATs, they require zero baseline, they are near-zero-FP on a normal machine, and they are cheaply watchable with RegNotifyChangeKeyValue on a handful of HKCU keys. This is the single highest-value missing rule for the cold-start set.
- No credential-hive dump detection. `reg save HKLM\SAM`, `reg save HKLM\SYSTEM`, esentutl /y copies of ntds.dit or the hives, and shadow-copy reads of \Windows\System32\config\SAM are all classic, high-precision, machine-independent. The catalogue covers LSASS and browser stores but not the hives.
- No kernel driver / BYOVD coverage. There is no rule for a new kernel-mode service being created, for a driver loading from a user-writable path, or for a known-vulnerable signed driver (the Microsoft vulnerable-driver blocklist is a shipped, offline, versioned data file — exactly the shape of trust-seeds.json and lolbins.json). Loading a signed vulnerable driver is how modern threats disable EDR, and Warden would not notice.
- Persistence type list has significant gaps: Active Setup (HKLM\SOFTWARE\Microsoft\Active Setup\Installed Components), Session Manager BootExecute/SetupExecute, UserInitMprLogonScript, Group Policy startup/logon scripts, BITS jobs, PowerShell profile.ps1 (highly relevant for this user), Office XLSTART/VBA and add-ins, accessibility-tool debuggers (sethc/utilman IFEO), StartupApproved, AppX/UWP StartupTasks, Time Providers, Credential and Network Providers, the WinSock autodial DLL, and KnownDLLs. Several of these are more common in real intrusions than half the types that are listed.
- No clock-tamper guard. Decay half-lives, allowlist expiry, the 6-hour dedup window, the 24-hour snooze, the token-bucket refills, the sigma-growth daily checkpoint and the bootstrap gate are ALL driven by wall-clock time. Setting the clock forward ages the entire baseline out and expires every allowlist entry; setting it back resets every rate limit and defeats the alert budget. Needs a monotonic tick source (QueryUnbiasedInterruptTime) for all rate limits and budgets, wall-clock only for decay, and a "system time jumped by more than N hours" event that freezes decay and raises a notice.
- No timezone/DST handling for the hour-of-day histogram, which is explicitly "local time". A DST transition or a timezone change shifts every entity's learned schedule by an hour, and hr is a scored channel via the categorical/behaviour path. Store UTC plus the offset at observation time, or accept and document the annual noise.
- No observe-only / shadow mode, which is the obvious way to validate every number in this document. The implementation notes list twenty-odd constants to "re-validate against real data" and the risks list says the alert budget is "guesses until measured", but the shipping default is auto-kill-and-quarantine enabled. Given that a single false quarantine of a debugger, a build artefact, an anti-cheat component or a BlueStacks driver destroys trust permanently, auto-action should be OFF by default until the replay harness demonstrates zero auto-actions across a captured fortnight of this user's real work, and the UI should show "Warden would have acted here" during that period.
- No offline recovery tool. The un-brickable requirement implies a path for the case where Warden itself makes the machine unusable — quarantined a file needed to boot, to log in, or to build. There must be a standalone restore executable that reads the quarantine manifests and puts every file back with its original ACL/ADS/identity, that runs with the service stopped, from Safe Mode, and from WinRE. It should be produced before the auto-action path is enabled.
- No uninstall story. Uninstall must revert the auditpol Process Creation setting and ProcessCreationIncludeCmdLine_Enabled, restore the Security log size, restore everything still in quarantine, remove the service and autorun entry, and offer to delete or keep verdicts.jsonl. The spec offers to revert the audit changes in one sentence and covers none of the rest.
- Warden's own updates are unhandled. Warden's binaries change on every release; the persistence entry pointing at Warden changes; Warden's signer is Warden's own (likely unsigned or self-signed for a free personal tool, i.e. T0 or T-1). The design would flag its own update as a signer break on a Run/service entry pointing into a user-writable path — the PER_RUNKEY_USERPATH + PRO_SIGNER_BREAK combination. Needs an explicit self-identity pin.
- The four regression fixtures omit the two cases that actually decide whether this product survives contact with the machine: (a) a per-user Electron/Squirrel install, which as shown scores 16.16 with two families and auto-quarantines; (b) a Windows cumulative update, which the spec's own risks section names as the anti-storm mechanism's most important test. Both should be fixtures with asserted point totals, and (a) should assert that no automated action occurs.
- No multi-user / fast-user-switching model. Entities are keyed globally by tokenised path, but sess.sid, integrity level, the interactive-user DACL grant, the digest trigger, the foreground validation and the %LOCALAPPDATA% tokens are all per-user. Nothing says what happens when a second account logs in, or how the LocalSystem service picks "the interactive user SID" when there are two.
- WMI persistence via PowerShell shell-out has no failure plan. Get-CimInstance against root/subscription can be blocked by execution policy, Constrained Language Mode, AppLocker/WDAC, or a broken WMI repository; each takes ~1-2 s of process startup; and the enumeration omits root\default and the specifics of ActiveScriptEventConsumer vs CommandLineEventConsumer scoring. A silent failure here means the highest-stealth persistence class is simply unmonitored with no indication.
