# Warden Maintenance Half — Itemised Capability Catalogue (grounded in live measurements of this machine)

> Area: `maintenance-module` · adversarial critique verdict: **sound_with_fixes**

## Summary
This spec catalogues 64 maintenance capabilities for Warden, and every size figure below was measured on the live machine rather than estimated. The headline result is that C: is not actually short of space for the reasons you would expect: the single largest consumer is BlueStacks at 149.6 GB (a 111.02 GB Pie64\\Data.vhdx that is fully allocated, not sparse), followed by a 6.56 GB Windows Update download cache holding 307,372 files, a 6.70 GB uv cache, and a 3.40 GB npm cache. Across all drives the biggest single reclaim is E:\\$RECYCLE.BIN at 107.4 GB / 226,184 files, which is pure free-on-demand space. Conservative safe reclaim on C: without touching anything ambiguous is ~24 GB (88.2 GB free to ~112 GB), and BlueStacks vhdx compaction plausibly adds tens more. Three findings materially change the design: D: is a 12 TB SATA spinning HDD (WDC WD121KRYZ), not an SSD, so scanning "D:\\My projects" is seek-bound and TRIM advice is wrong there while defrag advice is right; all SMART/NVMe health, VSS sizing, and even opening the boot-performance event log fail with access-denied when not elevated, so the health panel must be split into an unelevated tier and an elevated tier rather than silently showing blanks; and C:\\Users\\finla\\CrossDevice\\OnePlus 13\\storage\\ is a reparse point with no LinkType and no target that makes a naive recursive walk enumerate the user's phone. The catalogue is ordered by the seven requested areas, each item carrying its exact path/API/command line, measured or expected reclaim, runtime, risk level, admin requirement, dry-run shape, and an explicit statement of what breaks if the detection is wrong.

## Items (66)
### [critical] E:\$RECYCLE.BIN — 107.4 GB, the single biggest reclaim on the whole machine
MEASURED: E: recycle bin holds 107,440.2 MB across 226,184 files. F: holds 2,827.5 MB (15 files), D: holds 221.6 MB (350 files), C: holds ~0 MB (13 files). This is 107 GB of space the user has already declared they do not want. Reclaim: 110.5 GB total across all four drives. Time: 30-120 s on E: (NVMe) because of the file count; the shell API deletes per-drive. Risk: LOW-MEDIUM — it is by definition user-discarded data, but it is also the last undo. Admin: no (per-user bins).

**How:** Size without deleting via SHQueryRecycleBin (shell32.dll, SHQUERYRBINFO{cbSize,i64Size,i64NumItems}) per drive root — instant, no enumeration. Empty via SHEmptyRecycleBinW(IntPtr.Zero, "E:\\", SHERB_NOCONFIRMATION|SHERB_NOPROGRESSUI). To preview CONTENTS, enumerate E:\$RECYCLE.BIN\<SID>\ and parse the $I* index files (header: version int64, original file size int64, deletion time FILETIME, then path) pairing each $I to its $R data file. Present as a sortable list: original path, size, deleted date.

**False positives:** Never auto-empty. 226,184 files is a lot of history and users routinely restore from the bin days later. Default to prompting with a preview and an age filter ('empty only items deleted >30 days ago'), implementable by filtering on the $I deletion-time field and deleting matched $I/$R pairs directly rather than calling SHEmptyRecycleBin. Warn explicitly that restore is impossible afterwards.

### [critical] BlueStacks Pie64 Data.vhdx — 111.02 GB, fully allocated, not sparse
MEASURED: C:\ProgramData\BlueStacks_nxt total 149.58 GB. Engine\Pie64 = 114.94 GB (Data.vhdx alone 111.02 GB), Engine\Tiramisu64 = 34.63 GB (Data.vhdx 29.78 GB). Reclaim: typically 30-60% of a long-lived Android guest disk, so plausibly 30-60 GB. Time: 10-40 min. Risk: MEDIUM. Admin: yes.

**How:** Detect: enumerate C:\ProgramData\BlueStacks_nxt\Engine\*\Data.vhdx, compare file Length against guest free space. ### [critical] Windows Update download cache — 6.56 GB in 307,372 files
MEASURED: C:\Windows\SoftwareDistribution\Download = 6,561.7 MB across 307,372 files; the parent SoftwareDistribution is 6,605.2 MB. 307k files for 6.5 GB averages 21 KB/file, the signature of expanded ESD/CBS payloads left behind rather than a couple of clean .cab downloads — i.e. this cache is stale, not in-flight. Reclaim: 6.56 GB. Time: 2-6 min (file-count-bound, not byte-bound). Risk: LOW. Admin: YES.

**How:** Stop services first: 'net stop wuauserv' and 'net stop bits' (or Stop-Service wuauserv,bits -Force). Then delete the CONTENTS of C:\Windows\SoftwareDistribution\Download (not the folder). **False positives:** If an update is mid-download or a feature update is staged and pending reboot, deleting this forces a full re-download (potentially several GB of metered bandwidth) and can leave a partially-staged update in a confusing state. Gate on: no pending-reboot flags set (all four keys read False on this machine right now) AND wuauserv stopped cleanly. If Stop-Service times out, abort rather than deleting under a running service.

### [medium] Orphaned node_modules under D:\My projects — currently ZERO, do not fake this feature
MEASURED: a recursive scan of D:\My projects found 0 node_modules directories, and the whole tree is only 904 files enumerated in 0.01 s. The tree contains just .claude, nova-hoard, repo, warden. MEASURED on this machine: enumerating E:\ with System.IO.Directory.EnumerateFiles plus EnumerationOptions returned 200,000 files in 1.75 s = 113,753 files/s on NVMe. MEASURED AND CONFIRMED: C:\Users\finla\CrossDevice\OnePlus 13\storage\ contains dozens of directories (DCIM, Download, Android\media, Snapchat, WhatsApp status...) that are reparse points with NO LinkType and NO Target — a Phone Link virtual provider. ### [high] Duplicate finder — three-stage, never auto-deletes

### [critical] Reversible cleanup via the shared quarantine vault
The project's non-negotiable constraint is that deletion is never the first response and every action is reversible. This applies to Maintenance as much as Guardian. Time: adds the cost of a move. Risk: reduces all other risks. Admin: no.

**How:** For anything ambiguous, MOVE rather than delete: File.Move to %LOCALAPPDATA%\Warden\vault\<runId>\<hash>\ preserving a JSON manifest of original path, size, timestamps and ACL. Same-volume moves are metadata-only and instant; cross-volume moves are a full copy, so keep the vault per-volume (a vault root on each of C:, D:, E:, F:) to keep restores cheap. Age vault entries out after 30 days with a size cap, and show the vault's own footprint in the space report so it never becomes a hidden consumer. For genuinely regenerable caches (browser Cache_Data, npm, uv, pip), skip the vault — copying 6.7 GB of uv cache to a vault would defeat the purpose — and instead record only the manifest of what was removed and the command that restores it.

**False positives:** The failure mode to avoid is a vault that silently eats the space the tool just reclaimed. Distinguish two classes explicitly: REGENERABLE (record a manifest and the restore command, delete immediately, no copy) and USER-DATA (move to vault, keep 30 days). Getting a cache into the user-data class makes the tool appear to free nothing; getting user data into the regenerable class makes it unrecoverable. Default to user-data whenever the classification is uncertain.

### [high] The weekly report — what it must contain to be worth reading
A weekly 'here is what I did and what I found' report, generated after the scheduled idle run, delivered as a tray notification linking to a dashboard page and retained as history so trends are visible.

**How:** Sections, in this order: (1) ACTIONS TAKEN — each automatic cleanup with exact bytes reclaimed and the restore path/command, e.g. 'Windows Update cache: 6.56 GB (307,372 files) — re-downloads automatically'. (3) NEEDS YOUR DECISION — the ranked prompt-only queue with sizes, sorted by bytes: E:\$RECYCLE.BIN 107.4 GB, BlueStacks Pie64 compaction, DISM component cleanup, etc. Each with a one-line 'what breaks if you are wrong'. (4) HEALTH — disk health per physical disk (and clearly which readings needed admin and were skipped), pending reboot, Defender freshness, time sync, top 5 event clusters with noise suppressed. (5) UPDATES — the winget inventory split into 'applied', 'review needed' (toolchain), and 'excluded, and why'. (6) CHANGED SINCE LAST WEEK — new startup entries, new scheduled tasks, new services, new large directories over 1 GB. This section is where Maintenance feeds Guardian. (7) WHAT I DELIBERATELY DID NOT DO — Prefetch, pagefile, driver updates, RAM cleaning — with one-line reasons.

**False positives:** Section 7 is the credibility anchor and should not be cut: a maintenance tool that explains its restraint is trusted far more than one that maximises its reported numbers. Never report apparent WinSxS size, cache sizes that were not actually deleted, or a 'boot time saved' figure as reclaimed/achieved — every number in the ACTIONS TAKEN section must be a measured delta the tool actually caused. ## Risks
- The largest single reclaim (E:\$RECYCLE.BIN, 107.4 GB / 226,184 files) is also the most irreversible action in the entire catalogue. If Warden ever empties a recycle bin automatically — even under an 'obviously safe' heuristic — one bad call permanently destroys user data with no vault fallback, because the recycle bin IS the vault. This must be prompt-only forever, with an age filter and a full preview parsed from the $I index files.
- BlueStacks vhdx compaction touches a 111 GB file and a 29.78 GB file that back live Android VMs, one of which (Tiramisu64) the user has rooted with ReZygisk+LSPosed. A compaction interrupted by a power event, or run while HD-Player still holds the disk, can corrupt the guest filesystem and destroy a root setup that is expensive to rebuild. Default to Pie64 only, require the process tree to be fully stopped and verified, and never schedule this.
- Browser and Electron cache cleaning is the highest-frequency destructive operation in the tool and sits one directory away from Cookies, Login Data and Local State. A blocklist-based implementation, or a path-joining bug, logs the user out of everything and can lose saved passwords irrecoverably. The allowlist of cache leaf directory names must be the only mechanism, with unit tests asserting that no non-allowlisted path is ever passed to a delete.
- All SMART/NVMe health, VSS sizing, the boot-performance log, C:\Windows\Temp and DISM analysis are admin-gated — verified by measurement, not assumption. If Warden renders these as zeros or blanks when unelevated (as a naive implementation will, since several calls return empty rather than throwing), the health dashboard silently lies about disk wear and free space. A per-item AccessState of Measured/AccessDenied/NotPresent is required throughout.
- D: is a 12 TB spinning HDD while C:, E: and F: are NVMe. Related: the spec measured Volsnap Event ID 36 twice in 7 days, which means shadow storage is ALREADY hitting its configured maximum and copies are being aborted — that argues directly against the VSS item's default recommendation to cap max storage lower.
  - **Fix:** Report both 'bytes deleted' and 'volume free-space delta', and explain the difference when they diverge. Change the VSS default recommendation from 'cap max storage' to 'shadow storage is already at its limit; consider raising it or accept fewer restore points', and re-read vssadmin list shadowstorage before recommending anything.
- **Claim:** %TEMP% in-use test: 'test by attempting File.Open(path, FileMode.Open, FileAccess.ReadWrite, FileShare.None) and skipping on IOException'.
  - **Why wrong:** Two bugs. Read-only files and ACL-denied files throw UnauthorizedAccessException, which is not an IOException, so the handler misses them and the sweep throws instead of skipping. And it is a TOCTOU test — the handle is closed before the delete, so an app can reopen the file in between. It also updates last-access time on every file tested.
  - **Fix:** Catch UnauthorizedAccessException and IOException, and skip the open-test entirely: just attempt the delete and treat ERROR_SHARING_VIOLATION / ERROR_ACCESS_DENIED as 'skipped, in use'. One syscall instead of two, no race window, no last-access churn.
- **Claim:** Cargo: '\registry\src and \registry\index are fully regenerable from \registry\cache'.
  - **Why wrong:** src is extracted from the .crate files in cache, so that half is right. index is the registry index — with the sparse protocol (cargo default since 1.70) it is a local cache of HTTP-fetched index JSON. It is regenerable from the NETWORK, not from \registry\cache. Deleting index on a machine that is offline breaks resolution even though cache is intact.
  - **Fix:** State the two restore sources separately. Keep the existing 'never touch .cargo\bin' rule.
- **Claim:** 'Never disable ... RtkAudUService (audio will break)'.
  - **Why wrong:** RtkAudUService in HKLM\Run is the Realtek audio universal service front-end / effects helper. Audio is provided by the driver and the Windows Audio service; removing the Run entry costs the Realtek Audio Console features and any vendor DSP effects, not sound output. Stating 'audio will break' is the kind of overclaim that erodes the credibility the spec is trying to build elsewhere.
  - **Fix:** Reword to 'disabling this removes Realtek Audio Console and vendor audio effects; core audio keeps working'. Keep it on the do-not-touch-by-default list anyway.
- **Claim:** Scheduled tasks via 'the ITaskService COM API: TaskScheduler.TaskSchedulerClass'.
  - **Why wrong:** TaskScheduler.TaskSchedulerClass is the managed name from a COM interop assembly generated off the Task Scheduler 1.1 type library — i.e. an added dependency or a tlbimp build step, contrary to the zero-dependency rule. Also, Get-ScheduledTask cannot read tasks whose folder ACLs deny the user, and Disable-ScheduledTask on a machine-scoped task requires elevation, neither of which the item notes.
  - **Fix:** Use late-bound in-box activation: Type.GetTypeFromProgID("Schedule.Service") plus dynamic, or hand-declare the ITaskService/ITaskFolder/IRegisteredTask interfaces with [ComImport]. Mark the item as partly admin-gated.
- **Claim:** 'Enumerate with Get-CimInstance Win32_Service (Name, DisplayName, StartMode, State, DelayedAutoStart, PathName)' combined with the (correct) advice that 'Automatic but not running is usually correct behaviour on modern Windows, where most services are trigger-started'.
  - **Why wrong:** Win32_Service cannot see trigger-start. StartMode reports 'Auto' for both true auto-start and Automatic (Trigger Start), and there is no trigger property. So the tool cannot implement the very distinction the item says is required to avoid false positives — it would classify trigger-started services as anomalies.
  - **Fix:** Read SERVICE_CONFIG_TRIGGER_INFO via QueryServiceConfig2 (P/Invoke, in-box) and suppress any service with registered triggers. This is also the correct detector for the W32Time item above.
- **Claim:** Windows Update history: 'Also Get-HotFix / Win32_QuickFixEngineering for installed KBs'.
  - **Why wrong:** Win32_QuickFixEngineering enumerates only MSU/QFE-registered hotfixes. Cumulative updates and feature updates delivered through CBS do not appear, so this list is chronically incomplete and typically shows a handful of entries on a fully-patched Windows 11 machine. Presenting it as 'installed KBs' misleads.
  - **Fix:** Use the Microsoft.Update.Session QueryHistory results (which the item already specifies) as the authoritative list, and drop Get-HotFix or label it 'servicing-stack hotfixes only'.
- **Claim:** 'Conservative safe reclaim on C: without touching anything ambiguous is ~24 GB'.
  - **Why wrong:** The ledger backing that number includes Gradle caches (1.53 GB, which the same item rates LOW-MEDIUM and requires stopping the daemon), NuGet global-packages, and a full 'uv cache clean' — all of which the spec itself classifies as not-safe-by-default (it recommends uv cache prune and NuGet http-cache only). The genuinely no-decision subset is closer to 15-17 GB.
  - **Fix:** Publish two totals: 'automatic tier' (regenerable, no user decision, nothing running) and 'prompt tier'. Given the VSS point above, also label both as bytes-deleted rather than expected free-space gain.
- **Claim:** Microsoft Store: "Run 'wsreset.exe -i'".
  - **Why wrong:** -i is not a documented WSReset switch; wsreset takes no arguments for the cache-clear behaviour. Passing an unrecognised argument may just run the default path or open the Store.
  - **Fix:** Call wsreset.exe with no arguments, and note that it briefly opens a console window and then the Store — which makes it a poor fit for an unattended run regardless.
- **Claim:** Delivery Optimization: 'Get-DeliveryOptimizationStatus and Get-DeliveryOptimizationPerfSnap (in-box PowerShell, no admin needed to read)'.
  - **Why wrong:** The DO cmdlets query the DO service and are documented as requiring an elevated session; this was not among the spec's verified-unelevated list, so it is an assumption presented alongside verified facts. Also, the stated 'normal' cache location (ServiceProfiles\NetworkService\...\DeliveryOptimization\Cache) is the older layout; current builds commonly use C:\Windows\SoftwareDistribution\DeliveryOptimization.
  - **Fix:** Move both cmdlets to the elevated tier until tested, check both cache paths, and keep the row hidden when neither exists.

### False-positive risks
- Unreal 'Binaries\' deletion is unsafe on two of this user's own projects. SatisfactoryModding and ModWorkspace ship PREBUILT binaries from the modding SDK/starter project that are downloaded, not compiled locally — deleting them does not trigger a rebuild, it produces a project that will not open until the SDK is re-fetched. Restrict Binaries deletion to projects with a Source\ directory AND a matching .sln/.uproject with C++ modules, and default it off.
- Globbing '*.uproject' across all of D:\ will match sample and template projects INSIDE the engine installs (UE_5.8, 'Unreal Engine - CSS', Twinmotion, RealityScan). Deleting Intermediate/Binaries under an engine's own templates corrupts the installed engine's template set. Exclude any .uproject whose path is under a directory containing Engine\Binaries\Win64\UnrealEditor.exe.
- The 'is the tool running?' gate (uv.exe, cargo.exe, MSBuild.exe, dotnet.exe, VBCSCompiler.exe, Discord.exe, gradle daemon) is a point-in-time check with no lock. On a dev box a build starts seconds later and the cleaner is mid-delete inside .gradle\caches or the NuGet global-packages folder, producing exactly the 'bizarre build failures' the spec warns about. Take a real interlock: hold an exclusive handle on a sentinel file the cleaner creates, re-check immediately before each delete batch, and abort the batch on first sharing violation rather than continuing.
- 'Detect chrome.exe/msedge.exe/opera.exe and skip' means the Edge cache row will effectively never fire on Windows 11 — msedge.exe runs continuously for widgets, search, startup boost and WebView2 hosting. The item will silently do nothing forever while the UI keeps advertising 344 MB. Distinguish 'browser UI running' from 'a WebView2 host is running' (msedgewebview2.exe has its own profiles under %LOCALAPPDATA%\Microsoft\EdgeWebView), and if the browser genuinely never closes, offer per-profile cache clearing through the browser's own mechanism rather than a permanently-skipped row.
- The %TEMP% rule (>7 days old, exclude directories modified in the last 24 h) will delete Blender crash-recovery .blend files and Unreal/MSBuild intermediate state older than a week. The Blender item correctly says 'never delete a blender temp dir modified in the last 7 days' but the generic %TEMP% sweeper does not know about it, and the generic sweeper is the one on the automatic schedule. The named-exclusion list must be consulted by the generic sweeper, not just by the per-app item.
- node_modules orphan scoring uses 'newest mtime under .git older than 90 days'. A fresh clone or a branch switch rewrites working-tree mtimes to now while .git object mtimes stay old, and a repo whose active development happens in a linked git worktree elsewhere will look dead at the main checkout. Also 'restore with npm ci' silently assumes every pinned version is still published. Given the spec measured zero node_modules on this machine, the honest move is to ship the detector disabled with the scoring documented, not to tune heuristics against no data.
- 'bin'/'obj' pairing is right, but slot-game and Unreal-adjacent projects routinely keep vendored tooling under a 'bin' next to a csproj in a monorepo (e.g. a tools/bin beside a shared project file). Require BOTH a co-located obj/ AND that every file under bin/ is a known build-output extension or is reproducible by 'dotnet build', and skip anything git-tracked (a bin/ with tracked files is not build output).
- Event-log clustering will surface Netwtw10 5002/5005/5032 (Intel Wi-Fi roam/reset) and Security-SPP 8211/8228 as findings. Both are routine on healthy machines. Ship them in the suppression list from day one alongside AppModel-State 4, or the very first weekly report leads with three non-problems.
- Scheduled-task orphan detection will flag \Ubisoft\Ubisoft Connect Background Update, \Google Play Games Notifier and the IObit Uninstaller_SkipUac task. All three belong to software the user installed on purpose. The spec is right to cross-file the SkipUac task to Guardian, but Guardian's auto-kill autonomy must be explicitly excluded from anything Maintenance discovers this way — a maintenance inventory must never become an auto-remediation input.
- The duplicate finder's exclusion list (%WINDIR%, Program Files, WinSxS, C:\Windows\Installer, .git) misses the cases that dominate this machine: Steam depot/library files, Epic and Ubisoft game content, Unreal engine content shared across UE_5.8 and 'Unreal Engine - CSS', and the two BlueStacks Data.vhdx files. Add: any directory containing a steamapps/appmanifest, any Unreal Engine install root, any *.vhd/*.vhdx, and any path under a package manager cache (npm, uv, pip, NuGet, cargo, Gradle) — those are content-addressed by design and full of legitimate identical files.
- 'Automatic services that are not running' is correctly called a trap, but the item still offers MapsBroker as a curated allowlist entry. Changing MapsBroker's start type breaks offline Maps downloads and is worth ~0 bytes and ~0 ms. A curated allowlist of one marginal service is not worth the code path; make the whole item read-only.
- Free-space trend alerting on 'a single-day drop over 20 GB' will fire on every Unreal cook, every game install, every Blender render cache, and every BlueStacks session that grows a vhdx — i.e. on this user's normal Tuesday. The suppression rule ('when the drop is attributable to a known event Warden itself observed') requires Warden to be watching directory growth continuously, which is not specced anywhere. Either spec that watcher or drop the daily-drop alert and keep only the 10%-free threshold.

### Safety objections
- The automatic-schedule list contains admin-gated actions while the same item forbids scheduling anything requiring elevation. If that is resolved by running the scheduled task as SYSTEM or with highest privileges, you get a SYSTEM-context process performing recursive deletions under C:\Windows on a timer with no user present — the single most dangerous construct in the whole design, and one the spec explicitly names as a footgun. Resolve it by moving those actions to the prompt tier, not by elevating the task.
- There is no defined elevation mechanism anywhere in the spec, only a requirement to 'batch every admin-gated probe behind ONE elevation prompt'. A WPF process cannot elevate itself in place. This needs a designed answer — a separate signed helper .exe launched with the runas verb communicating over a named pipe with a hardened, allowlisted command surface — because an under-specified elevation broker in a security tool is a local privilege-escalation primitive. It also needs a rule that the broker never accepts a path from the UI without re-validating it against the same allowlists.
- Warden and Defender will fight each other, and the spec does not mention Defender once outside the freshness item. Three concrete collisions: (a) files moved into the quarantine vault by the Guardian half will be re-detected in place by real-time protection and deleted, silently destroying the rollback the project's non-negotiable constraints depend on; (b) if Controlled Folder Access is on, every move/delete under Documents, Desktop and Pictures fails with an opaque access-denied; (c) a tray-resident process that kills processes, writes Run keys and mass-deletes files will trip ASR rules and behaviour-based detection. Design the vault with a Defender path exclusion the user explicitly approves (and disclose that an exclusion is itself a security tradeoff), and handle CFA denial as a distinct, explained state.
- No snapshot is taken before reversible-but-fiddly system changes. The spec edits StartupApproved binary values, service start types and scheduled-task enablement, and relies on 'Warden's rollback store' to undo them. That store is a single point of failure. Export the affected registry keys to the vault and create a System Restore checkpoint (SRSetRestorePoint / the SystemRestore WMI class, elevated) before the first change of a run — cheap insurance that also gives the user an escape hatch Warden itself does not control.
- cleanmgr /sagerun is proposed as a driver for OS-blessed handlers. Beyond the StateFlags-persistence hazard the spec already notes, the 'Update Cleanup' handler queues a component-store cleanup that runs during the NEXT boot and can extend it by many minutes with a 'Working on updates' screen and no way to cancel. If cleanmgr is used at all, warn about that specific consequence; better, drive the handlers you have already sized directly and use the VolumeCaches registry only as the cross-check the spec describes.
- Direct $I/$R deletion for the age-filtered recycle-bin option must delete $R before $I and must handle $R directories recursively; getting the order wrong leaves data with no index, i.e. space consumed that no tool (including Explorer) will ever show or reclaim. Given this is 107 GB across 226,184 files, a partial failure mid-run also needs a resumable design — a single Directory.Delete-style call over that many entries will fail somewhere and leave an inconsistent bin.
- Cross-volume vault moves lose ACLs and alternate data streams (including Zone.Identifier / mark-of-the-web, which matters if the Guardian half is vaulting a downloaded executable). The spec says it records ACLs in a manifest but never says it restores them, and File.Move across volumes is a copy+delete that drops streams. Also, moving a file that is one of several NTFS hardlinks reclaims zero bytes while reporting the file's full size — relevant because the same document says the tool must never report bytes it did not actually free.
- The weekly report is retained as history and contains a full inventory of paths — including, if the reparse-point handling ever regresses, contents of C:\Users\finla\CrossDevice\OnePlus 13 (the phone). The spec treats the phone as a scanner hazard but never says the report store itself must be ACL'd to the user and must never persist paths from a reparse-point-classified subtree. Add both rules explicitly.

### Omissions
- C:\Qt at 160 GB is the second-largest single consumer on C: after BlueStacks, and it appears in this spec exactly once — as a line in the arithmetic that does not reconcile. Multiple Qt versions with Sources/ and debug symbols are a classic multi-tens-of-GB dev reclaim, removable through the Qt Maintenance Tool. It deserves an item of its own with the same 'go through the vendor's uninstaller, never delete the tree' discipline the spec applies to Windows Kits.
- Gaming shader and download caches are absent, on a machine with Steam, Epic, Ubisoft Connect, Roblox and Warframe installed: Steam\steamapps\shadercache, Steam\appcache\httpcache, Steam\depotcache, Epic's webcache, %LOCALAPPDATA%\NVIDIA\DXCache and GLCache, %LOCALAPPDATA%\AMD\DxCache, and %LOCALAPPDATA%\D3DSCache. These are typically several GB, fully regenerable, and safer than half the items that did make the list. The spec even name-checks the OS 'D3D Shader Cache' handler without covering the per-vendor equivalents.
- The Windows Search index (C:\ProgramData\Microsoft\Search\Data\Applications\Windows\Windows.edb) and the event log store (C:\Windows\System32\winevt\Logs) are both commonly multi-GB on a dev machine with 1.8M-file toolchains indexed, and both have supported reset paths. Neither is mentioned.
- BlueStacks Root.vhd.bsrbak files — verified present at 1.91 GB (Pie64) and 2.38 GB (Tiramisu64), 4.29 GB total — are not in the catalogue despite BlueStacks being the headline item. They are BlueStacks' own root-disk backups. Flag them read-only rather than as a reclaim: on the rooted Tiramisu64 the .bsrbak is plausibly the pre-root Root.vhd, so it is simultaneously the user's root-recovery artefact and, if restored by accident, the thing that un-roots the instance.
- Storage Sense is never checked. It ships enabled-by-default behaviour that overlaps directly with several Warden items (Temp, Downloads, Recycle Bin age-out) and its config lives at HKCU\Software\Microsoft\Windows\CurrentVersion\StorageSense\Parameters\StoragePolicy. Two tools deleting the same paths on different schedules makes 'bytes reclaimed' unattributable, and if Storage Sense's Downloads cleanup is on, Warden's 'we never touch Downloads' promise is misleading.
- The autorun inventory is incomplete for a tool whose Maintenance half feeds a security half. Missing sources: MSIX/UWP StartupTasks (HKCU\Software\Classes\Local Settings\Software\Microsoft\Windows\CurrentVersion\AppModel\SystemAppData\<PFN>\<TaskId>\State), Task Scheduler logon triggers (how Steam, Discord and most launchers actually autostart on modern Windows), Winlogon Userinit/Shell, Active Setup, AppInit_DLLs, and auto-start services. The spec is right that joining Run against StartupApproved is necessary; it is nowhere near sufficient.
- There is no mass-delete engine design, and every large item depends on one. Deleting 307,372 files (SoftwareDistribution), 224,647 (uv), 226,184 ($RECYCLE.BIN) needs: batched deletion with progress and cancellation, per-file failure tolerance with a categorised skip list, resume after interruption, and a decision about whether a partially-completed delete is reported as an action taken. Directory.Delete(path, true) satisfies none of these and will abort the whole tree on the first locked file.
- No dry-run/simulation mode is specified as a cross-cutting requirement. The spec mandates unit tests only for the browser cache allowlist. For a tool with this blast radius the right shape is: every action implements Plan() returning the exact set of paths and bytes, the UI shows the plan, and a test fixture asserts each planner's output against a synthetic directory tree containing the known traps (a junction loop, a reparse point with no target, a hardlinked file, a read-only file, a file held open, a >260-char path, a bin/ with tracked files). Ship that fixture before any deleter.
- The vault has no restore-path design for the case that matters: restoring a file whose original directory no longer exists, whose original name now collides, or whose volume has been reformatted or is offline (the spec puts vault roots on D:, E: and F:). Also no answer for what happens to vault entries when the 30-day age-out fires while the machine was off, and no cap-exceeded policy beyond 'show its footprint'.
- Long-path handling is undefined. LongPathsEnabled is already 1 on this machine, which mitigates it, but the app should still declare longPathAware in its manifest, and the shell APIs the spec relies on (SHEmptyRecycleBin, SHFileOperation) and diskpart do not honour it regardless of the policy. npm and uv caches are exactly where >260-char paths appear.
- Free-disk preconditions are not checked before actions that need headroom. DISM component cleanup, a feature-update staging, and a VHDX attach all need working space on a volume the spec describes as 90.5% full. Add a precondition per action and refuse rather than fail halfway.
- No mention of what Warden does when a maintenance action is interrupted by shutdown, sleep, or the user killing the tray app mid-delete — which is the normal case for an idle-triggered task with StopOnIdleEnd=true. IdleTrigger plus StopOnIdleEnd will terminate long operations the moment the user touches the keyboard; a compaction or a 300k-file delete must either be resumable or must never be scheduled that way.
