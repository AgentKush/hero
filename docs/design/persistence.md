# Warden Persistence Surface Inventory — Windows 11 26200, C#/.NET 10, zero-NuGet

> Area: `persistence-tradecraft` · adversarial critique verdict: **sound_with_fixes**

## Summary
This is a prioritised, literal inventory of 46 persistence mechanisms Warden must enumerate, each with the exact hive/key/value, filesystem path, COM interface or command line, plus the verified clean baseline for THIS machine (Win11 Pro 26200, captured live during this task) and the concrete false-positive traps present on it. The architecture I propose is a set of independent IPersistenceProvider collectors that each emit a normalised PersistenceEntry { SurfaceId, Location, DisplayName, RawValue, ResolvedImagePath, Arguments, Scope, Enabled, LastWriteUtc, Owner }, feeding one shared scoring pipeline (signature verification, path-class scoring, command-line lexing, age, publisher allow-list) so scoring rules are written once rather than per-surface. Two hard constraints discovered by inspecting the actual .NET 10.0.11 shared frameworks: System.Management (WMI) and System.ServiceProcess.ServiceController are NOT in-box — System.ServiceProcess.dll in Microsoft.NETCore.App/10.0.11 is a 1-typedef facade that forwards ServiceController to a NuGet-only assembly — so services must be read from the registry plus advapi32 P/Invoke, and WMI must go through raw IWbemLocator COM interop. System.Diagnostics.EventLog IS in-box in Microsoft.WindowsDesktop.App/10.0.11 (103 real typedefs), which gives Warden real-time persistence-change detection via EventLogWatcher for free. Roughly a third of these surfaces (TaskCache, C:\Windows\System32\Tasks, service ACLs) return ACCESS_DENIED unelevated — verified on this box — so Warden needs a clearly-scoped elevated helper or must degrade gracefully and say so in the UI rather than silently reporting "clean".

## Items (56)
### [critical] HKCU Run key
HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run — the single most-abused autorun on Windows. REG_SZ/REG_EXPAND_SZ values; value name is arbitrary, value data is a command line executed by Explorer at logon as the user. No elevation needed to write, so it is the default landing spot for commodity stealers (RedLine, Lumma, Vidar) and Node/Electron-based RATs.

**How:** Registry.CurrentUser.OpenSubKey(@"Software\Microsoft\Windows\CurrentVersion\Run", writable:false); foreach GetValueNames() -> GetValue(name, null, RegistryValueOptions.DoNotExpandEnvironmentNames) to capture the RAW string, then Environment.ExpandEnvironmentVariables() separately so you can flag entries that deliberately hide behind %APPDATA%. Split exe from args with CommandLineToArgvW (shell32.dll, P/Invoke, free with LocalFree). Get last-write time via RegQueryInfoKey P/Invoke (advapi32) — the managed RegistryKey has no LastWriteTime property. Enumerate every user by walking HKEY_USERS: RegistryKey.OpenBaseKey(RegistryHive.Users, RegistryView.Registry64) skipping _Classes-suffixed SIDs; for logged-off users load NTUSER.DAT with `reg load HKU\WardenTmp C:\Users\<u>\NTUSER.DAT` and `reg unload` after.

**False positives:** VERIFIED BASELINE ON THIS MACHINE: 4 values — `Steam` = "C:\Program Files (x86)\Steam\steam.exe" -silent; `AMDNoiseSuppression` = "C:\WINDOWS\system32\AMD\ANR\AMDNoiseSuppression.exe"; `Opera GX Stable` = "C:\Users\finla\AppData\Local\Programs\Opera GX\opera.exe" --autostart; `MicrosoftEdgeAutoLaunch_8A3A66FA36EB299D94CC10CED1DE771A`. Three traps: (1) AMD ships a THIRD-PARTY binary under C:\WINDOWS\system32\AMD\ — do not treat 'under system32' as inherently trusted OR the AMD subdir as inherently suspicious; (2) Opera GX, Discord, Slack, VS Code, GitHub Desktop and every Squirrel/Electron app legitimately live under %LOCALAPPDATA%\Programs — a user-profile path alone must NEVER be sufficient for auto-kill; (3) Edge/Chrome append a 32-hex-char hash to the value name, which looks like DGA junk. Also expect on dev boxes: `Docker Desktop`, `com.squirrel.*`, NVIDIA `NvBackend`, `RTSS`, `EpicGamesLauncher -silent`, `Ubisoft Connect`, `OneDrive` /background.

### [critical] HKLM Run key (both registry views)
HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Run and the 32-bit view HKEY_LOCAL_MACHINE\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Run. Machine-wide, runs for every user at logon. Requires admin to write, so an entry here means the attacker already had elevation — treat any unknown entry as higher severity than the HKCU equivalent.

**How:** You MUST open both views explicitly, because a 64-bit process silently reads only the 64-bit view: RegistryKey.OpenBaseKey(RegistryHive.LocalMachine, RegistryView.Registry64).OpenSubKey(@"SOFTWARE\Microsoft\Windows\CurrentVersion\Run") and RegistryKey.OpenBaseKey(RegistryHive.LocalMachine, RegistryView.Registry32).OpenSubKey(the same path). Do not hand-write the WOW6432Node path AND use Registry32 or you will double-read.

**False positives:** VERIFIED BASELINE: exactly 2 values — `SecurityHealth` = C:\WINDOWS\system32\SecurityHealthSystray.exe and `RtkAudUService` = "C:\WINDOWS\System32\DriverStore\FileRepository\realtekservice.inf_amd64_b55ed36a9a78cc75\RtkAudUService64.exe" -background. Wow6432Node\Run is EMPTY. The Realtek entry is the trap: a random-hex-suffixed DriverStore FileRepository path looks machine-generated and unfamiliar, but is the correct modern driver-package location. Allow-list the pattern C:\Windows\System32\DriverStore\FileRepository\*.inf_amd64_*\ when the file is WHQL/catalog-signed.

### [critical] RunOnce and RunOnceEx
HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce, HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\RunOnce, the WOW6432Node twin, and HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\RunOnceEx. RunOnce values are deleted by Explorer BEFORE execution unless the value name is prefixed with `!` (forces run-to-completion, survives failure); a `*` prefix makes it run even in Safe Mode. RunOnceEx is structurally different and more dangerous: numbered subkeys RunOnceEx\0001\, \0002\ whose values are `dllname|entrypoint` and are LOADED IN-PROCESS by runonce.exe/rundll32 — a DLL-execution primitive with no new process for an EDR to see.

**How:** Read all four locations with RegistryKey.OpenSubKey. Strip and RECORD any leading `!` or `*` on the value name — their presence is itself a signal, since virtually no legitimate installer uses them. For RunOnceEx recurse one level: for each subkey (typically 4-digit ordinals) enumerate its values and split each on '|' into module path + exported function name; resolve the module before scoring.

**False positives:** VERIFIED BASELINE: all RunOnce keys EMPTY on this machine, RunOnceEx absent. Normal — RunOnce is transient. Legitimate transient occupants mid-install: Windows Update servicing cleanup, `Uninstall<GUID>` from MSI rollback, Adobe ARM, NVIDIA installer cleanup, Git for Windows post-install. Because entries self-delete, snapshot-and-diff is the right model, not point-in-time scanning: a RunOnce value that PERSISTS across two reboots is anomalous by construction.

### [medium] RunServices / RunServicesOnce (legacy)
HKCU\Software\Microsoft\Windows\CurrentVersion\RunServices, RunServicesOnce, and the HKLM equivalents plus their WOW6432Node twins. Windows 9x-era keys that modern Windows 11 no longer honours for execution, but still created by old droppers and by tooling that follows outdated persistence lists.

**How:** Registry.CurrentUser.OpenSubKey(@"Software\Microsoft\Windows\CurrentVersion\RunServices") and RunServicesOnce; same under HKLM\SOFTWARE and HKLM\SOFTWARE\WOW6432Node. Treat mere EXISTENCE of the key as the signal, not just its values.

**False positives:** VERIFIED BASELINE: keys do not exist. Near-zero legitimate software creates these on Windows 11, making them a very high-precision, very low-recall indicator. Do not auto-kill on this alone — it does not actually execute on Win11; it is evidence of a dropper, not a live threat.

### [high] Policies\Explorer\Run
HKCU\Software\Microsoft\Windows\CurrentVersion\Policies\Explorer\Run and HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\Explorer\Run (+ Wow6432Node). Values are named with ordinals ('1','2','3') rather than descriptive names. A Group Policy surface, so it is invisible to msconfig and the Task Manager Startup tab — which is exactly why loaders use it.

**How:** OpenSubKey on all three paths; values are REG_SZ ordinals. Also read the sibling policy values in ...\Policies\System (DisableTaskMgr, DisableRegistryTools, EnableLUA) and ...\Policies\Explorer (NoRun, NoDrives) — these set alongside a Run entry is a strong tamper cluster.

**False positives:** VERIFIED BASELINE: none of the three keys exist. On a domain-joined machine these are legitimately populated by GPO, but this box is standalone, so any value here is genuinely anomalous. Check for a real GPO source before flagging: HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Group Policy\History and the machine's DomainRole.

### [critical] Per-user and common Startup folders
%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup and %ProgramData%\Microsoft\Windows\Start Menu\Programs\Startup. Everything in them (.lnk, .exe, .bat, .cmd, .vbs, .js, .wsf, .hta, .url, .scr) runs at logon. Crucially the folder LOCATIONS are themselves redirectable via the registry, so scanning the hard-coded path is not sufficient.

**How:** Do NOT hard-code the path. Resolve with Environment.GetFolderPath(Environment.SpecialFolder.Startup) and Environment.SpecialFolder.CommonStartup, and SEPARATELY read the redirection values HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders -> `Startup` (REG_EXPAND_SZ) and HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders -> `Common Startup`; flag any value that does not expand to the canonical path. Then Directory.EnumerateFiles(path, "*", SearchOption.AllDirectories) and resolve every .lnk. Watch live with FileSystemWatcher (NotifyFilters.FileName | LastWrite | CreationTime).

**False positives:** VERIFIED BASELINE: BOTH startup folders are EMPTY, and HKCU User Shell Folders `Startup` = C:\Users\finla\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup (canonical), `Common Startup` unset. Empty is the modern norm — vendors moved to Run keys and Scheduled Tasks. Legit occupants when they appear: OneDrive.lnk, Send to OneNote.lnk, Zoom.lnk, SteamVR, Logitech/Corsair/Razer utilities, and Blender/Unreal build helpers the user dropped there himself. NOTE: OneDrive is installed (OneDrive env var set), so on other profiles Documents/Desktop may be redirected under OneDrive — always resolve via SpecialFolder/SHGetKnownFolderPath, never string-build from %USERPROFILE%.

### [high] StartupApproved (Task Manager enable/disable state)
HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\StartupApproved\Run, \Run32, \StartupFolder and the HKLM twins. Each value is REG_BINARY, 12 bytes: byte[0] is the state (0x02/0x06 = ENABLED, 0x03/0x09 = DISABLED — low bit set means disabled), bytes[4..11] are a little-endian FILETIME of when the user toggled it. Two abuses: malware writes 0x02 to force-enable an entry the user disabled, and Warden must read this so it does not report disabled cruft as live.

**How:** key.GetValue(name) as byte[]; enabled = (blob[0] & 0x01) == 0; toggledUtc = DateTime.FromFileTimeUtc(BitConverter.ToInt64(blob, 4)) — guard against blob.Length < 12 and a zero timestamp ('never toggled'). JOIN on value name to the corresponding Run value / Startup .lnk filename. `Run32` maps to the WOW6432Node Run key; `StartupFolder` value names are the .lnk FILENAME including extension.

**False positives:** VERIFIED BASELINE and the single best FP lesson on this box: StartupApproved\Run holds TEN values while the actual Run key holds only FOUR. Six are orphaned graveyard entries for software uninstalled or moved: `electron.app.BlueStacks Services`, `Discord`, `YY`, `dola`, `ut`, `Opera GX Browser Assistant`. Short meaningless names like `YY`, `dola`, `ut` look exactly like malware naming but are dead approval records with no executable behind them. RULE: an entry in StartupApproved with NO matching Run value / Startup .lnk is inert history — never surface it as a detection; at most offer it under Maintenance as 'stale startup records you can clean up'.

### [critical] Scheduled Tasks — live enumeration via Task Scheduler 2.0 COM
The authoritative live view. Persistence via tasks is now more common than Run keys above commodity tier: triggers can be logon, boot, idle, or event-log-driven (an XPath subscription to any channel); the task can run as SYSTEM, hidden, with a spoofed Author/Description.

**How:** Zero-NuGet COM interop. Either late-bind — `dynamic svc = Activator.CreateInstance(Type.GetTypeFromProgID("Schedule.Service")); svc.Connect(); var root = svc.GetFolder("\\");` then recurse root.GetFolders(0) and root.GetTasks(1) (the 1 = TASK_ENUM_HIDDEN; WITHOUT it hidden tasks are invisible) — or declare [ComImport, Guid("2FABA4C7-4DA9-4013-9697-20CC3FD40F85")] ITaskService / [Guid("8CFAC062-A080-4C15-9A88-AA7C2AF80DFC")] ITaskFolder / [Guid("9C86F320-DEE3-4DD1-B972-A303F26B061E")] IRegisteredTask and CoCreateInstance CLSID {0F87369F-A4E5-4CFC-BD3E-73E6154572DD}. Per task read .Xml, .Enabled, .State, .LastRunTime, .NextRunTime, and walk Definition.Actions (IExecAction.Path/.Arguments/.WorkingDirectory, plus IComHandlerAction.ClassId — a ComHandler action is a strong signal), Definition.Principal.UserId/.RunLevel/.LogonType, Definition.Settings.Hidden, Definition.RegistrationInfo.Author/.Date. Late-binding via dynamic works on .NET 10 because built-in COM interop is on by default for net10.0-windows.

**False positives:** VERIFIED NON-MICROSOFT TASKS (22) — each a different flavour of trap. `\Git for Windows Updater` = "C:\Program Files\Git\git-bash.exe" --hide --no-needs-console --command=cmd\git.exe update-git-for-windows --quiet --gui — a HIDDEN-window shell launching a nested command, trips almost every naive heuristic, 100% legitimate. `\PoE_Trader_Hourly_Snapshot` = C:\Users\finla\Documents\Claude\Projects\SOMETH~1\poe_trader\run_scheduled.bat — an UNSIGNED .bat under the user profile with an 8.3 short path, written by the user himself; the archetypal developer FP, needs a 'user-authored script' review flow, never auto-quarantine. `\Opera GX scheduled Autoupdate 1762736724` has a Unix-epoch suffix (looks DGA) and passes the literal token $(Arg0). `\Uninstaller_SkipUac_finla` and `\Driver Booster SkipUAC (finla)` are IObit tasks whose purpose is UAC bypass — genuinely reduce security, legitimate products, tell the user rather than kill. `\SoftLanding\S-1-5-21-...-1001\SoftLandingTriggerTask-128000000001615609-render-{33cb6242-...}` is IN-BOX Windows with a fully generated-looking name. Also: BlueStacksHelper_nxt, StartCN/StartDVR (AMD), Google Play Games Notifier, GoogleUserPEH\*, Ubisoft Connect Background Update, IObit `\Pub\fls26.exe /rpop` and `onlinesr18_en.exe /rpop` (adware-grade promo popups — low reputation, not malware).

### [critical] Scheduled Tasks — on-disk XML
C:\Windows\System32\Tasks\<folder>\<TaskName> — extensionless UTF-16LE XML files, one per task, mirroring the folder hierarchy. Reading these directly catches tasks whose registry index was tampered with, and gives a file mtime harder to fake than the XML's RegistrationInfo/Date.

**How:** Directory.EnumerateFiles(@"C:\Windows\System32\Tasks", "*", SearchOption.AllDirectories); parse with System.Xml.Linq (XDocument.Load) against namespace "http://schemas.microsoft.com/windows/2004/02/mit/task". Pull //t:Actions/t:Exec/t:Command and /t:Arguments, //t:Principals/t:Principal/t:UserId and /t:RunLevel, //t:Settings/t:Hidden, //t:Triggers/*, //t:RegistrationInfo/t:Author and /t:Date. Compare RegistrationInfo/Date against File.GetCreationTimeUtc — a mismatch of more than a few seconds means the XML was authored elsewhere and dropped in. Also compare this file set against the COM enumeration and TaskCache\Tree: a task present in only two of the three is hidden.

**False positives:** VERIFIED: reading C:\Windows\System32\Tasks THROWS UnauthorizedAccessException when not elevated (confirmed on this machine). Warden must detect this and either route through its elevated helper or mark the surface 'not fully scanned' in the UI. Never let an ACCESS_DENIED silently render as a green tick. Note RegistrationInfo/Author is attacker-controlled free text — Microsoft's own tasks say things like 'Microsoft Corporation', so it is a hint, never proof.

### [critical] Scheduled Tasks — TaskCache registry (hidden-task detection)
HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache with subkeys Tree (mirrors the folder hierarchy; each leaf holds `Id` = the task GUID, `Index`, and `SD` = the binary security descriptor), Tasks\{GUID} (holds `Path`, `Actions` REG_BINARY, `Triggers` REG_BINARY, `DynamicInfo`), plus Plain, Logon, Boot, Maintenance. The classic hiding trick is DELETING the `SD` value under Tree\<task>, which makes the task invisible to schtasks.exe, the MMC snap-in AND the COM API while it still executes. A second trick is registering directly into TaskCache\Tasks with no Tree entry.

**How:** RegistryKey.OpenBaseKey(RegistryHive.LocalMachine, RegistryView.Registry64).OpenSubKey(@"SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree", writable:false). Do a THREE-WAY RECONCILIATION and alert on any asymmetry: (a) task paths from the COM enumeration, (b) files under C:\Windows\System32\Tasks, (c) Tree leaves and Tasks\{GUID}\Path values. Specifically flag: a Tree leaf with no `SD` value; a Tasks\{GUID} with no corresponding Tree entry; a Tree entry whose `Id` GUID has no Tasks\{GUID}. The `Actions` REG_BINARY blob is undocumented but stable — magic version WORD (0x0003), then a length-prefixed UTF-16 author string, then action records each beginning with an action-type WORD (0x6666 = Exec, 0x7777 = ComHandler, 0x8888 = Email, 0x9999 = ShowMessage) followed by length-prefixed UTF-16 command/args/workdir. Parsing it recovers the command line even when the XML file was deleted. Fallback `schtasks.exe /query /fo CSV /v` inherits the same blindness to SD-less tasks, so it is not a substitute.

**False positives:** VERIFIED: 'Requested registry access is not allowed' on TaskCache\Tree when not elevated on this machine — the key is ACL'd to SYSTEM. This surface is elevated-only, full stop. Legitimate asymmetry sources not to flag: tasks mid-creation (a race — re-read after 2s before alerting), and the per-SID \SoftLanding\S-1-5-21-... tree which Windows populates and prunes on its own.

### [critical] Windows Services — auto-start image analysis
HKLM\SYSTEM\CurrentControlSet\Services\<name> with values `ImagePath` (REG_EXPAND_SZ), `Start` (REG_DWORD: 0=Boot, 1=System, 2=Automatic, 3=Manual, 4=Disabled), `Type` (0x1/0x2 = kernel/fs driver, 0x10 = own-process, 0x20 = share-process), `ObjectName`, `DisplayName`, `Description`, `DelayedAutoStart`. A service running as LocalSystem at boot is the strongest persistence a RAT can get short of a driver.

**How:** DO NOT use System.ServiceProcess.ServiceController — VERIFIED: System.ServiceProcess.dll in Microsoft.NETCore.App\10.0.11 is a facade with exactly 1 typedef that type-forwards ServiceController to the NuGet-only System.ServiceProcess.ServiceController assembly, which is NOT present in any shared framework on this machine. Read the registry directly: RegistryKey.OpenBaseKey(RegistryHive.LocalMachine, RegistryView.Registry64).OpenSubKey(@"SYSTEM\CurrentControlSet\Services") and enumerate subkeys. For live state and the controls mask, P/Invoke advapi32: OpenSCManager(null, null, SC_MANAGER_ENUMERATE_SERVICE|SC_MANAGER_CONNECT) -> EnumServicesStatusEx(SC_ENUM_PROCESS_INFO, SERVICE_WIN32|SERVICE_DRIVER, SERVICE_STATE_ALL) -> OpenService + QueryServiceConfigW + QueryServiceConfig2W(SERVICE_CONFIG_DESCRIPTION / SERVICE_CONFIG_FAILURE_ACTIONS / SERVICE_CONFIG_TRIGGER_INFO) -> CloseServiceHandle. Kernel-driver ImagePath values use the \??\C:\... or \SystemRoot\ NT prefix — normalise before file lookup.

**False positives:** VERIFIED AUTO-START SERVICES OUTSIDE C:\WINDOWS, one of which destroys a naive rule: `WinDefend` = "C:\ProgramData\Microsoft\Windows Defender\Platform\4.18.26030.3011-0\MsMpEng.exe" and `MDCoreSvc` = the same versioned ProgramData directory. WINDOWS DEFENDER ITSELF RUNS FROM %PROGRAMDATA% WITH A VERSION-STAMPED PATH, so 'auto-start service under ProgramData' cannot be a high-confidence rule. Also legitimate here: `TeamViewer` (a genuine remote-access product — RAT-shaped by design, allow-list by signature not behaviour), `CloudflareWARP` (warp-svc.exe), `edgeupdate`, `GoogleUpdaterService152.0.7933.0` and `GoogleUpdaterInternalService152.0.7933.0` (version-numbered SERVICE NAMES that look like DGA), `GooglePlayGamesServices-26.8.308.0`, `ClickToRunSvc`, `WSLService`, and `CoworkVMService` = C:\Program Files\WindowsApps\Claude_1.40609.1.0_x64__pzs8sxrjxfjjc\app\resources\cowork-svc.exe (a WindowsApps path, unusual for a service). On a dev box add Docker Desktop Service, com.docker.service, NVIDIA Display Container LS, vgc (Riot Vanguard), EasyAntiCheat, BEService, and BlueStacks BstHdAndroidSvc/BstHdUpdaterSvc.

### [critical] Services — svchost-hosted ServiceDll
HKLM\SYSTEM\CurrentControlSet\Services\<name>\Parameters\ServiceDll (REG_EXPAND_SZ) plus ServiceMain, combined with an ImagePath of the form %SystemRoot%\System32\svchost.exe -k <groupname>. The group must appear as a value under HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Svchost. Hijacking here gives DLL execution inside a signed Microsoft host process — the stealthiest classic persistence on Windows.

**How:** For every service whose ImagePath contains "svchost.exe", open <service>\Parameters and read `ServiceDll`, `ServiceDllUnloadOnStop`, `ServiceMain`. Cross-check the -k group token against the value names under HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Svchost (VERIFIED: 73 groups on this machine) — a -k group absent from there, or a group with exactly one non-Microsoft member, is a strong signal. Verify the ServiceDll file is catalog- or Authenticode-signed by Microsoft and resident under C:\Windows\System32 or SysWOW64. Flag ANY ServiceDll outside %SystemRoot% as critical. Note that on Win11 with >3.5GB RAM most svchost services are split into their own process, so process grouping is not a reliable signal — go by the registry.

**False positives:** Legitimate third-party ServiceDll entries exist but are rare on a consumer box: some Intel/AMD management components and older printer stacks. The more common FP is misreading an unrelated value named ServiceDll in a Parameters key. Windows Defender's WdNisSvc and Sense also have non-obvious paths. Never quarantine a ServiceDll under System32 that passes catalog signature verification, even if the name is unfamiliar — there are hundreds.

### [high] Services — unquoted ImagePath and user-writable binary path
Two distinct weaknesses malware creates or exploits. (1) Unquoted service path: ImagePath = C:\Program Files\Some Vendor\svc.exe -arg with no quotes makes the SCM try C:\Program.exe, then C:\Program Files\Some.exe. (2) User-writable ImagePath: the service binary or a parent directory grants FILE_WRITE_DATA/FILE_ADD_FILE/WRITE_DAC to Users, Authenticated Users, or the interactive user — a non-admin can replace the binary SYSTEM executes at next boot.

**How:** (1) Unquoted: after stripping any leading \??\ , if ImagePath[0] != '"' AND the path portion before the first space contains a space AND the image is not under %SystemRoot%\System32, enumerate every hijack point (each prefix truncated at a space with '.exe' appended) and test File.Exists plus write access. (2) Writability: new FileInfo(imagePath).GetAccessControl() -> FileSecurity.GetAccessRules(true, true, typeof(SecurityIdentifier)) and look for FileSystemRights.WriteData / AppendData / ChangePermissions / TakeOwnership / FullControl granted to WellKnownSidType.BuiltinUsersSid, AuthenticatedUserSid, WorldSid, or WindowsIdentity.GetCurrent().User; repeat up the directory chain. Also check the SERVICE object DACL via QueryServiceObjectSecurity(hService, DACL_SECURITY_INFORMATION, ...) for SERVICE_CHANGE_CONFIG (0x0002) granted to non-admins — a direct privilege-escalation persistence primitive.

**False positives:** Unquoted paths are ENDEMIC in legitimate third-party installers — expect several here among the IObit, AMD and older game-launcher services. Only flag an unquoted path when a hijack file is actually creatable at one of the truncation points; otherwise report under Maintenance as hardening advice, not as a threat. Likewise developer tooling (Unreal, Docker, npm global installs, C:\ProgramData\chocolatey) legitimately has loose ACLs; the finding is 'weak ACL', not 'malware'.

### [high] Service recovery / failure command
A service's FailureActions can include SC_ACTION_RUN_COMMAND, executing an arbitrary command line when the service crashes. Malware sets a benign service's recovery command to its payload then deliberately crashes the service — persistence that fires on demand and lives nowhere a startup-item scanner looks. Stored at HKLM\SYSTEM\CurrentControlSet\Services\<name>\FailureActions (REG_BINARY) and FailureCommand (REG_SZ).

**How:** Read the `FailureCommand` REG_SZ value directly (the human-readable form), and for completeness QueryServiceConfig2W(hService, SERVICE_CONFIG_FAILURE_ACTIONS = 2, ...) into a SERVICE_FAILURE_ACTIONSW struct, checking each SC_ACTION.Type for SC_ACTION_RUN_COMMAND (3) and reading lpCommand. Equivalent shell-out: `sc.exe qfailure <name>`.

**False positives:** Almost nothing legitimate sets a run-command recovery action; normal values are SC_ACTION_RESTART (1) and SC_ACTION_NONE (0). A few enterprise agents (backup, monitoring) set a command to write an event or restart a helper. The base rate is so low this is high precision — but confirm the target binary is unsigned or in a user path before acting.

### [critical] WMI permanent event subscription (root\subscription)
The trio __EventFilter (a WQL query, typically __InstanceModificationEvent WITHIN 60 ISA 'Win32_PerfFormattedData_PerfOS_System' for a boot trigger, or Win32_ProcessStartTrace / RegistryKeyChangeEvent), __EventConsumer (CommandLineEventConsumer with CommandLineTemplate, or ActiveScriptEventConsumer with ScriptText/ScriptFileName), and __FilterToConsumerBinding joining them. Fileless: it lives in C:\Windows\System32\wbem\Repository\OBJECTS.DATA, runs as SYSTEM via WmiPrvSE.exe, survives reboot with no file on disk. Used by POWERLIKS-lineage loaders, miners, and modern .NET RATs.

**How:** System.Management is NOT in-box on .NET 10 (VERIFIED: no System.Management.dll anywhere under C:\Program Files\dotnet\shared), so ManagementObjectSearcher is off the table under the zero-NuGet rule. Use raw COM: CoCreateInstance(CLSID_WbemLocator = {4590F811-1D3A-11D0-891F-00AA004B2E24}, IID_IWbemLocator = {DC12A687-737F-11CF-884D-00AA004B2E24}) declared [ComImport]; ConnectServer("ROOT\\subscription", ...) -> IWbemServices.ExecQuery("WQL", "SELECT * FROM __EventFilter") -> IEnumWbemClassObject.Next -> IWbemClassObject.Get("Query"/"Name"/"CommandLineTemplate"/"ScriptText"). Alternatively late-bind Type.GetTypeFromProgID("WbemScripting.SWbemLocator") with dynamic. Acceptable fallback: pwsh -NoProfile -Command "Get-CimInstance -Namespace root/subscription -ClassName __EventFilter,__EventConsumer,__FilterToConsumerBinding | ConvertTo-Json -Depth 4". Do NOT use wmic.exe — deprecated and removed/disabled on 24H2+ builds.

**False positives:** VERIFIED CLEAN BASELINE ON WINDOWS 11 26200 — there is EXACTLY ONE subscription: __EventFilter Name='SCM Event Log Filter' with Query='select * from MSFT_SCMEventLogEvent', bound to NTEventLogEventConsumer Name='SCM Event Log Consumer'. That is the entire clean state. Anything beyond that trio warrants immediate surfacing. Known legitimate additions elsewhere: SCCM/ConfigMgr, Dell/HP/Lenovo management agents, some enterprise EDR — none present here, so on THIS box any second binding is critical severity. Extremely high precision; arguably Warden's best single detection.

### [high] WMI class-store persistence outside root\subscription
Beyond the standard trio, payloads can be stashed as static properties of custom classes in root\default, root\cimv2 or a bespoke namespace (a base64 blob on an innocuously named class), retrieved later by a small stager in a scheduled task. The repository file itself is the artefact.

**How:** Enumerate namespaces recursively via IWbemServices.ExecQuery on "SELECT * FROM __NAMESPACE" starting at ROOT. In each, query "SELECT * FROM meta_class WHERE __Class NOT LIKE 'Win32%' AND __Class NOT LIKE '__%' AND __Class NOT LIKE 'CIM_%' AND __Class NOT LIKE 'MSFT_%'" and inspect for classes with long string-valued static properties (>512 chars, high base64 character ratio). Also monitor mtime and size of C:\Windows\System32\wbem\Repository\OBJECTS.DATA and INDEX.BTR — unexpected growth outside patch windows is a cheap tripwire. Live signal: enable and subscribe to Microsoft-Windows-WMI-Activity/Operational, event ID 5861 (permanent subscription created).

**False positives:** Legitimate custom WMI classes exist for Office (root\cimv2\ms_409), Defender (root\Microsoft\Windows\Defender), Hyper-V (root\virtualization\v2), and potentially the AMD and Intel management stacks on this machine. Restrict alerting to classes with embedded long encoded strings, not merely to non-Microsoft namespaces.

### [critical] Winlogon Shell and Userinit
HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon values `Shell` (must be exactly 'explorer.exe') and `Userinit` (must be exactly 'C:\Windows\system32\userinit.exe,' — note the mandatory TRAILING COMMA). Both are comma-separated lists, so appending ',C:\Users\Public\x.exe' gets a payload launched by winlogon.exe at every interactive logon. The per-user twin HKCU\Software\Microsoft\Windows NT\CurrentVersion\Winlogon needs no elevation. Also check `AppSetup`, `VMApplet`, `GinaDLL` (must be absent on Vista+), `taskman`, and `AlternateShell` under HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot.

**How:** Read all values from both the HKLM and HKCU Winlogon keys. Split `Userinit` and `Shell` on ',' and evaluate EVERY element, not just the first — appending is the whole technique. Normalise case and trailing whitespace before comparing to the golden values.

**False positives:** VERIFIED BASELINE: HKLM Shell='explorer.exe', Userinit='C:\WINDOWS\system32\userinit.exe,', AppSetup empty, GinaDLL empty, taskman empty, and VMApplet='SystemPropertiesPerformance.exe /pagefile' (this VMApplet value is NORMAL on Win11 — do not flag it). HKCU Winlogon Shell and Userinit are both EMPTY, the correct clean state. The only legitimate non-default Shell values come from kiosk/shell-launcher and some VDI images — neither applies here. Treat any deviation as critical.

### [medium] Winlogon Notify packages
HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\Notify\<name> with a `DllName` value; historically loaded into winlogon.exe on logon/logoff/lock/unlock. Microsoft removed support in Vista+, but the key is still created by legacy droppers and by tooling following old checklists, so its presence is diagnostic.

**How:** OpenSubKey(@"SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\Notify"); for each subkey read `DllName`, `Startup`, `Logon`, `Logoff`, `Lock`, `Unlock`, `Impersonate`, `Asynchronous`.

**False positives:** VERIFIED: the Notify key exists but has ZERO subkeys on this machine — the clean Windows 11 state. Any subkey is anomalous. ### [critical] Image File Execution Options — Debugger
HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options\<exename.exe>\Debugger (REG_SZ) plus the WOW6432Node twin. Whatever is in `Debugger` launches INSTEAD of the named executable with the original command line appended. Two uses: hijack a frequently-run program (accessibility binaries, taskmgr.exe, a security product's exe) for persistence, and neutralise defences by pointing a security tool's exe at a no-op.

**How:** Enumerate subkeys of both views; for each read `Debugger`. ALSO read the parallel per-architecture subkey ...\Image File Execution Options\<name>\<arch> if present. Any non-empty Debugger value is worth surfacing; one pointing outside %SystemRoot% or at a script host is critical.

**False positives:** VERIFIED: 59 IFEO subkeys exist on this machine and NOT ONE has a Debugger value. The 59 subkeys are normal — Windows and installers use IFEO for MitigationOptions, DisableExceptionChainValidation and similar flags, so 'a subkey exists' means nothing. Legitimate Debugger values do occur: Visual Studio's JIT debugger (vsjitdebugger.exe), Store/WWAHost debugging, gflags.exe/AppVerifier during a developer session, and Unreal/Unity crash-handler setups. This user runs Visual Studio and Unreal, so expect transient legitimate Debugger entries — always verify the target's signature before acting.

### [high] IFEO GlobalFlag / VerifierDlls (Application Verifier hijack)
Under the same IFEO\<exename.exe> key: `GlobalFlag` = 0x100 (FLG_APPLICATION_VERIFIER) together with `VerifierDlls` = attacker.dll causes ntdll to load that DLL into the target process at startup. A DLL-injection persistence that never touches Debugger and is missed by most autorun scanners.

**How:** For every IFEO subkey in both registry views, read `GlobalFlag` (REG_DWORD) and test (value & 0x100) != 0, plus `VerifierDlls` (REG_SZ) and `VerifierFlags`. Resolve VerifierDlls against %SystemRoot%\System32 (the loader searches System32 first for verifier providers). Flag any VerifierDlls naming a DLL outside the in-box provider set: vrfcore.dll, vfbasics.dll, vfcompat.dll, vfluapriv.dll, vfprint.dll, vfnet.dll, vfntlmless.dll, vfnws.dll.

**False positives:** VERIFIED: no Debugger values, and GlobalFlag entries under IFEO are common and benign (Windows sets FLG_HEAP_* and mitigation flags for various binaries). Only the 0x100 bit combined with a VerifierDlls value is the signal. A developer running Application Verifier deliberately — plausible for this user, who does native game dev — will produce a legitimate hit; check whether appverif.exe ran recently and whether the named DLL is one of the in-box vf*.dll providers.

### [high] SilentProcessExit MonitorProcess
HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\SilentProcessExit\<exename.exe> with `ReportingMode` (REG_DWORD; 2 = LAUNCH_MONITORPROCESS, 3 = dump and launch), `MonitorProcess` (REG_SZ, the command line to run) and `GlobalFlag` = 0x200 (FLG_MONITOR_SILENT_PROCESS_EXIT) on the corresponding IFEO key. When the named process exits silently, WerFault launches MonitorProcess. Attackers pair this with a process they can reliably terminate — persistence triggered by ordinary user activity.

**How:** Enumerate subkeys of HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\SilentProcessExit; for each read ReportingMode, MonitorProcess, LocalDumpFolder, DumpType. Cross-reference: the IFEO key for the same exe name should have GlobalFlag with bit 0x200 set. Flag the pairing.

**False positives:** VERIFIED: the SilentProcessExit key has NO subkeys on this machine — clean. Legitimate use is essentially limited to developers configuring silent-exit dump collection and a few crash-telemetry agents. Very high precision on a consumer/developer box; near-zero base rate.

### [critical] AppInit_DLLs
HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Windows values `AppInit_DLLs` (REG_SZ, space- or comma-separated DLL list), `LoadAppInit_DLLs` (REG_DWORD, must be 1 for the mechanism to work), `RequireSignedAppInit_DLLs`. Every DLL listed loads into EVERY process that links user32.dll. Also check the WOW6432Node twin. Disabled when Secure Boot is on for 64-bit processes, still viable for 32-bit and on non-Secure-Boot systems.

**How:** Read all three values from both RegistryView.Registry64 and RegistryView.Registry32 at @"SOFTWARE\Microsoft\Windows NT\CurrentVersion\Windows". Also read the sibling `Load` and `Run` values in that SAME key — ancient but still-honoured autorun values, distinct from CurrentVersion\Run and frequently missed by scanners. Alert if AppInit_DLLs is non-empty at all; escalate to critical if LoadAppInit_DLLs == 1.

**False positives:** VERIFIED BASELINE: AppInit_DLLs = empty string, LoadAppInit_DLLs = 0, RequireSignedAppInit_DLLs unset. Clean. Historically abused by legitimate-but-awful software: older Nvidia/ATI overlays, some AV products, OEM bloatware, screen-reader/IME software. On a modern Win11 install a non-empty value is almost always bad. One FP class to respect: overlay/injection tooling a game developer might install (RivaTuner, MSI Afterburner, Discord overlay) generally uses other hooks, so do not assume.

### [critical] AppCertDLLs
HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\AppCertDlls — every value names a DLL loaded into any process that calls CreateProcess/CreateProcessAsUser/WinExec/ShellExecute. Undocumented, invisible in msconfig, a favourite of long-dwell implants.

**How:** RegistryKey.OpenBaseKey(RegistryHive.LocalMachine, RegistryView.Registry64).OpenSubKey(@"SYSTEM\CurrentControlSet\Control\Session Manager\AppCertDlls"). Treat the mere EXISTENCE of the key with any value as a detection. Note the DLL is loaded from the standard search order, so an unqualified filename is a phantom-DLL opportunity too.

**False positives:** VERIFIED: the AppCertDlls key DOES NOT EXIST on this machine — the clean Windows 11 state. Essentially no legitimate consumer software uses this. One of the very few surfaces where auto-quarantine on a single hit is defensible, though Warden's policy still says prompt unless the DLL is also unsigned and outside %SystemRoot%.

### [critical] COM CLSID hijacking via HKCU\Software\Classes
COM resolution checks HKEY_CURRENT_USER\Software\Classes\CLSID\{guid} BEFORE HKEY_LOCAL_MACHINE\SOFTWARE\Classes\CLSID\{guid}. So a non-admin can create HKCU\Software\Classes\CLSID\{well-known-guid}\InprocServer32 with (Default) = evil.dll and ThreadingModel = Both, and every process instantiating that CLSID loads the attacker's DLL. Targets of choice are CLSIDs instantiated by explorer.exe at startup, by the Task Scheduler's ComHandler action, or by scheduled COM-activated components.

**How:** Enumerate Registry.CurrentUser.OpenSubKey(@"Software\Classes\CLSID") subkeys; for each probe child keys `InprocServer32`, `InprocHandler32`, `LocalServer32`, `TreatAs`, `ProgID` and read their (Default) values with GetValue(string.Empty). For every CLSID found under HKCU, ALSO look it up in Registry.LocalMachine.OpenSubKey(@"SOFTWARE\Classes\CLSID\{guid}") — if BOTH exist and point at different modules, that is a live hijack and is critical. Additionally cross-reference CLSIDs referenced by scheduled tasks' ComHandler actions and by HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\ShellServiceObjects.

**False positives:** VERIFIED BASELINE: HKCU\Software\Classes\CLSID has 12 subkeys, of which 2 carry InprocServer32 — {89D46FFF-9F69-43E2-9CBA-3E6278A6EF06} -> C:\WINDOWS\system32\shell32.dll (benign) and {D45F043D-F17F-4e8a-8435-70971D9FA46D} -> C:\Program Files\Blender Foundation\Blender 5.1\BlendThumb.dll. THAT SECOND ONE IS THE TRAP: Blender legitimately registers a per-user thumbnail provider under HKCU. Unreal, Substance, Autodesk, 7-Zip, TortoiseGit, Dropbox and OneDrive all register per-user COM this way on a content-creator's machine. The discriminator is not 'HKCU CLSID exists' but 'HKCU CLSID SHADOWS an existing HKLM CLSID with a different module' — Blender's GUID has no HKLM twin, so it is not a shadow and must not be flagged.

### [high] COM TreatAs redirection
A `TreatAs` subkey under a CLSID redirects all activation of that CLSID to a different CLSID — an indirection that survives module-path allow-listing because the malicious module is registered under a second, innocuous GUID. Works in both HKCU\Software\Classes\CLSID\{a}\TreatAs and HKLM\SOFTWARE\Classes\CLSID\{a}\TreatAs.

**How:** For every CLSID subkey in both HKCU\Software\Classes\CLSID and HKLM\SOFTWARE\Classes\CLSID, test for a `TreatAs` child and read its (Default) — a CLSID string. Follow the redirection to the target CLSID, resolve ITS InprocServer32/LocalServer32, and score THAT module. Flag chains longer than one hop, and flag any TreatAs whose source CLSID is a well-known Windows component.

**False positives:** VERIFIED: exactly one TreatAs exists in HKCU on this machine — {0003000A-0000-0000-C000-000000000046} -> {D3E34B21-9D75-101A-8C3D-00AA001A1652}. That is the in-box OLE 'Package' object mapped to the Packager Shell Object, a normal Windows/Office mapping, and must be allow-listed by exact GUID pair. Ship a small allow-list of known-good TreatAs pairs; everything else is worth a prompt.

### [high] Shell extension handlers and ShellServiceObjectDelayLoad
DLLs loaded into explorer.exe. Key locations: HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\ShellServiceObjectDelayLoad (values map a name to a CLSID, loaded at Explorer start); HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\ShellIconOverlayIdentifiers\<name> (Default) = CLSID; HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\ShellExecuteHooks; HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Browser Helper Objects; HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Shell Extensions\Approved (the gate list).

**False positives:** VERIFIED BASELINE: ShellServiceObjectDelayLoad has exactly ONE value, `WebCheck` = {E6FB5E20-DE35-11CF-9C87-00AA005127ED} (in-box). ### [medium] Context-menu handlers and ShellEx
HKCU\Software\Classes\*\shellex\ContextMenuHandlers\<name>, HKCU\Software\Classes\AllFileSystemObjects\shellex\ContextMenuHandlers\<name>, HKCU\Software\Classes\Directory\shellex\ContextMenuHandlers\<name>, HKCU\Software\Classes\Directory\Background\shellex\ContextMenuHandlers\<name>, HKCU\Software\Classes\Folder\shellex\..., HKCU\Software\Classes\Drive\shellex\..., plus every HKLM\SOFTWARE\Classes equivalent and per-extension HKCR\.<ext>\shellex. ### [critical] Shell open-command / ProgID hijacking
Rewriting the command for a file class so that opening any file of that type runs the payload first. Highest-value targets: HKCU\Software\Classes\exefile\shell\open\command, txtfile\shell\open\command, mscfile\shell\open\command (the eventvwr.exe UAC bypass), ms-settings\shell\open\command with a `DelegateExecute` value (the fodhelper.exe/computerdefaults.exe UAC bypass), Folder\shell\open\command, and .lnk/.url ProgIDs.

**How:** Probe this explicit list of HKCU\Software\Classes paths for a `shell\open\command` child and read (Default) plus any `DelegateExecute` value: exefile, txtfile, batfile, cmdfile, comfile, piffile, regfile, scrfile, mscfile, ms-settings, Folder, Directory, Drive, htmlfile, xmlfile. **False positives:** VERIFIED: HKCU\Software\Classes\CLSID has only 12 keys and no such hijacks are present; clean. ### [critical] LSA Authentication / Notification / Security packages
HKLM\SYSTEM\CurrentControlSet\Control\Lsa values `Authentication Packages` (REG_MULTI_SZ), `Notification Packages` (REG_MULTI_SZ, DLLs called on every password change — classic credential harvesting), `Security Packages`, the parallel HKLM\SYSTEM\CurrentControlSet\Control\Lsa\OSConfig\`Security Packages`, and HKLM\SYSTEM\CurrentControlSet\Control\SecurityProviders\`SecurityProviders` (REG_SZ, comma-separated SSP DLLs). ### [high] BITS jobs
BITS jobs persist across reboots for up to 90 days and can carry a SetNotifyCmdLine that executes an arbitrary command when the transfer completes or errors. ### [high] .lnk shortcut hijacking
A .lnk file's target and Arguments can be rewritten while its icon, name and description stay identical, so a Start Menu / taskbar / desktop shortcut silently launches a loader that chain-launches the real app. Locations: the two Startup folders, %APPDATA%\Microsoft\Windows\Start Menu\Programs\**, %ProgramData%\Microsoft\Windows\Start Menu\Programs\**, %APPDATA%\Microsoft\Internet Explorer\Quick Launch\User Pinned\TaskBar\**, and the Desktop. **How:** No in-box managed .lnk parser. Option (a) is far less code. **False positives:** VERIFIED: both Startup folders are empty on this machine. ### [high] DLL search-order and phantom DLL hijacking
A signed, trusted application loads a DLL by unqualified name; the attacker plants a malicious DLL earlier in the search order (the application directory is searched first) or plants a DLL the app looks for but that does not ship (a 'phantom'). Persistence is inherited from the host app's own autostart. Classic Windows 11 phantom targets: WptsExtensions.dll (Task Scheduler), wlbsctrl.dll (IKEEXT), TSMSISrv.dll / TSVIPSrv.dll (SessionEnv), fxsst.dll, wbemcomn.dll (in the wbem directory), plus side-loading pairs where a signed EXE sits next to an attacker's msvcp140.dll / vcruntime140.dll / version.dll / dbghelp.dll.

**How:** Positive check: File.Exists on the known phantom paths — C:\Windows\System32\WptsExtensions.dll, C:\Windows\System32\wlbsctrl.dll, C:\Windows\System32\TSMSISrv.dll, C:\Windows\System32\TSVIPSrv.dll, C:\Windows\System32\wbem\wbemcomn.dll, C:\Windows\System32\fxsst.dll — none should exist on a clean Win11; presence is a detection. Hardening check: read HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\`SafeDllSearchMode` (VERIFIED ABSENT on this machine, which means the secure default of 1 applies — report as 'default, secure', not 'missing/insecure') and enumerate ...\Session Manager\KnownDLLs (VERIFIED: 37 entries) since KnownDLLs are immune. Behavioural check: for each running process walk loaded modules and flag any module in the process's own directory that is unsigned AND shares a name with a System32 DLL — CreateToolhelp32Snapshot(TH32CS_SNAPMODULE|TH32CS_SNAPMODULE32, pid) + Module32FirstW/Module32NextW, or Process.Modules (System.Diagnostics, in-box).

**False positives:** Enormous FP surface on a developer machine; tune conservatively. Legitimate app-local copies of msvcp140.dll, vcruntime140.dll, concrt140.dll, ucrtbase.dll, dbghelp.dll, D3DCompiler_47.dll and openvr_api.dll are shipped by Steam games, Unreal projects, Blender, BlueStacks and Python venvs by the thousand. Restrict alerting to (a) the fixed phantom list, which has a zero base rate, and (b) an UNSIGNED module shadowing a System32 name inside a SIGNED process whose publisher differs from the module's. ### [high] Explorer Load/Run values and Shell Folder redirection
Two often-missed values in HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Windows: `Load` and `Run` (REG_SZ) — 16-bit-era holdovers that Windows 11 STILL honours at logon, distinct from CurrentVersion\Run. Plus HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Shell Folders and User Shell Folders, where redirecting `Startup`, `Common Startup` or `Desktop` moves the folder Explorer actually reads at logon to an attacker-controlled directory.

**How:** Read `Load` and `Run` from HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Windows, its WOW6432Node twin, and the HKCU twin at HKCU\Software\Microsoft\Windows NT\CurrentVersion\Windows. Both should be empty or absent. Then read every value under HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders and the HKLM equivalent, expand them, and compare each against Environment.GetFolderPath for the corresponding SpecialFolder — flag any divergence that is not a OneDrive Known Folder Move target.

**False positives:** VERIFIED: HKCU User Shell Folders `Startup` points at the canonical path and `Common Startup` is unset. OneDrive Known Folder Move legitimately redirects Desktop, Documents and Pictures under C:\Users\<u>\OneDrive\ — this user HAS OneDrive (the env var is set), so build that exception in before flagging redirection. The Load/Run values under Windows NT\CurrentVersion\Windows have essentially zero legitimate modern users; treat non-empty as a detection.

### [critical] Real-time change detection via the in-box event log reader
Rather than polling 46 surfaces on a timer, subscribe to the events that fire when persistence is CREATED. This is the low-overhead half of Warden's monitoring loop and it is available with zero NuGet packages.

**How:** System.Diagnostics.Eventing.Reader ships inside System.Diagnostics.EventLog.dll, which IS present in Microsoft.WindowsDesktop.App\10.0.11 (VERIFIED: 103 real typedefs, not a facade). Use EventLogWatcher with an EventLogQuery + XPath on: Security 4698 (scheduled task created), 4699 (deleted), 4702 (updated), 4657 (registry value modified — requires SACL auditing on the specific keys, which Warden can set via RegistrySecurity.AddAuditRule with SeSecurityPrivilege), 4697 (service installed); System 7045 (new service installed by SCM) and 7040 (start type changed); Microsoft-Windows-TaskScheduler/Operational 106 (task registered) and 200/201; Microsoft-Windows-WMI-Activity/Operational 5857/5860/5861 (5861 = permanent subscription created); Microsoft-Windows-Bits-Client/Operational 3 and 59. Enable disabled-by-default operational channels with `wevtutil.exe sl <channel> /e:true`. For registry change without auditing, use RegNotifyChangeKeyValue (advapi32) with REG_NOTIFY_CHANGE_LAST_SET | REG_NOTIFY_CHANGE_NAME and fWatchSubtree, waiting on the event handle from a background thread — far cheaper than polling.

**False positives:** 7045 fires legitimately on every driver and service install, which for this user means every GPU driver update, every Docker/WSL update, and every anti-cheat install. 4698 fires on every software update that registers a task. The value is not the event but the CORRELATION: a 7045 whose ImagePath is unsigned and under %TEMP%, or a 4698 within seconds of a 4688 for a script host. Treat events as triage triggers that schedule a full surface re-scan, not as detections in their own right.

## Risks
- ELEVATION SPLIT IS THE BIGGEST ARCHITECTURAL RISK. Verified on this exact machine, non-elevated: HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree throws 'Requested registry access is not allowed', and C:\Windows\System32\Tasks throws UnauthorizedAccessException. Service object DACLs, C:\Program Files\WindowsApps enumeration, and SACL-based registry auditing are equally gated. If Warden runs unelevated and swallows these exceptions, the dashboard shows a green 'all clear' for the surfaces attackers most prefer. Mitigation: a per-surface ScanStatus enum { Complete, PartialAccessDenied, Failed } surfaced in the UI, plus a narrowly-scoped elevated helper (a service or a UAC-prompted broker) that ONLY performs enumeration and quarantine, never arbitrary commands.
- TWO ASSUMED-IN-BOX APIS ARE NOT IN-BOX, verified by inspecting C:\Program Files\dotnet\shared: (1) System.Management.dll does not exist in ANY shared framework, so ManagementObjectSearcher/ManagementScope require the System.Management NuGet package — WMI must go through IWbemLocator COM interop or a pwsh shell-out. (2) System.ServiceProcess.dll in Microsoft.NETCore.App\10.0.11 has exactly 1 typedef and type-forwards ServiceController to System.ServiceProcess.ServiceController, which is not present — so ServiceController is unavailable and services must be read from the registry plus advapi32 P/Invoke. Discovering these late forces either a NuGet dependency (breaking a stated constraint) or a large rewrite.
- SIGNATURE VERIFICATION IS THE LOAD-BEARING FALSE-POSITIVE CONTROL AND IS EASY TO GET WRONG. X509Certificate.CreateFromSignedFile / X509Certificate2 only reads EMBEDDED Authenticode signatures and returns nothing for the large majority of Windows system binaries, which are CATALOG-signed. If Warden uses it, most of System32 scores as 'unsigned' and the precision-over-recall promise collapses immediately. The correct implementation is WinVerifyTrust (wintrust.dll) with pgActionID = WINTRUST_ACTION_GENERIC_VERIFY_V2 {00AAC56B-CD44-11d0-8CC2-00C04FC295EE} and a WINTRUST_DATA whose dwUnionChoice is WTD_CHOICE_FILE, falling back to the catalog path via CryptCATAdminAcquireContext2 -> CryptCATAdminCalcHashFromFileHandle -> CryptCATAdminEnumCatalogFromHash -> WINTRUST_CATALOG_INFO. Set dwUIChoice = WTD_UI_NONE and fdwRevocationChecks = WTD_REVOKE_NONE so verification never hits the network (the project forbids default egress) and never blocks the UI thread.
- AUTO-KILL ON A PATH HEURISTIC WILL BREAK THIS MACHINE. Three verified counterexamples on this box alone: Windows Defender's own WinDefend and MDCoreSvc run from C:\ProgramData\Microsoft\Windows Defender\Platform\<version>\; AMD ships a third-party binary at C:\WINDOWS\system32\AMD\ANR\AMDNoiseSuppression.exe; and the user's own PoE_Trader_Hourly_Snapshot task runs an unsigned .bat from his Documents folder. Any rule of the form 'ProgramData or user-profile path + auto-start => quarantine' quarantines the antivirus or the user's own work. High-confidence auto-action must require a CONJUNCTION of independent signals (unsigned AND user-writable path AND obfuscated command line AND created within the observation window AND not on the publisher allow-list), and the un-killable list must include the Defender processes, the SCM, csrss, wininit, winlogon, lsass, smss, services, and anything running as a Protected Process Light.
- QUARANTINE OF NON-FILE PERSISTENCE NEEDS A DIFFERENT ROLLBACK MODEL. Most of these 46 surfaces are registry values, WMI repository objects, scheduled-task definitions or JSON fragments, not files — 'move + rename + strip execute' does not apply. Warden needs a typed vault: for registry, store hive/key/valuename/kind/raw-bytes plus the key's original DACL; for WMI, store the full MOF text (recoverable via IWbemClassObject::GetObjectText) so the subscription can be recreated; for tasks, store the complete XML; for JSON surfaces, store the byte-exact original file. Deleting a registry value without recording its RegistryValueKind (REG_EXPAND_SZ vs REG_SZ vs REG_MULTI_SZ) makes a faithful restore impossible.
- THIS USER'S SOFTWARE PROFILE IS ADVERSARIAL TO NAIVE HEURISTICS. Verified installed and legitimate: TeamViewer (a genuine RAT by function), CloudflareWARP (traffic-tunnelling VPN), BlueStacks with root (Android emulator that installs drivers and services), IObit Driver Booster and Uninstaller (which install explicit UAC-bypass scheduled tasks literally named 'SkipUAC'), Git for Windows' updater task that launches a hidden-window bash, and a Claude MSIX package that runs a SYSTEM service from C:\Program Files\WindowsApps. Every one of these is flagged by textbook rules. The allow-list must be built from this machine's actual baseline during first-run onboarding, not from a generic list, and the first run should be an explicit 'this is your baseline, confirm it' step rather than an immediate wall of alerts.
- PERFORMANCE AND TOCTOU. Enumerating HKLM\SYSTEM\CurrentControlSet\Services (hundreds of keys), HKLM\SOFTWARE\Classes\CLSID (tens of thousands), every shellex parent and every scheduled task XML, then WinVerifyTrust-ing every resolved binary, is far too expensive for a continuous loop. Use RegNotifyChangeKeyValue subtree watches plus EventLogWatcher for the continuous path and reserve full enumeration for a scheduled deep scan; cache signature verdicts keyed by (path, size, mtime, SHA-256) with the hash computed lazily. Separately, every path resolved during a scan can be swapped before it is verified — always open the file with a handle first and verify THAT handle, never re-open by path between check and use.
- SACL-BASED REGISTRY AUDITING (event 4657) REQUIRES ENABLING SYSTEM AUDIT POLICY, a machine-wide security-configuration change. The project's safety constraints put 'modifying system or security settings' out of bounds without explicit user consent. Warden should therefore prefer RegNotifyChangeKeyValue (no policy change, no auditing required) and treat auditpol/SACL configuration as an opt-in the user actively enables, with a clear explanation and a one-click revert.

## Implementation notes
ORDER OF WORK. Build the shared scoring pipeline and the PersistenceEntry model first, then the collectors in this order — the value is heavily front-loaded: (1) HKCU/HKLM Run + RunOnce + Startup folders + StartupApproved, (2) Scheduled Tasks via COM, (3) Services via registry, (4) WMI root\subscription, (5) Winlogon/IFEO/AppInit/AppCertDlls/LSA (these five are tiny, near-zero-FP, and implementable in an afternoon because their clean baselines are single known values), (6) everything else.

VERIFIED FRAMEWORK FACTS (checked against C:\Program Files\dotnet\shared on this machine; 10.0.11 installed alongside 6.0.36/8.0.30/9.0.19):
- Microsoft.Win32.Registry.dll IS in Microsoft.NETCore.App/10.0.11 — the Registry API is free.
- Microsoft.Win32.Registry.AccessControl.dll IS in Microsoft.WindowsDesktop.App/10.0.11 — RegistrySecurity/GetAccessControl available.
- System.Diagnostics.EventLog.dll IS in Microsoft.WindowsDesktop.App/10.0.11 with 103 real typedefs — EventLogWatcher/EventLogQuery/EventRecord are free.
- System.Diagnostics.PerformanceCounter.dll IS in Microsoft.WindowsDesktop.App/10.0.11.
- System.Management.dll is ABSENT everywhere -> WMI needs IWbemLocator COM interop or a pwsh shell-out.
- System.ServiceProcess.dll is a 1-typedef facade forwarding to a MISSING assembly -> ServiceController is unusable; use registry + advapi32.

REGISTRY MECHANICS.
- Always open with RegistryKey.OpenBaseKey(hive, view) and scan BOTH RegistryView.Registry64 and RegistryView.Registry32 for every HKLM\SOFTWARE path. Never combine an explicit WOW6432Node path WITH Registry32 — that double-redirects.
- Read raw with RegistryValueOptions.DoNotExpandEnvironmentNames, keep the raw string for display and for detecting deliberate %VAR% obfuscation, and expand separately for resolution.
- RegistryKey has no LastWriteTime. P/Invoke advapi32!RegQueryInfoKey and convert the FILETIME. Key mtime is one of the strongest "recently created" signals available.
- Enumerate all users via RegistryHive.Users, skipping SIDs ending in _Classes and the well-known S-1-5-18/19/20. For logged-off users, `reg load HKU\Warden_<sid> C:\Users\<name>\NTUSER.DAT` then ALWAYS `reg unload` in a finally block — a leaked hive load blocks that user's next logon, exactly the class of damage the never-brick constraint forbids.
- REG_MULTI_SZ values come back as string[] and may contain a trailing empty element; the LSA Security Packages value on this machine is literally a single empty string, so guard every parser against empty and whitespace entries.

COMMAND-LINE LEXING. Use CommandLineToArgvW (shell32) via P/Invoke, marshal the returned char** with Marshal.PtrToStringUni over the pointer array, and LocalFree the result — hand-rolled quote parsing gets unquoted service paths and embedded-quote arguments wrong, which is precisely the bug class that produces false positives. Suspicion tokens to score on the ARGUMENT VECTOR (not the raw string, to defeat casing and whitespace tricks): -enc / -e / -ec / -encodedcommand, -w hidden / -windowstyle hidden, -nop / -noprofile, -ep bypass / -executionpolicy bypass, IEX, FromBase64String, DownloadString, mshta with a javascript:/vbscript: URI, rundll32 with a comma-entrypoint into a non-System32 DLL, regsvr32 /s /u /i:http, certutil -urlcache / -decode, bitsadmin /transfer, wmic process call create, msiexec /q with an http path, curl/wget writing to %TEMP%, and any single argument over 512 chars with a base64 character distribution.

PATH CLASSIFICATION. Build one function PathClass(resolvedPath) returning { SystemProtected, ProgramFiles, ProgramData, UserProfileProgram, UserProfileData, Temp, Public, Removable, Network, Unknown } and score on the class, never on a substring match. Note explicitly that ProgramData is NOT inherently suspicious on this machine because Defender lives there, and that %LOCALAPPDATA%\Programs is where every Electron/Squirrel app legitimately installs.

WOW64 FILE REDIRECTION. A 64-bit process reading C:\Windows\System32 sees the 64-bit directory; a path recorded by a 32-bit component may mean SysWOW64. When a service or DLL reference resolves to System32 but the referencing component is 32-bit, also probe C:\Windows\SysWOW64. Use C:\Windows\Sysnative only from 32-bit processes — it does not exist for 64-bit ones.

COM INTEROP ON .NET 10. Built-in COM interop is enabled by default for net10.0-windows; do NOT set BuiltInComInteropSupport=false, and do not enable aggressive trimming or NativeAOT without testing, because Type.GetTypeFromProgID and dynamic late-binding are how Task Scheduler, WMI, IShellLinkW and BITS are reached without packages. Prefer explicit [ComImport] interface declarations over dynamic for hot paths (trim-safe and much faster); reserve dynamic for the Task Scheduler prototype. Always Marshal.ReleaseComObject (or a SafeHandle-style wrapper) in a finally — leaking IWbemServices references keeps WmiPrvSE.exe alive and looks like a leak in Task Manager.

THREE-WAY TASK RECONCILIATION is the highest-value single algorithm here: compare the COM enumeration (with TASK_ENUM_HIDDEN), the file set under C:\Windows\System32\Tasks, and the TaskCache\Tree + TaskCache\Tasks registry sets. A task missing from any one of the three, or a Tree leaf whose SD value has been deleted, is hidden by construction and cannot be explained benignly. Guard against the creation race by re-reading after ~2 seconds before alerting.

BASELINE-FIRST ONBOARDING. Because the verified baseline on this machine is unusually clean on the high-signal surfaces (WMI has exactly one in-box subscription; zero IFEO Debuggers; empty AppInit_DLLs; AppCertDlls key absent; BootExecute is 'autocheck autochk *'; netsh has exactly the 21 in-box helpers; print processors are just winprint; Winlogon Shell/Userinit are canonical; both Startup folders are empty), Warden should snapshot all 46 surfaces at first run, present the ~30 non-Microsoft entries for the user to confirm as known-good, and thereafter alert primarily on DELTAS. Snapshot-and-diff converts most of these surfaces from a noisy classification problem into a near-noiseless change-detection problem, and it is what makes "precision beats recall" actually achievable on a machine this heavily populated with developer tooling.

ACCEPTABLE SHELL-OUTS, and the one that is not: `schtasks.exe /query /xml ONE`, `sc.exe qc` / `sc.exe qfailure`, `netsh winsock show catalog`, `wevtutil.exe sl <channel> /e:true`, and `pwsh -NoProfile -NonInteractive -Command "... | ConvertTo-Json -Depth 6"` for CIM queries are all fine as fallbacks. Do NOT use wmic.exe — it is deprecated and is removed or disabled on 24H2/25H2-era builds including this one. Always pass -NoProfile when invoking any PowerShell so a compromised profile script (surface #38) cannot execute inside Warden's own scan.

- **Claim:** Phantom-DLL positive check: 'C:\Windows\System32\fxsst.dll ... none should exist on a clean Win11; presence is a detection.'
  - **Why wrong:** Verified on the target machine right now: C:\Windows\System32\fxsst.dll EXISTS (Test-Path = True). fxsst.dll is the in-box Fax shell/service stub shipped with Windows 11. Warden would fire a 'high' phantom-DLL detection on this box on first run, on a Microsoft-signed in-box file — the exact damaging false positive the project says is its primary risk. (The other five in the list were verified absent: WptsExtensions.dll, wlbsctrl.dll, TSMSISrv.dll, TSVIPSrv.dll, System32\wbem\wbemcomn.dll. Note System32\wbemcomn.dll DOES exist and is the legitimate one — an implementation that drops the \wbem\ segment inverts the test.)
  - **Fix:** Remove fxsst.dll from the zero-base-rate presence list. Re-derive the whole phantom list by running File.Exists against a clean 26200 image at build time and shipping only the paths that are actually absent; for anything that exists, degrade the rule from 'presence = detection' to 'presence + fails WinVerifyTrust Microsoft catalog check = detection'. Hard-code the \wbem\ path with a comment saying the System32 sibling is legitimate.
- **Claim:** Print Processors: 'Resolve the DLL relative to C:\Windows\System32\spool\prtprocs\<env>\ (NOT System32)' where <env> comes from enumerating HKLM\SYSTEM\CurrentControlSet\Control\Print\Environments.
  - **Why wrong:** The registry environment names and the on-disk directory names are different namespaces. Verified on this machine: Print\Environments has 5 subkeys — 'Windows 4.0', 'Windows ARM64', 'Windows IA64', 'Windows NT x86', 'Windows x64' — while C:\Windows\System32\spool\prtprocs contains exactly one child directory: 'x64'. String-building spool\prtprocs\Windows x64 yields a non-existent path, so every print processor resolves to 'file not found' and either scores as unresolvable/suspicious or is silently skipped.
  - **Fix:** Map environment name to directory ('Windows x64'->x64, 'Windows NT x86'->w32x86, 'Windows ARM64'->arm64, 'Windows 4.0'->win40), or better, read the print processor key's own 'Directory' value where present and fall back to enumerating the actual child directories of spool\prtprocs. Also skip environments with no on-disk directory rather than treating them as missing files.
- **Claim:** 'System.Diagnostics.EventLog IS in-box ... which gives Warden real-time persistence-change detection via EventLogWatcher for free', with a watch list including Security 4698/4699/4702/4657/4697 and TaskScheduler/Operational 106.
  - **Why wrong:** The assembly is in-box (verified: System.Diagnostics.EventLog.dll is in Microsoft.WindowsDesktop.App\10.0.11), but the events are not free. Verified on this machine: (a) reading the Security channel unelevated is denied — 'To access the Security log start PowerShell with elevated user rights ... Attempted to perform an unauthorized operation'; (b) Microsoft-Windows-TaskScheduler/Operational is Enabled=False, so event 106 is not being generated at all. On top of that, 4698/4699/4702 require 'Audit Other Object Access Events', 4697 requires 'Audit Security System Extension', 4688 requires 'Audit Process Creation', and 4657 requires both audit policy AND per-key SACLs — none of which are on by default on a standalone Win11 Pro box. So the majority of the proposed watch list produces zero events as shipped.
  - **Fix:** Split the event table into three tiers and surface the tier in the UI: FREE+UNELEVATED (System 7045/7040; Microsoft-Windows-WMI-Activity/Operational 5857/5860/5861 and Microsoft-Windows-Bits-Client/Operational 3/59 — both verified Enabled=True with live records on this box); REQUIRES ELEVATION (anything on Security, or add Warden's account to Event Log Readers, which is itself a security-settings change); REQUIRES AUDIT-POLICY OPT-IN (4657/4688/4697/4698/4699/4702) and CHANNEL ENABLEMENT (TaskScheduler/Operational). Default the continuous loop to RegNotifyChangeKeyValue + FileSystemWatcher + the two already-enabled operational channels, and make everything else an explicit, revertible opt-in.
- **Claim:** 'use RegNotifyChangeKeyValue (advapi32) with REG_NOTIFY_CHANGE_LAST_SET | REG_NOTIFY_CHANGE_NAME and fWatchSubtree, waiting on the event handle from a background thread'.
  - **Why wrong:** Two omissions that make this silently stop working. (1) Without REG_NOTIFY_THREAD_AGNOSTIC (0x10000000) the notification registration is bound to the calling thread and is cancelled when that thread exits — with any ThreadPool, Task, or async continuation the watch dies at a random point and Warden reports 'no changes' forever. (2) The notification is one-shot: it signals once and must be re-registered after every signal, and it tells you nothing about WHAT changed, so each signal needs a full re-read and diff of that key.
  - **Fix:** Always OR in REG_NOTIFY_THREAD_AGNOSTIC; hold the RegistryKey/SafeRegistryHandle open for the life of the watch; re-arm inside the wait loop before doing the diff (otherwise you miss changes that occur during the diff); and keep a dedicated long-lived thread per watch group rather than ThreadPool work items.
- **Claim:** 'Split exe from args with CommandLineToArgvW (shell32.dll, P/Invoke, free with LocalFree)' as the way to derive ResolvedImagePath from a Run value / ImagePath.
  - **Why wrong:** CommandLineToArgvW implements the CRT argv rules, not the CreateProcess image-resolution rules. For an unquoted 'C:\Program Files\Vendor\svc.exe -arg' it returns argv[0] = 'C:\Program', so ResolvedImagePath is wrong exactly for the unquoted-path case the spec elsewhere builds a whole detection around — you get a bogus 'image does not exist' on legitimate entries and you lose the real binary for signature verification.
  - **Fix:** Two different parsers. For the image: replicate CreateProcess resolution — if the string starts with a quote take the quoted span; otherwise progressively truncate at each space, appending '.exe' where there is no extension, and take the first candidate that File.Exists. For the argument vector used by the token scorer: CommandLineToArgvW on the remainder only. Keep both on PersistenceEntry and never feed argv[0] into the path classifier.
- **Claim:** 'Service ACLs return ACCESS_DENIED unelevated — verified on this box' and 'Service object DACLs ... are equally gated'.
  - **Why wrong:** Verified false on this machine unelevated: 'sc.exe qc WinDefend' returns QueryServiceConfig SUCCESS, and 'sc.exe sdshow WinDefend' and 'sc.exe sdshow Spooler' both return the full DACL. Default service security descriptors grant READ_CONTROL and SERVICE_QUERY_CONFIG to Authenticated Users/Interactive, so QueryServiceConfigW and QueryServiceObjectSecurity(DACL_SECURITY_INFORMATION) succeed without elevation. If Warden marks this surface PartialAccessDenied it will tell the user a surface is unscanned when it was fully scanned — which trains them to ignore the badge.
  - **Fix:** Only SACL reads (SACL_SECURITY_INFORMATION, needs SeSecurityPrivilege) and writes need elevation. Drop services from the elevated-only list; keep TaskCache and System32\Tasks there (both re-verified denied unelevated on this box).
- **Claim:** 'C:\Program Files\WindowsApps enumeration' is listed among the surfaces gated behind elevation.
  - **Why wrong:** Verified unelevated on this machine: Get-ChildItem 'C:\Program Files\WindowsApps' -Directory returned 306 package directories, and listing inside a package directory also succeeded. Directory listing of WindowsApps is permitted to Users on Windows 11; only some file contents are restricted.
  - **Fix:** Move WindowsApps from 'elevated-only' to 'enumerable unelevated, some file reads restricted'. Report per-file access failures rather than declaring the whole surface unscanned.
- **Claim:** MSIX StartupTask State mapping: 'REG_DWORD: 1 or 2 = enabled, 0 = disabled by user, 3+ = disabled by policy'.
  - **Why wrong:** This inverts two of the five states. The StartupTaskState enum is Disabled=0, DisabledByUser=1, Enabled=2, DisabledByPolicy=3, EnabledByPolicy=4. The spec's mapping reports a user-disabled task (1) as ENABLED — a false positive for an autostart that does not run — and reports EnabledByPolicy (4) as 'disabled by policy', hiding a genuinely active autostart.
  - **Fix:** Use the documented enum: {0:Disabled, 1:DisabledByUser, 2:Enabled, 3:DisabledByPolicy, 4:EnabledByPolicy}, treat only 2 and 4 as live, and cross-check against the package's AppxManifest StartupTask extension rather than trusting the DWORD alone.
- **Claim:** Winsock LSP: 'check ProtocolChain.ChainLen — ChainLen > 1 means a layered provider is inserted.'
  - **Why wrong:** ChainLen has three meanings: 0 = this entry IS a layer (the malicious DLL registers itself this way), 1 = a base protocol, >1 = a protocol chain that references layers. Testing only for >1 finds the chain but never identifies the layer itself, and on a clean machine with no LSPs at all there is nothing to find; conversely a lone layer with no chain yet installed is invisible to the test.
  - **Fix:** Enumerate all entries; flag any entry with ChainLen == 0 (a layer) and, for entries with ChainLen > 1, resolve every catalog entry ID in ChainEntries[] and score each referenced DLL. Keep the read-only stance the spec already states.
- **Claim:** AMSI item: read the Defender exclusion lists at 'HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions\{Paths,Extensions,Processes}'.
  - **Why wrong:** Verified on this machine: opening HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions throws SecurityException. That subtree is protected by Defender's own tamper protection and is not readable by ordinary admins either, so the elevated helper will not rescue this. Warden would report 'no exclusions' on a machine that has them — the opposite of the intended signal.
  - **Fix:** Read exclusions through Defender's own surface: Get-MpPreference (ExclusionPath/ExclusionExtension/ExclusionProcess) or MSFT_MpPreference in root\Microsoft\Windows\Defender via the IWbemLocator path already required for WMI. HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions IS readable and covers the policy-set ones only. Also add Get-MpComputerStatus for the real-time-protection state instead of inferring it from the DisableRealtimeMonitoring policy value, which is absent on a healthy machine.
- **Claim:** Perflib item: 'Warden must not itself trigger the payload — resolve and verify the DLL on disk WITHOUT calling PerformanceCounterCategory' and then, in the same item, 'System.Diagnostics.PerformanceCounter.dll IS in-box ... if you need the managed category list for cross-reference'.
  - **Why wrong:** Self-contradictory and the second half is the dangerous one. PerformanceCounterCategory.GetCategories() and any counter query cause the perflib provider DLLs — including the attacker's Library — to be loaded into Warden's own process. Since Warden may be running from an elevated helper, that is code execution as SYSTEM triggered by the scanner itself.
  - **Fix:** Delete the cross-reference suggestion entirely. Enumerate Services\*\Performance from the registry only, and get the category name list (if it is really needed) from HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Perflib\009\Counter, which is a plain REG_MULTI_SZ read.
- **Claim:** RunOnce: 'a RunOnce value that PERSISTS across two reboots is anomalous by construction'.
  - **Why wrong:** Not by construction. RunOnce is processed by Explorer at interactive logon only; a value survives indefinitely if (a) the name is '!'-prefixed and the command keeps failing, (b) no interactive logon has happened since it was written, (c) the writing installer was uninstalled/rolled back leaving the value behind, or (d) a servicing operation is waiting on a pending-reboot condition. Windows Update and MSI rollback entries legitimately outlive several reboots. As written this rule will alarm on installer residue.
  - **Fix:** Downgrade to a triage signal: correlate persistence-across-reboots with an unresolvable or unsigned image, or a '!'/'*' prefix, before surfacing anything. Otherwise route stale RunOnce values to the Maintenance half as cleanup candidates.
- **Claim:** Accessibility-binary remediation: 'NEVER delete or quarantine the System32 binary itself, restore it from WinSxS instead' (and 'compare size/hash against the WinSxS copies of the same binary').
  - **Why wrong:** Restoring from WinSxS is a write into System32, and the component store holds multiple versions/variants of the same binary (per-update, per-language, per-architecture). Copying the wrong one, or taking ownership from TrustedInstaller and loosening the ACL to make the copy possible, is exactly the 'could break Windows' action the project forbids — and a permanently non-TrustedInstaller-owned System32 file breaks future servicing. The hash comparison has the same version-matching problem and will produce spurious mismatches after any cumulative update.
  - **Fix:** Never write to System32. On a tamper finding, quarantine only the IFEO registry value, then tell the user to run 'sfc /scannow' or 'DISM /Online /Cleanup-Image /RestoreHealth' from an elevated prompt themselves. For the integrity check, use WinVerifyTrust catalog verification plus the TrustedInstaller-owner check the spec already has — not a hash diff against WinSxS.
- **Claim:** 'for logged-off users load NTUSER.DAT with reg load HKU\WardenTmp ... and reg unload after' / 'ALWAYS reg unload in a finally block'.
  - **Why wrong:** A finally block is not sufficient to guarantee the unload. RegUnLoadKey fails while ANY handle under the loaded hive is still open, and .NET RegistryKey objects hold those handles until they are disposed and, for keys reachable only through finalization, until a GC has run. A failed unload leaves an orphaned hive mounted, which is the documented cause of that user getting a temporary profile at next logon — the never-brick class of damage. Also, reg load requires elevation and fails outright if the SID is already present in HKEY_USERS.
  - **Fix:** Skip any SID already present under HKEY_USERS. Wrap every opened key in using/Dispose, force GC.Collect()+WaitForPendingFinalizers() before unload, check the RegUnLoadKey return code, retry with backoff, and if it still fails raise a loud, actionable error rather than swallowing it. Better: make offline-profile scanning an explicitly user-invoked action, not part of the continuous loop.
- **Claim:** Shell-out fallbacks: 'pwsh -NoProfile ...', 'reg load ...', 'sc.exe qfailure', 'netsh winsock show catalog', 'wevtutil.exe sl <channel> /e:true', 'schtasks.exe'.
  - **Why wrong:** Every one of these is invoked by bare name, so resolution goes through the PATH of the invoking process. HKCU\Environment on this box already has a user-writable Path (verified: Path, JAVA_HOME, ANDROID_HOME, WWISEROOT, ChocolateyLastPathUpdate...). If Warden's elevated helper shells out by name, a non-admin-writable PATH entry gives arbitrary code execution as SYSTEM — Warden itself becomes the best persistence surface on the machine.
  - **Fix:** Always invoke by absolute path built from Environment.GetFolderPath(SpecialFolder.System) (C:\Windows\System32\reg.exe, sc.exe, netsh.exe, wevtutil.exe, schtasks.exe) and a resolved, signature-verified absolute path for pwsh.exe. Set ProcessStartInfo.UseShellExecute=false, pass an explicit sanitised environment block, and verify the Authenticode signature of the target before launching it from the elevated helper.
- **Claim:** BITS: 'EnumJobs(BG_JOB_ENUM_ALL_USERS = 1)' and the fallbacks 'bitsadmin /list /allusers' / 'Get-BitsTransfer -AllUsers'.
  - **Why wrong:** BG_JOB_ENUM_ALL_USERS requires administrator privileges; unelevated the flag is ignored/denied and you enumerate only the current user's jobs. Since Microsoft's own jobs (Windows Update, Defender, Store) run as SYSTEM, an unelevated scan sees essentially nothing and the surface silently reports clean — and the spec's own headline discriminator (a SYSTEM-owned job with a NotifyCmdLine) is precisely what gets hidden.
  - **Fix:** Mark BITS as elevated-required for the all-users view, run it in the helper, and in the unelevated path label the surface PartialAccessDenied rather than Complete.
- **Claim:** IFEO enumeration: 'Enumerate subkeys of both views; for each read Debugger. ALSO read the parallel per-architecture subkey ...\<name>\<arch>'.
  - **Why wrong:** This misses the per-path IFEO form introduced in Windows 10 and present on 26200: an arbitrary-named subkey under IFEO\<exename.exe> carrying UseFilter=1 on the parent plus FilterFullPath=<full path> and its own Debugger/GlobalFlag/VerifierDlls. A collector that only reads <exe>\Debugger and <exe>\<arch> will not see a Debugger targeted at one specific copy of an executable.
  - **Fix:** For each IFEO\<exe> key, read UseFilter; if set, recurse every subkey looking for FilterFullPath plus Debugger/GlobalFlag/VerifierDlls, and record the FilterFullPath as part of the entry's Location so the user can see which binary is targeted.
- **Claim:** PowerShell profiles: the fixed 12-path list including '%ProgramFiles%\PowerShell\7\profile.ps1', described as covering this machine's pwsh 7.6.5.
  - **Why wrong:** The spec itself notes this pwsh is an MSIX under C:\Program Files\WindowsApps, which means $PSHOME is the versioned package directory, not %ProgramFiles%\PowerShell\7 — so the AllUsers profile path in the list does not exist here and the real one moves on every package update. The list also omits the VS Code host profile (Microsoft.VSCode_profile.ps1), which a developer using the PowerShell extension will have.
  - **Fix:** Do not hard-code $PSHOME. Derive it once per host by running the resolved pwsh.exe with -NoProfile -Command '$PROFILE | Format-List *' (or read the package root from the AppModel repository), cache it, and re-derive when the package version changes. Add Microsoft.VSCode_profile.ps1 for both PowerShell editions.
- **Claim:** 'System.ServiceProcess.dll in Microsoft.NETCore.App/10.0.11 is a 1-typedef facade' and 'System.Management.dll is ABSENT everywhere', plus the four in-box assembly claims.
  - **Why wrong:** These are correct and I verified them, but the inventory is incomplete in a way that matters for the ACL work the spec depends on: Microsoft.Win32.Registry.AccessControl.dll is ONLY in Microsoft.WindowsDesktop.App (not in Microsoft.NETCore.App), while System.IO.FileSystem.AccessControl.dll (104,272 bytes, real) and System.Security.AccessControl.dll (227,152 bytes) ARE in Microsoft.NETCore.App. Verified sizes: System.ServiceProcess.dll 15,656 (facade), Microsoft.Win32.Registry.dll 116,520 (real, NETCore.App).
  - **Fix:** Record the split explicitly, because it constrains any future decision to ship a non-WPF console component: a net10.0-windows tool that does NOT reference Microsoft.WindowsDesktop.App loses RegistryKey.GetAccessControl (Microsoft.Win32.Registry.AccessControl), EventLogWatcher, and PerformanceCounter. Keep the elevated helper on the WindowsDesktop framework reference too, or plan the P/Invoke replacements.

### False-positive risks
- BlueStacks-with-root on this specific machine: the user's own setup has a PATCHED HD-Player binary. A patched PE fails Authenticode/catalog verification, and BlueStacks ships auto-start services (BstHdAndroidSvc/BstHdUpdaterSvc) plus kernel drivers. The conjunction 'unsigned image + auto-start service + kernel driver' is exactly the highest-scoring pattern in the proposed pipeline, so Warden's very first deep scan will rank the user's deliberately-patched emulator as a critical finding, and any auto-action would break his root setup. Needs an explicit user-declared-exception mechanism at onboarding, not just a publisher allow-list.
- GPU and graphics debugging tools set IFEO Debugger on game/engine executables as their normal launch mechanism — NVIDIA Nsight, PIX for Windows, RenderDoc's injection, and Steam/EOS overlay shims. The spec anticipates vsjitdebugger and 'Unreal/Unity crash-handler setups' but not these, and on a game-dev box they are far more likely than the ones listed. An IFEO Debugger detection at 'critical' will fire during ordinary graphics debugging sessions.
- DLL search-order behavioural check via Process.Modules / CreateToolhelp32Snapshot over every process: on a machine with Steam/Epic/Ubisoft installed, hundreds of processes have app-local msvcp140/vcruntime140/dbghelp copies, and Python venvs, node native modules, Unreal editor plugin DLLs and Blender's bundled Python all shadow System32 names. The spec's mitigation ('unsigned module shadowing a System32 name inside a signed process whose publisher differs') still hits every Unreal project DLL loaded into a signed UnrealEditor.exe and every unsigned native node/python extension loaded into a signed node.exe/python.exe. This rule as stated is not shippable on this machine.
- IObit Driver Booster/Uninstaller self-repair: these products recreate their scheduled tasks and services when removed. If Warden quarantines the 'SkipUAC' tasks or the /rpop promo tasks, IObit recreates them and Warden re-detects — an alert loop that trains the user to dismiss everything. Warden needs re-creation detection (same SurfaceId reappearing within N minutes of a remediation) and a 'stop fighting this, suppress permanently' path.
- The 'Policies\Explorer\Run + Policies\System tamper cluster' rule on a standalone Pro machine that already runs IObit UAC-bypass tooling, and where debloat/tweak scripts are common in this user's population, will collide with legitimately-set policy values (UAC prompt behaviour, NoDrives, Task Manager policy) that the user or a tweak tool set deliberately. Correlate strictly with a NEW Run value appearing in the same window; a policy value alone is a hardening observation, not a detection.
- COR_/CORECLR_ profiler detection: the spec covers it, but the same class of injection is also configured through DOTNET_STARTUP_HOOKS, DOTNET_ADDITIONAL_DEPS and DOTNET_SHARED_STORE, which the spec does not enumerate at all. A .NET developer running coverage/APM tooling can have any of the five set, so a rule that only knows about COR_* will both miss the attack and, when the missing three are added later without an allow-list, produce a fresh wave of FPs.
- WSL rc-file scanning: the spec's own FP note is right but understates it. Reaching \\wsl.localhost\<distro> STARTS the distro (wslservice launches the VM on first access), which (a) executes the [boot] command= the scan is looking for, (b) costs seconds and hundreds of MB, and (c) will do this on every scan cycle. This turns a detection into a trigger. Gate the WSL surface behind 'distro already running' (wsl.exe --list --running) or make it a user-invoked deep scan only.
- Service 'unquoted ImagePath' on this box: the spec says to expect several among IObit/AMD/older launchers and to only flag when a hijack file is actually creatable. That gate is right, but the writability probe itself (attempting a create at C:\Program.exe, C:\Program Files\Some.exe) must be a permissions evaluation, not an actual file create — an actual probe file left behind at a hijack point is itself a persistence artefact and would be picked up by the next scan or by another AV.
- StartupApproved orphan rule ('an entry with no matching Run value is inert history — never surface it'): the join must consider Run64, Run32 (WOW6432Node) and BOTH startup folders, and StartupFolder value names are .lnk filenames including extension. A join that only checks the 64-bit HKCU Run key will classify every legitimate 32-bit-app approval record as an orphan and silently hide a live 32-bit autostart — inverting the rule from 'suppress noise' to 'suppress detections'.
- Chromium shortcut-argument deny-list: Opera GX, Edge, Steam's embedded CEF, Discord, VS Code (Electron), Unreal's own web widgets and every Puppeteer/Playwright run legitimately pass long flag sets including --remote-debugging-port. The spec correctly restricts to persisted .lnk files, but the Start Menu on this box contains Electron app shortcuts that Squirrel rewrites on every update, so 'recently modified .lnk with many flags' will churn. Score only the specific deny-listed flags on a browser target, never flag count or recency alone.

### Safety objections
- The elevated helper is specified only as 'narrowly-scoped ... ONLY performs enumeration and quarantine, never arbitrary commands' — that is not narrow. A SYSTEM service that will move a caller-named file into a vault and delete a caller-named registry value is an arbitrary-file-move-as-SYSTEM and arbitrary-registry-delete primitive available to any process running as the user. That is a textbook local privilege escalation, and it also lets any local malware disable Defender by asking Warden to quarantine MsMpEng's directory. Required: named-pipe IPC with an explicit client SID/session check, a fixed operation enum with no free-form paths, server-side re-derivation (the helper re-runs the detection itself and refuses any target ID it did not just produce), a hard deny-list (System32, WinSxS, the Defender Platform directory, SCM/Services keys, anything owned by TrustedInstaller), and opening every target with FILE_FLAG_OPEN_REPARSE_POINT plus verifying by handle so a junction swapped in between decision and action cannot redirect the move.
- The quarantine vault's restore path is an equal-and-opposite SYSTEM arbitrary-file-WRITE primitive. Restoring to a stored original path must re-validate that path against the same deny-list at restore time (not at quarantine time), and the vault directory itself must have an ACL denying the interactive user write/rename, or malware simply edits the stored original-path metadata and has Warden write its payload into System32 as SYSTEM.
- The baseline snapshot is load-bearing for the entire 'snapshot-and-diff' design, and nothing in the spec protects it. If the baseline file lives anywhere the user (and therefore user-level malware) can write, the first thing a stealer does is add itself to the baseline and become permanently invisible. The baseline needs to live under a SYSTEM-writable-only directory with an HMAC keyed to a DPAPI-machine-protected secret, and Warden must alarm loudly if the baseline fails integrity check rather than silently rebuilding it.
- Enumerating other processes' modules (CreateToolhelp32Snapshot/Process.Modules) and reading command lines out of the PEB via NtQueryInformationProcess + PROCESS_VM_READ are the exact behaviours kernel-mode anti-cheat (Riot Vanguard, EasyAntiCheat, BattlEye) classifies as cheating. On a machine that plays games, a tray-resident process doing this continuously risks account bans and, with some AC drivers, handle-stripping or a bugcheck. Neither technique is necessary: Win32_Process.CommandLine over the WMI interop the project already needs gets command lines out-of-process, and the phantom/side-loading checks can be done entirely on disk. If module enumeration is kept at all it must be opt-in, one-shot, and skip any process whose image is under a game/anti-cheat directory.
- 'wevtutil.exe sl <channel> /e:true' is listed as an acceptable shell-out with no consent gate, but enabling an event channel is a persistent machine-wide configuration change that also grows on-disk log storage. The spec correctly flags SACL/audit-policy as needing opt-in and then quietly exempts channel enablement. Treat both identically: explain, get an explicit yes, record it, and provide one-click revert (/e:false).
- The never-kill list covers processes but not services and drivers, and the destructive action for a service is not 'kill' — it is setting Start=4 or deleting the key. Setting Start=4 on a boot-start storage or filter driver (stornvme, storahci, iaStorAC, volsnap, or the vendor filter drivers BlueStacks and Docker install) produces INACCESSIBLE_BOOT_DEVICE and an unbootable machine. Warden must refuse to modify any service with Type 0x1/0x2 or Start 0/1 outright, and must refuse to disable any service that other running services depend on (read DependOnService transitively first).
- Reading other users' NTUSER.DAT hives is framed purely as a technical problem. On a shared machine it is also a privacy decision the owner of that profile has not made. It should require an explicit, per-profile consent step in the UI, and the scan should never copy hive contents into logs or the baseline beyond the specific values being evaluated.
- Parsing untrusted .lnk files through IShellLinkW + IPersistFile means loading attacker-controlled shell data through the Shell's own COM parsers inside Warden's process — historically a source of shell-parsing vulnerabilities, and Warden may be the elevated helper. For files in the two Startup folders and anywhere else an attacker can write, prefer the pure-managed MS-SHLLINK binary parse (the spec's option (b)) despite it being more code, or do the COM parse in a low-integrity, non-elevated sacrificial worker process.

### Omissions
- Kernel drivers are not treated as a distinct surface. The services item folds Type 0x1/0x2 in with user-mode services, but a driver is the highest-severity persistence on the machine and needs its own rules: Start 0/1 with an ImagePath outside %SystemRoot%\System32\drivers, a driver whose signature is valid but is on a known-vulnerable-driver list (BYOVD — the actual delivery mechanism for most 2024-26 EDR-killers), and the filter-driver surfaces HKLM\SYSTEM\CurrentControlSet\Control\Class\{class-guid}\UpperFilters / LowerFilters. Directly relevant here: BlueStacks-with-root and Docker/WSL both install filter drivers.
- Boot configuration is absent. bcdedit testsigning=on, nointegritychecks=on, or a disabled Secure Boot / disabled VBS-HVCI is what makes an unsigned driver loadable in the first place, and this user's rooted-BlueStacks setup is exactly the population that has toggled these. Read the BCD (HKLM\BCD00000000 elevated, or 'bcdedit /enum {current}') plus Secure Boot state (Confirm-SecureBootUEFI / the UEFISecureBootEnabled value) and report them as a hardening context that raises or lowers the severity of every driver finding.
- Legacy .job scheduled tasks are not covered. C:\Windows\Tasks exists on this machine (verified — it contains SA.DAT). Modern Windows still enumerates .job files through the Task Scheduler 1.0 compatibility surface, and they appear in none of the three sources the three-way reconciliation compares, so a .job dropped there is invisible to the entire task pipeline as designed. Add it as a fourth source.
- DOTNET_STARTUP_HOOKS / DOTNET_ADDITIONAL_DEPS / DOTNET_SHARED_STORE are missing from the environment-injection item. On a box with four .NET runtimes and a .NET-based Warden, a startup hook set in HKCU\Environment injects managed code into every .NET process started thereafter — including, potentially, Warden itself. Same key, same collector, three more value names.
- PSModulePath hijacking is missing. Adding a user-writable directory to PSModulePath (HKCU\Environment) and placing a module named like one that is auto-loaded (e.g. a fake PSReadLine or Microsoft.PowerShell.Utility proxy) gets code executed in every PowerShell session without touching any profile file. This user's HKCU\Environment is already heavily populated, making the addition easy to hide.
- Group Policy client-side extension DLLs: HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\GPExtensions\{guid}\DllName. Loaded by gpsvc as SYSTEM on every policy refresh, a well-known and rarely-checked SYSTEM persistence point, and structurally identical to the Notify/TimeProviders collectors already specified.
- HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Drivers32 (msacm.* / vidc.* codec DLLs) and HKLM\SOFTWARE\Classes\Protocols\{Filter,Handler} (pluggable protocol handlers loaded into Explorer and WebView2 hosts) are both classic autorun-scanner surfaces with near-zero legitimate churn, and both are absent.
- Text-input / CTF surfaces: HKLM\SOFTWARE\Microsoft\Ctf\LangBarAddin and the TIP registrations under HKLM\SOFTWARE\Microsoft\CTF\TIP\{clsid}. A registered text service DLL is loaded into essentially every process with a text field, and it is a documented persistence technique that no consumer software on this box uses — high precision, cheap to enumerate.
- Developer-targeted persistence is missing entirely despite the user profile being the stated threat model. Concretely: git's core.hooksPath in the global .gitconfig and the .git/hooks/* of any repo under D:\My projects (a pull that runs code), VS Code's .vscode/tasks.json with runOptions.runOn = folderOpen (opens a folder, runs a command), and %USERPROFILE%\.vscode\extensions. These are the realistic 2026 attack path against this specific user and they are more likely than several of the legacy surfaces the spec spends items on.
- Nothing addresses Warden's own persistence and self-integrity. Warden itself will occupy a Run key or a scheduled task, which is a first-class target: hijack Warden's own autorun and you inherit its tray presence and, if it has an elevated helper, its privileges. The spec needs a self-check (verify the helper binary's signature and ACL before starting it, verify Warden's own autorun entry each run, refuse to start the helper from a user-writable directory) and an explicit statement that Warden's own entries are shown, not hidden, in its dashboard.
- No specification of what happens when a surface's raw value cannot be represented losslessly. The rollback model correctly says to store RegistryValueKind and raw bytes, but there is no handling for a REG_SZ containing embedded nulls, a value name containing characters the UI cannot render, a value larger than the API's convenience path, or a key whose DACL denies Warden delete-but-allows-read. Each of these is a way to make a persistence entry unquarantinable — and, without an explicit 'detected but could not be remediated' state distinct from 'remediated', Warden will report success on a failed removal.
- The three-way task reconciliation has no false-negative story for the case it most needs to handle. If the COM enumeration is the only source available (unelevated, because both TaskCache and System32\Tasks are denied — re-verified on this box), the algorithm cannot run at all, and an SD-deleted task is invisible to COM by definition. So unelevated Warden is structurally blind to the single technique the spec calls its highest-value algorithm. That needs to be stated plainly in the UI as 'hidden-task detection requires elevation', not folded into a generic PartialAccessDenied badge.
