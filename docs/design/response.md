# Warden — Response & Containment Subsystem: Structural Safety Design

> Area: `safe-response` · adversarial critique verdict: **needs_rework**

## Summary
This design makes catastrophic action structurally impossible rather than merely unlikely, by enforcing three invariants: (1) every destructive action must produce a typed undo record *before* it executes or it is refused at the type level; (2) the elevated broker independently re-validates the entire protected set, so a bug in the unelevated scorer cannot cause a catastrophic elevated action; (3) on any error, ambiguity, or missing undo record, the answer is always "do not act." I probed the target machine and four findings reshape the design. Controlled Folder Access is ENABLED and Tamper Protection is ON, so quarantining a file out of Desktop/Documents will be blocked by Defender even when elevated — this must be a guided manual allowlisting step, never automated. System Restore has ZERO restore points with VSS and sppsvc Stopped, so the assumed OS-level rollback does not exist and must be probed, not presumed. Unelevated, OpenProcess with PROCESS_QUERY_LIMITED_INFORMATION is DENIED (err 5) on every PPL and SYSTEM process, so the protection query itself is unavailable for exactly the processes that most need identifying — handle-open failure must therefore be treated as the protection signal (fail-closed). And IsProcessCritical returns False for explorer, audiodg, sihost, ctfmon and RuntimeBroker, proving the API is necessary but nowhere near sufficient and that the static denylist carries the real safety load. The machine also runs ~28 claude.exe, ~23 cmd.exe, ~22 node.exe and ~30 conhost.exe concurrently, which is behaviourally indistinguishable from a RAT — so autonomy ships OFF for a 7-day shakedown and developer roots are permanently ineligible for autonomous action.

## Items (32)
### [critical] Protected Set Tier 0 — kernel, session and boot-critical processes (NEVER kill, suspend, quarantine, or firewall)
Terminating any of these while elevated produces an immediate bugcheck (CRITICAL_PROCESS_DIED, 0xEF) or an unrecoverable session. The OS does NOT protect these from an administrator — an elevated Warden can blue-screen the machine. This static list, not any API, is the primary safety mechanism. Exhaustive Tier 0: Idle (PID 0), System (PID 4), Registry, Secure System, Memory Compression, smss.exe (session manager), csrss.exe (all instances), wininit.exe, winlogon.exe, services.exe, lsass.exe, LsaIso.exe, svchost.exe (ALL instances — never act on svchost by image; only ever stop the specific hosted service), dwm.exe, fontdrvhost.exe, userinit.exe, logonui.exe, consent.exe, TrustedInstaller.exe, TiWorker.exe, msiexec.exe, wlanext.exe, dasHost.exe, WUDFHost.exe, vmcompute.exe, vmwp.exe, vmms.exe, NgcIso.exe, SgrmBroker.exe, WerFault.exe, wermgr.exe.

**How:** Match case-insensitively on BOTH the Win32 image name from QueryFullProcessImageNameW(h, 0, ...) AND the resolved full path. Never match on Process.ProcessName alone — a dropper named 'csrss.exe' in %TEMP% must NOT inherit protection. Rule: protection requires name-in-list AND path under C:\Windows\System32 (or \SystemRoot\System32) AND Authenticode-valid Microsoft signature. Name-in-list AND path-elsewhere = a masquerade signal, score it UP, but still route to prompt-only because the risk of a naming collision is asymmetric.

**False positives:** The inverse error is the dangerous one: a masquerading binary in %TEMP%\svchost.exe must not gain protection. Resolve the path first, always. Conversely a legitimately relocated system binary (WinSxS servicing, DriverStore\FileRepository like the verified amdfendrsr.exe and atiesrxx.exe on this machine) is signed and benign — treat DriverStore\FileRepository as System32-equivalent for trust purposes.

### [critical] Protected Set Tier 1 — security, shell and UX-critical processes (never autonomous; prompt-only at most)
Killing these does not bugcheck but destroys the user's session, breaks input, or disables the machine's actual antivirus. Killing MsMpEng would be an attacker's dream and must be structurally impossible. Exhaustive Tier 1: MsMpEng.exe, MpDefenderCoreService.exe, NisSrv.exe, MpCmdRun.exe, SecurityHealthService.exe, SecurityHealthSystray.exe, smartscreen.exe, WmiPrvSE.exe, WMIRegistrationService.exe, spoolsv.exe, audiodg.exe, explorer.exe, sihost.exe, ctfmon.exe, TextInputHost.exe, RuntimeBroker.exe, dllhost.exe, SearchHost.exe, SearchIndexer.exe, SearchProtocolHost.exe, SearchFilterHost.exe, StartMenuExperienceHost.exe, ShellExperienceHost.exe, ApplicationFrameHost.exe, taskhostw.exe, backgroundTaskHost.exe, conhost.exe, OpenConsole.exe, ctfmon.exe, ApplicationFrameHost.exe.

**How:** explorer.exe is a special case: demote to RESTART-ONLY (Process.Kill then Process.Start("explorer.exe")) and NEVER quarantine C:\Windows\explorer.exe. conhost.exe/OpenConsole.exe are console hosts — killing one detaches a live terminal and loses the user's unsaved work; this machine has ~30 running. dllhost.exe and rundll32.exe/regsvr32.exe/mshta.exe are LOLBin *hosts*: when malicious, act on the command line and the loaded module, never quarantine the host binary itself.

**False positives:** Defender processes are frequently flagged by naive heuristics for high I/O, memory scanning behaviour, and opening handles to every process — precisely the RAT signature. Hard-exclude MsMpEng from all behavioural scoring, not just from action.

### [critical] Protected Set — Warden's own process, full ancestor chain, and descendants
Warden killing its own ancestor kills Warden mid-action, stranding a half-applied change with no undo. Measured ancestry on this machine is pwsh.exe -> claude.exe -> claude.exe -> sihost.exe -> svchost.exe -> services.exe -> wininit.exe, which shows the chain reaches session-critical processes within a few hops. Protecting only the immediate parent is insufficient — the whole chain to the session root must be protected, plus Warden's own descendants (the broker, any dump helper).

**How:** At startup walk the chain: repeatedly Get-CimInstance Win32_Process ParentProcessId, or NtQueryInformationProcess(ProcessBasicInformation).InheritedFromUniqueProcessId, until PID 0 or an unresolvable parent. Cache as an immutable ProtectedAncestry set. CRITICAL: pair every PID with its creation time from GetProcessTimes to defeat PID reuse. Recompute the chain on each incident, not once at boot, since intermediate parents die.

**False positives:** A compromised parent is a real scenario, but the correct response is to alert and refuse to self-destruct, never to kill up the chain. If an ancestor scores HIGH, escalate to the user with a clear explanation rather than acting.

### [critical] Detecting protected-process (PPL/PP) status from usermode — and why IsProcessCritical is insufficient
MEASURED ON TARGET: unelevated, OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION) is DENIED with ERROR_ACCESS_DENIED (5) for System, Registry, smss, csrss, wininit, winlogon, services, lsass, MsMpEng, LsaIso, dwm, svchost and fontdrvhost. This is a chicken-and-egg problem: you cannot query the protection level of the processes whose protection matters most, because the query itself needs a handle you cannot get. Therefore handle-open failure IS the protection signal. Separately, IsProcessCritical returned False for explorer, audiodg, sihost, ctfmon and RuntimeBroker — so the API alone would authorise killing the user's entire shell. It is necessary but nowhere near sufficient.

**How:** Layered, fail-closed: (1) OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION=0x1000). If NULL and GetLastError()==5, classify PROTECTED and stop — never escalate. (PID 0 returns err 87 ERROR_INVALID_PARAMETER; treat identically.) (2) If a handle is obtained, NtQueryInformationProcess(h, ProcessProtectionInformation=61, &byte, 1, NULL); decode PS_PROTECTION: Type = bits 0-2 (0=None, 1=ProtectedLight, 2=Protected), Signer = bits 4-7 (3=Antimalware, 4=Lsa, 5=Windows, 6=WinTcb). Any Type != 0 => never act. (3) IsProcessCritical(h, out bool) from kernel32 => true means never act. (4) Token SID via OpenProcessToken + GetTokenInformation(TokenUser): S-1-5-18/19/20 => never autonomous. (5) SessionId == 0 => never autonomous. Pass ALL five to be eligible.

**False positives:** Do not interpret 'query succeeded and returned unprotected' as 'safe to kill'. audiodg returned ProtectionByte=0x00 (unprotected) yet killing it kills all system audio. The query is a veto, never an authorisation.

### [critical] What happens when a kill is denied by the OS, and how Warden must react
Understanding the failure modes prevents retry loops and privilege-escalation attempts that would themselves be dangerous. PPL processes cannot be terminated from usermode even as SYSTEM with SeDebugPrivilege — this is enforced in the kernel and is not an elevation problem, so retrying elevated is futile. Critically, the OS does NOT protect Tier 0 critical processes from an administrator: an elevated TerminateProcess on csrss.exe SUCCEEDS and immediately bugchecks the machine with CRITICAL_PROCESS_DIED (0xEF). The denylist is the only thing standing between Warden and a blue screen.

**How:** OpenProcess(PROCESS_TERMINATE=0x0001) returning NULL with GetLastError()==5 (ERROR_ACCESS_DENIED) => the target is PPL or higher-privileged. TerminateProcess returning false with err 5 => same. err 87 => invalid PID (0, or already exited). ERROR_INVALID_HANDLE (6) => process exited between open and terminate; treat as success. Warden's reaction to err 5 must be: log as ACTION_DENIED_BY_OS, mark the incident as needing manual review, and raise a SCORING DEFECT event — a denied kill means the scorer targeted something it should have excluded. Never retry, never attempt elevation to force it, never fall back to a driver.

**False positives:** A denied kill on a legitimately suspicious PPL-hosted item (e.g. malware injected into a protected process) is a real detection but an un-actionable one. The correct output is 'escalate to user with full evidence and recommend an offline scan', not a workaround.

### [critical] Protected Set — path denylist (never quarantine, never firewall by ApplicationName)
Moving or renaming any of these breaks boot, servicing, or the security stack. Because quarantine is a move, and a move from these trees is silently catastrophic, the path check must run inside the elevated broker, not only in the scorer.

**How:** Deny the entire subtree of: C:\Windows\ (all of it, with System32, SysWOW64, WinSxS, servicing, Boot, Fonts, INF, DriverStore called out), C:\Windows\System32\config\ (registry hives), C:\Program Files\WindowsApps\, C:\ProgramData\Microsoft\Windows Defender\, C:\$Recycle.Bin\, C:\System Volume Information\, the EFI System Partition, and the files pagefile.sys, hiberfil.sys, swapfile.sys, $MFT. Also deny Warden's own install directory, its vault, its ledger and its journal. Canonicalise first with GetFinalPathNameByHandleW(VOLUME_NAME_DOS) to defeat 8.3 short names, symlinks, junctions, and \\?\ prefixes — a string compare on the raw path is bypassable.

**False positives:** Malware genuinely does drop into C:\Windows\Temp and C:\Windows\Tasks, which are inside the denied tree. Carve these two back out as quarantine-eligible-with-prompt, since neither is required for boot or servicing.

A freshly built, unsigned, high-entropy .exe from Unreal/cargo/dotnet that spawns children and opens sockets is textbook malware behaviour and textbook game-dev behaviour simultaneously. Also permanently allowlist the toolchain caches: %USERPROFILE%\.nuget\, %USERPROFILE%\.cargo\bin\, %APPDATA%\npm\, %LOCALAPPDATA%\Programs\Microsoft VS Code\. Store as a user-editable list in the dashboard.

**False positives:** Also allowlist this user's known-odd software: HD-Player.exe and BstkSVC.exe (rooted BlueStacks with ReZygisk/LSPosed — will exhibit unusual syscall and network patterns by design), and TeamViewer_Service.exe / warp-svc.exe / steamservice.exe which were observed running and are legitimate remote-access and tunnelling software that RAT heuristics will flag.

### [critical] Protected Set — services and scheduled-task namespaces
Disabling or deleting a core service is as destructive as killing a process but harder to notice and harder to undo, since service configuration has a dozen fields that must all round-trip.

**How:** Never disable, delete, or reconfigure any service whose ImagePath resolves under C:\Windows\System32 with a valid Microsoft signature. Explicit deny by name: WinDefend, MpsSvc (firewall), wscsvc, SecurityHealthService, Sense, wuauserv, TrustedInstaller, BFE (Base Filtering Engine — killing this disables the firewall entirely and is a known attacker move), RpcSs, DcomLaunch, LSM, Power, Schedule, EventLog, CryptSvc, ProfSvc, Themes, AudioSrv, AudioEndpointBuilder, WSearch, VSS, swprv, gpsvc, SamSs, Netlogon, Dhcp, Dnscache, nsi, WinHttpAutoProxySvc. For tasks: never touch anything under the \Microsoft\Windows\ folder (verified 14 tasks in root via Schedule.Service COM, which connected successfully).

**False positives:** BFE and MpsSvc deserve special mention: legitimate detection logic may notice they are being tampered with, but Warden must never be the thing that stops them. Any Warden action that would reduce the machine's security posture is refused by design.

### [high] Microsoft-signature trust rule — and the Third Party PCA trap
'Signed by Microsoft' is the core trust primitive but is routinely misapplied. Microsoft cross-signs third-party kernel drivers and components under a DIFFERENT CA; treating those as system-trusted would allowlist a large amount of third-party code including known vulnerable drivers used in BYOVD attacks.

**How:** Use WinVerifyTrust (wintrust.dll, verified present) or System.Security.Cryptography.X509Certificates via Get-AuthenticodeSignature semantics. Require Status == Valid AND SignerCertificate.Subject contains 'O=Microsoft Corporation' AND the chain's issuing CA is one of 'Microsoft Windows Production PCA 2011', 'Microsoft Code Signing PCA', or 'Microsoft Windows'. Verified live on this machine: C:\Windows\System32\svchost.exe returns Status=Valid, Subject='CN=Microsoft Windows, O=Microsoft Corporation, L=Redmond, S=Washington, C=US', Issuer='CN=Microsoft Windows Production PCA 2011'. EXPLICITLY REJECT 'Microsoft Windows Third Party Component CA' and 'Microsoft Windows Hardware Compatibility' as system-trust roots. Cache results keyed by (path, SHA-256, lastWriteTime) — WinVerifyTrust is slow and this runs continuously.

**False positives:** Signature checks fail offline for certificates requiring OCSP/CRL fetch. Since the product forbids network egress by default, configure WinVerifyTrust with WTD_CACHE_ONLY_URL_RETRIEVAL and treat 'revocation unknown' as 'valid but unconfirmed' rather than 'invalid' — otherwise every system binary looks untrusted the moment the machine is offline.

### [critical] The escalation ladder — rung definitions and the gates that trigger each
Each rung is strictly more invasive and strictly less reversible than the last. Autonomy is permitted only on rungs whose effects Warden can fully undo without user data loss. The gates are deliberately conservative because the product's stated primary risk is false positives.

**How:** Rung 0 OBSERVE (score <50): baseline only, no action. Rung 1 SUSPEND (score 70-84): freeze threads, fully reversible. Rung 2 NET-BLOCK (score 70-84): firewall block, fully reversible. Rung 3 KILL TREE (score 85-94): destroys volatile state, irreversible for the process. Rung 4 QUARANTINE FILE (score 85-94): reversible via vault. Rung 5 REMOVE PERSISTENCE (score >=95): reversible only via undo record. Rung 6 LOCKDOWN: user-initiated or >=3 corroborated HIGH incidents in 60s. AUTONOMY GATE — a rung >=3 fires autonomously only if ALL hold: score >=85; corroborated by >=2 independent signal families (never a single rule); target passes all five protected-process checks; image path outside C:\Windows and outside every developer root; binary unsigned or signed by an untrusted publisher; the rate limiter has budget. Score 50-84 always routes to prompt-only.

**False positives:** The 2-independent-signal-family requirement is the main precision lever. A single high-confidence rule firing alone should never reach rung 3 — most real false positives are one over-tuned rule, not two unrelated ones agreeing.

### [critical] Rung 1 — thread suspension, and why suspension must precede kill
Suspension is the highest-value rung in the ladder and the one that makes the whole design safe. It stops exfiltration and encryption in-flight *immediately* — faster than the kill decision can be made — while preserving the entire address space for forensics. A kill destroys the evidence you need to prove the detection was correct, which means a killed false positive can never be fully explained or fully undone. Suspension is also the only destructive-feeling action that is 100% reversible, so it can be fired autonomously at a lower score than a kill. Crucially, the memory dump (rung 3 prerequisite) can only be taken from a frozen process without tearing.

**How:** Preferred: NtSuspendProcess(hProcess) / NtResumeProcess(hProcess) from ntdll.dll, requiring PROCESS_SUSPEND_RESUME (0x0800). Fallback if unavailable: CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD, 0), iterate Thread32First/Thread32Next filtering th32OwnerProcessID, then OpenThread(THREAD_SUSPEND_RESUME, false, tid) + SuspendThread. Record every suspended TID in the undo record — a partial suspend that is resumed by thread list rather than by record can leave orphaned suspend counts. Always pair with an auto-resume timer (default 10 minutes) so a suspend that is never adjudicated self-heals rather than leaving a frozen app.

**False positives:** Suspending a process holding a global lock (an installer mid-MSI, a database write, a Blender or Unreal render holding GPU resources) can hang unrelated apps. Never suspend a process whose image is msiexec.exe or TiWorker.exe, and surface a visible tray indicator naming every currently suspended process so a mysterious hang is never unexplained.

### [critical] Rung 3 — kill process tree, with PID-reuse defence and job-object atomicity
Naive parent-child tree walking is a genuine catastrophic-action vector: Windows recycles PIDs aggressively, and on this machine with ~36,000 PIDs in active use recycling is frequent. If a malicious process's PID is reused by a legitimate one between enumeration and termination, Warden kills an innocent process — potentially a Tier 0 one. Ordering also matters: killing the parent first lets a supervisor respawn its children.

**How:** Enumerate with CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0) reading th32ParentProcessID. VALIDATE every parent-child edge by comparing creation times from GetProcessTimes: a child's creation time MUST be later than its claimed parent's, otherwise the parent PID has been recycled and the edge is discarded. Then: suspend the entire validated tree first (rung 1), re-validate each PID's creation time immediately before terminating, and terminate leaves-to-root. PREFERRED ALTERNATIVE: at first detection call CreateJobObject + AssignProcessToJobObject on the root, then TerminateJobObject(hJob, 1) — atomic, immune to PID reuse and to respawn races. Windows 8+ supports nested jobs so assignment usually succeeds even if the process is already jobbed; fall back to the validated tree walk if AssignProcessToJobObject fails with ERROR_ACCESS_DENIED.

**False positives:** On this machine the process tree is enormous and legitimately deep — node.exe spawning cmd.exe spawning pwsh.exe is the normal shape of the user's toolchain. Cap tree depth and breadth: if a proposed kill tree exceeds 8 processes or crosses into a different session, refuse autonomy and prompt, since a tree that large is far more likely to be a dev toolchain than a RAT.

### [high] Rung 6 — full incident lockdown, with mandatory auto-expiry
Lockdown is the highest-blast-radius action and the one most likely to strand the user. It must be aggressive enough to matter but must never be able to permanently damage access to the machine. The auto-expiry is the structural safety property: a false lockdown triggered while the user is away self-heals instead of leaving a bricked desktop.

**How:** Effects: suspend all non-protected, non-allowlisted processes started within the incident window; add firewall blocks for every implicated image path and remote endpoint; freeze the implicated trees; capture a full snapshot of everything; display a modal with the evidence. HARD PROHIBITIONS: lockdown NEVER reboots, NEVER logs off, NEVER disables a network adapter, NEVER creates a global outbound block (the user needs the dashboard and may be on a remote session), NEVER touches Defender, NEVER modifies boot configuration. ALL lockdown effects carry a 15-minute TTL and are automatically and completely reverted unless the user explicitly confirms within that window. The revert path is the same undo-record machinery as every other rung.

**False positives:** Trigger is >=3 corroborated HIGH incidents in 60 seconds, which a single broken rule could easily produce across the ~22 node.exe processes. Require that the 3 incidents involve at least 2 distinct image paths, otherwise it is one rule misfiring on one program.

### [high] Quarantine vault — per-volume layout so moves stay atomic
A single vault on C: forces a cross-volume copy+delete for anything on D:/E:/F:, which is non-atomic (a crash mid-copy loses the file), slow for large files, and silently drops alternate data streams and the NTFS file ID. All four volumes on this machine are NTFS, so a same-volume rename is always available and is atomic, instantaneous, and preserves ADS, object IDs and hard links. Note C: has only 88.5 GB free while D: has 6699 GB — sizing matters too.

**How:** Primary vault: C:\ProgramData\Warden\Vault\ for control data, ledger, journal and manifests. Per-volume payload vaults created on demand at <VolumeRoot>\.warden-vault\ (e.g. D:\.warden-vault\), each with FILE_ATTRIBUTE_HIDDEN|SYSTEM|NOT_CONTENT_INDEXED. ACL each vault via DirectorySecurity: SetAccessRuleProtection(true, false) to kill inheritance, then grant only SYSTEM and BUILTIN\Administrators FullControl; add an explicit Deny for Everyone on FileSystemRights.ExecuteFile and Traverse. Identify the source volume with GetVolumePathNameW then GetVolumeNameForVolumeMountPointW to get the \\?\Volume{GUID}\ form, and record that GUID in the manifest so restore survives drive-letter reassignment. Enforce a configurable vault quota (default 5 GB, and never allow the vault to consume more than 25% of free space on its volume).

**False positives:** Vault directories at volume roots may themselves be flagged by other security tools as suspicious hidden system directories. Document the location prominently and never hide it from the dashboard.

### [critical] Quarantine — move mechanics and the locked-file escalation ladder
The file will very often be locked, because the thing that made it suspicious is running. This is precisely why quarantine sits at rung 4, after the kill at rung 3. Deletion is never a fallback at any point in this ladder.

**How:** Step 1 (same volume): MoveFileExW(src, dst, MOVEFILE_REPLACE_EXISTING|MOVEFILE_WRITE_THROUGH) — atomic rename, preserves everything. Step 2 (cross volume, only if per-volume vault creation failed): MoveFileExW with MOVEFILE_COPY_ALLOWED, then explicitly re-apply timestamps, attributes, ACLs and enumerate/copy ADS via FindFirstStreamW/FindNextStreamW. Step 3 (locked): identify holders with the Restart Manager — RmStartSession, RmRegisterResources(files), RmGetList — from rstrtmgr.dll; this is the documented in-box way and needs no driver. Present holders to the user or kill them per rung 3. Step 4 (still locked): open a handle with CreateFileW(path, DELETE|GENERIC_READ, FILE_SHARE_READ|FILE_SHARE_WRITE|FILE_SHARE_DELETE, ...) and rename via SetFileInformationByHandle(h, FileRenameInfo, ...) — handle-based rename succeeds in cases where the path-based one fails. Step 5 (last resort): MoveFileExW(src, dst, MOVEFILE_DELAY_UNTIL_REBOOT), which writes HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\PendingFileRenameOperations and REQUIRES ADMIN; mark the manifest restoreState='pending-reboot' and reconcile at next start.

**False positives:** Defender may quarantine the same file first, in which case the move fails with ERROR_FILE_NOT_FOUND (2). Check the Microsoft-Windows-Windows Defender/Operational log for event IDs 1116/1117 referencing the path and record the incident as 'already handled by Defender' rather than surfacing an error.

### [critical] Quarantine — neutralisation so the file cannot run and cannot be re-detected
Three separate goals: the file must not be executable by accident, on-disk AV must not fight Warden over the vault contents, and vault tampering must be detectable. An AES-GCM envelope achieves all three at once and — importantly — removes any need to add a Defender exclusion, which would itself be a security hole requiring admin and blocked by Tamper Protection anyway.

**How:** (1) Rename to {incidentId}.{seq}.wqz — no executable extension anywhere in the name. (2) Encrypt with AES-256-GCM (System.Security.Cryptography.AesGcm), fresh 12-byte nonce per file, 16-byte tag stored in the manifest. The GCM tag gives tamper-evidence for free. Key: 32 random bytes held in C:\ProgramData\Warden\Vault\vault.key, itself wrapped with ProtectedData.Protect(key, entropy, DataProtectionScope.LocalMachine). (3) ACL the vault file: FileSecurity with SetAccessRuleProtection(true, false), all ACEs removed, SYSTEM + Administrators FullControl added, plus an explicit Deny ACE for Everyone on FileSystemRights.ExecuteFile — NTFS Deny-Execute does gate CreateProcess. (4) Set FILE_ATTRIBUTE_HIDDEN|SYSTEM|NOT_CONTENT_INDEXED. (5) Read and record the Zone.Identifier ADS before stripping it. Do NOT use XOR: a static XOR key is trivially reversed, still leaves the payload recoverable by other malware, and provides no integrity guarantee.

**False positives:** Because the payload is encrypted, losing vault.key makes every quarantined file permanently unrecoverable. Back the wrapped key up alongside the manifests, warn the user explicitly in the dashboard, and offer an export-vault-key action so a machine rebuild does not destroy the user's own files.

### [critical] Quarantine — the manifest, written ahead of the move
The manifest is the sole record enabling byte-identical restore. It must be written and flushed BEFORE the file moves, otherwise a crash between move and record leaves an unattributable blob in the vault and a missing file the user cannot recover. Write-ahead is the same discipline a database uses and for the same reason.

**How:** One JSON file per action at C:\ProgramData\Warden\Vault\Manifests\{incidentId}\{actionId}.json, written with FileOptions.WriteThrough and flushed, state='pending', then updated to 'committed' after the move succeeds. Required fields: schemaVersion; incidentId; actionId; utcTimestamp; originalFullPath; originalVolumeGuid (\\?\Volume{GUID}\ form); originalFileId (FILE_ID_INFO via GetFileInformationByHandleEx(FileIdInfo)); sha256; sizeBytes; timestamps as raw FILETIME 100ns ticks for creation/lastWrite/lastAccess (NOT DateTime — DateTime round-trips lossily); fileAttributes (raw FILE_ATTRIBUTE_* DWORD); sddl from FileSecurity.GetSecurityDescriptorSddlForm(AccessControlSections.All) capturing owner, group, DACL and SACL; alternateDataStreams[] as {name, base64Content}; authenticode {status, signerSubject, thumbprint}; detection {reason, ruleIds, score, signalFamilies[]}; processContext {pid, creationTime, parentPid, parentCreationTime, commandLine, tokenSid, integrityLevel, sessionId, loadedModules[], networkEndpoints[]}; vaultPath; encryption {alg:'AES-256-GCM', nonce, tag, keyId}; restoreState; actorUser; wardenVersion; wasElevated. HMAC-SHA256 the whole manifest with a key derived from vault.key and store the MAC alongside.

**False positives:** Capturing Win32_Process.CommandLine for another user's process requires elevation; record commandLine as null with a captureFailed reason rather than omitting the field, so the absence is distinguishable from an empty command line.

### [critical] Quarantine — the restore path, and why ordering is non-negotiable
Restore is where 'reversible' is either true or a lie. The ordering below is mandatory because each later step is destroyed by an earlier one performed out of sequence: writing content updates LastWrite, so timestamps must come after content; setting ReadOnly or Hidden blocks subsequent writes, so attributes must come last; applying a restrictive DACL before writing streams locks Warden out of its own restore.

**How:** Exact order: (1) verify manifest HMAC; (2) AES-GCM decrypt and verify the tag; (3) verify SHA-256 of plaintext equals the recorded hash — this is what makes 'byte-identical' a checked guarantee rather than a claim; (4) resolve originalVolumeGuid to a current drive letter (handles reassignment); (5) if a file already exists at originalFullPath, do NOT overwrite — restore alongside as {name}.restored-{utc}{ext} and tell the user; (6) write content; (7) write each alternate data stream; (8) apply ACL via new FileSecurity() + SetSecurityDescriptorSddlForm(sddl, AccessControlSections.All) + File.SetAccessControl; (9) apply timestamps with SetFileTime(handle, &creation, &lastAccess, &lastWrite) using the raw FILETIMEs; (10) apply attributes with SetFileAttributesW. Re-hash the restored file and record the verification result in the ledger.

**False positives:** Restoring the OWNER and the SACL from the SDDL requires SeRestorePrivilege and SeSecurityPrivilege respectively — both admin-only. Unelevated restore must apply the DACL only, and must explicitly tell the user that owner and audit settings were not restored rather than silently reporting full success.

### [critical] BLOCKER: Controlled Folder Access is enabled and will block quarantine
MEASURED ON TARGET: Get-MpPreference reports EnableControlledFolderAccess=1 and Get-MpComputerStatus reports IsTamperProtected=True with RealTimeProtectionEnabled=True. CFA blocks untrusted applications from writing to and DELETING FROM Documents, Desktop, Pictures, Videos, Music and Favorites. A quarantine is a move, and the source side of a move is a delete — so quarantining anything from the user's Desktop or Documents will fail with ERROR_ACCESS_DENIED even when Warden is fully elevated. This is not a permissions bug to work around; it is Defender working correctly, and it will make quarantine appear randomly broken depending on where the file sits.

**How:** Detect at startup: read EnableControlledFolderAccess via Get-MpPreference (shelling to powershell.exe is acceptable here). Catch the specific failure at the move site and map ERROR_ACCESS_DENIED on a source under the six CFA-protected folders to a distinct, actionable error. Remediation is a GUIDED MANUAL STEP the user performs: Windows Security > Virus & threat protection > Ransomware protection > Manage ransomware protection > Allow an app through Controlled folder access > Add both Warden.exe and Warden.Broker.exe. Do NOT attempt Add-MpPreference -ControlledFolderAccessAllowedApplications automatically — it requires admin and is blocked outright by Tamper Protection on this machine. NEVER disable CFA. The vault itself is under C:\ProgramData, which is not CFA-protected, so the destination side is fine.

**False positives:** Do not present this as a Warden failure. The dashboard should show a one-time setup card explaining that Defender is protecting those folders and that allowlisting Warden is a deliberate user decision.

### [high] Persistence removal — registry value
The most common persistence class and the easiest to undo perfectly, provided the raw value bytes and the exact value kind are captured. The classic bug is capturing an expanded string: reading an REG_EXPAND_SZ value normally returns 'C:\Users\finla\...' where the stored literal was '%USERPROFILE%\...', so a naive undo writes the wrong data and silently changes behaviour.

**How:** Verified-present locations to monitor: HKCU\Software\Microsoft\Windows\CurrentVersion\Run (currently holds legitimate Steam, AMDNoiseSuppression, Opera GX Stable, MicrosoftEdgeAutoLaunch entries — baseline these), ...\RunOnce, HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run, ...\RunOnce, HKLM\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Run, HKCU\Software\Microsoft\Windows NT\CurrentVersion\Windows (Load/Run), HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon (Shell must equal 'explorer.exe', Userinit must equal 'C:\WINDOWS\system32\userinit.exe,' — both verified at baseline), HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options (Debugger values). UNDO RECORD, captured first: hive, full subkey path, value name, RegistryValueKind, and RAW bytes read with RegistryValueOptions.DoNotExpandEnvironmentNames, plus the WOW64 view used (KEY_WOW64_64KEY vs KEY_WOW64_32KEY) and the key's SDDL. REMOVE with RegDeleteValueW. UNDO with RegSetValueExW passing the identical kind and byte array. Never delete the parent key.

**False positives:** For Winlogon Shell and Userinit, prefer REPAIR (restore the known-good baseline value) over DELETE — deleting Userinit entirely prevents logon. Treat these two keys as repair-only, never delete.

### [high] Persistence removal — scheduled task
Scheduled tasks have a perfect built-in undo record: the task XML round-trips exactly through the COM API. The trap is credentials — a task registered with a stored password cannot be recreated without that password, so a delete-then-restore silently produces a task that will never run again.

**How:** COM Schedule.Service (ITaskService), verified connecting successfully on this machine with 14 root-folder tasks. Connect(), GetFolder(path), GetTask(name). UNDO RECORD: IRegisteredTask.Xml (the complete definition), the containing folder path, IRegisteredTask.Enabled, the SDDL from IRegisteredTask.GetSecurityDescriptor(OWNER|GROUP|DACL), and the principal's LogonType and UserId. If LogonType is TASK_LOGON_PASSWORD or TASK_LOGON_S4U, record that the task CANNOT be fully restored and require explicit user confirmation before removal. REVERSIBLE RUNG: set IRegisteredTask.Enabled = false — prefer this over deletion. DESTRUCTIVE: ITaskFolder.DeleteTask(name, 0). UNDO: ITaskFolder.RegisterTask(name, xml, TASK_CREATE(2), userId, password, logonType, sddl), then re-apply Enabled. Never touch the \Microsoft\Windows\ folder.

**False positives:** Legitimate updaters (GoogleUpdate, OneDrive, Overwolf, Gigabyte, Steam — all observed running on this machine) register tasks that launch signed binaries from user-writable AppData with obfuscated arguments. Baseline the task set on first run and only score tasks that appear afterwards.

### [high] Persistence removal — service
Services have the largest undo surface of any persistence class — a dozen configuration fields plus a registry subtree plus a security descriptor — and getting any of them wrong on restore produces a service that exists but misbehaves. Additionally, for svchost-hosted services the real payload path lives in the Parameters subkey (ServiceDll), not in the ImagePath, so capturing only the service config loses the payload reference entirely.

**How:** OpenSCManager(NULL, NULL, SC_MANAGER_ALL_ACCESS) then OpenService. CAPTURE with QueryServiceConfigW (ServiceType, StartType, ErrorControl, BinaryPathName exactly as stored including arguments, LoadOrderGroup, TagId, Dependencies, ServiceStartName) plus QueryServiceConfig2W for SERVICE_CONFIG_DESCRIPTION, DELAYED_AUTO_START_INFO, FAILURE_ACTIONS, FAILURE_ACTIONS_FLAG, REQUIRED_PRIVILEGES_INFO, SERVICE_SID_INFO, PREFERRED_NODE_INFO and TRIGGER_INFO, plus QueryServiceObjectSecurity for the SDDL. ALSO export the whole registry subtree HKLM\SYSTEM\CurrentControlSet\Services\<name> including the Parameters subkey. REVERSIBLE RUNG: ChangeServiceConfigW(..., SERVICE_DISABLED, ...) — always prefer this. DESTRUCTIVE: DeleteService (takes effect when the last handle closes; the service must be stopped first via ControlService SERVICE_CONTROL_STOP). UNDO: CreateServiceW with every captured field, restore the registry subtree, then SetServiceObjectSecurity. Requires admin throughout.

**False positives:** This machine runs many legitimate third-party services from non-Microsoft publishers: TeamViewer_Service, warp-svc, steamservice, GigabyteUpdateService, OverwolfUpdater, jhi_service, GooglePlayGamesServices, wslservice, vmcompute. None should be autonomously actioned. Restrict autonomy to services created within the incident window whose binary is unsigned.

### [medium] Persistence removal — startup folder shortcut
The simplest class, and it should reuse the quarantine machinery wholesale rather than getting its own deletion path. A .lnk is just a file, so quarantining it gives byte-identical restore for free — including the shortcut's link-tracker data, which a reconstruct-from-parsed-properties approach would silently lose.

**How:** Monitor C:\Users\finla\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup and C:\ProgramData\Microsoft\Windows\Start Menu\Programs\Startup (both verified present, both currently empty — a clean baseline). REMOVE by routing the .lnk through the standard quarantine path (MoveFileExW into the vault with a full manifest). UNDO is the standard restore path — no separate code. Additionally parse for DISPLAY ONLY via IShellLinkW + IPersistFile::Load to show the user TargetPath, Arguments, WorkingDirectory, IconLocation and ShowCmd in the incident UI, but never reconstruct the .lnk from these on restore.

**False positives:** Both startup folders are currently empty on this machine, so any new arrival is genuinely notable — but installers legitimately add shortcuts. Correlate the shortcut's creation with a recent installer execution before scoring it.

### [high] Persistence removal — WMI event subscription
The stealthiest persistence class and the one where removal ORDER is load-bearing. The subscription is three linked objects; deleting the filter or consumer first can leave a dangling binding, and recreating them in the wrong order fails because a binding cannot reference objects that do not yet exist. Deleting the binding first is also the single most valuable action, because it immediately breaks the trigger while leaving both halves intact and fully restorable.

**How:** Namespace root\subscription (verified: __EventFilter, __FilterToConsumerBinding, CommandLineEventConsumer and ActiveScriptEventConsumer classes all present; 1 filter and 1 binding currently exist — baseline these as legitimate). Also scan root\default and enumerate custom namespaces, since attackers relocate. UNDO RECORD: for all three objects capture the class name, the namespace, __PATH and __RELPATH, and every non-system property as a typed dictionary (Query and QueryLanguage for __EventFilter; CommandLineTemplate/ExecutablePath or ScriptText/ScriptingEngine for the consumer; Filter and Consumer references for the binding). REMOVAL ORDER: __FilterToConsumerBinding first, then the consumer, then the __EventFilter. RECREATE ORDER: filter, then consumer, then binding. API: CimSession.DeleteInstance(namespace, instance) and CimSession.CreateInstance, or System.Management.ManagementObject.Delete()/Put(). Requires admin.

**False positives:** The one existing filter and binding on this machine are almost certainly legitimate (SCM or vendor telemetry). Snapshot the WMI subscription set on first run and treat the baseline as permanently allowlisted unless its properties change.

### [critical] Network containment — use the firewall COM API, and never bind a rule to a Windows path
Decision: INetFwPolicy2 via HNetCfg.FwPolicy2, verified working on this machine (639 existing rules enumerable, Grouping property readable and writable). WFP (fwpuclnt.dll, verified present) can filter per-PID and supports volatile filters that vanish on session close, but the P/Invoke surface is large and a mistake in a persistent sublayer can black-hole all networking with no UI to undo it — rejected as default, kept as a documented opt-in. netsh advfirewall gives no structured errors and no durable rule identity; New-NetFirewallRule costs a PowerShell spawn per rule. THE CRITICAL FOOT-GUN: firewall rules are PATH-based, not PID-based. An ApplicationName rule on a LOLBin such as powershell.exe, rundll32.exe or svchost.exe blocks that image for the entire system and will break Windows Update, the Store, and the user's own tooling.

**How:** HARD GUARD, enforced inside the broker: refuse to create any ApplicationName rule whose path resolves under C:\Windows. For those targets, contain by remote endpoint or by suspension instead. Per-process block: create TWO INetFwRule objects (NET_FW_RULE_DIR_IN=1 and NET_FW_RULE_DIR_OUT=2), each with ApplicationName=<canonical full path>, Action=NET_FW_ACTION_BLOCK(0), Protocol=256(ANY), Profiles=0x7FFFFFFF(ALL), Enabled=true. Per-endpoint block: omit ApplicationName, set RemoteAddresses='203.0.113.5' or CIDR, RemotePorts, Protocol=6(TCP). Add via fwPolicy.Rules.Add(rule). Requires admin. Use the local store, never the GPO store.

**False positives:** Blocking an image path blocks every instance including future legitimate ones. Always set a TTL and always show the user which image paths are currently blocked, since a forgotten block on a common binary produces baffling connectivity failures weeks later.

### [high] Network containment — rule tagging and the four-layer orphan-free guarantee
Orphaned block rules are a silent, long-lived way to break a machine: the user uninstalls Warden, and months later some application mysteriously cannot reach the network. Because the firewall store outlives the process, no single in-process mechanism is sufficient — the guarantee has to be layered so that a crash, a force-delete, and a clean uninstall are each independently covered.

**How:** TAGGING (verified writable): Name='Warden Block {incidentId} {in|out} {seq}'; Grouping='Warden Containment' — a LITERAL string, never an '@dll,-123' indirect resource string, which only resolves for registered resources and renders as garbage otherwise; Description=a JSON blob carrying {incidentId, createdUtc, ttlUtc, reason, wardenVersion}, which is the durable queryable metadata channel and survives reboot. FIND OWN RULES: iterate fwPolicy.Rules and match Grouping == 'Warden Containment'. FOUR LAYERS: (1) every rule carries ttlUtc and a reaper runs at startup and hourly, deleting expired rules; (2) a write-ahead journal at C:\ProgramData\Warden\Journal\firewall.jsonl is appended and flushed BEFORE Rules.Add, so a crash between add and record still leaves a trace; (3) on every start, reconcile the enumerated Warden-grouped rules against the live incident set and delete any with no matching open incident; (4) the uninstaller runs the same sweep AND registers a RunOnce entry so the sweep fires even if the app directory is force-deleted. Document the manual fallback for the user: Get-NetFirewallRule -Group 'Warden Containment' | Remove-NetFirewallRule.

**False positives:** Other software also writes to the Grouping field (this machine has rules grouped as 'Claude' and as raw GUIDs). Match on the exact literal 'Warden Containment' and additionally validate that Description parses as Warden JSON before deleting, so Warden never removes another product's rules.

### [high] Pre-action forensic snapshot and process dump
Nothing destructive fires until the evidence is on disk. This serves two purposes: it lets the user understand and contest a false positive after the fact, and it makes the detection reviewable so scoring bugs get found. The dump specifically must be taken while the process is SUSPENDED (rung 1) — a dump of a running process tears, giving an inconsistent snapshot. This is the second independent reason suspension precedes kill.

**How:** Snapshot to C:\ProgramData\Warden\Incidents\{id}\snapshot.json, hash-chained to the ledger. Contents: full process table (pid, creationTime, ppid, parentCreationTime, image path via QueryFullProcessImageNameW, command line, token SID, integrity level, sessionId, working set, CPU time); loaded modules via Module32FirstW/Module32NextW; open handles via NtQuerySystemInformation(SystemExtendedHandleInformation); network state via GetExtendedTcpTable(TCP_TABLE_OWNER_PID_ALL) and GetExtendedUdpTable(UDP_TABLE_OWNER_PID); the target file's SHA-256, Authenticode result and full manifest fields; relevant registry/task/service state; and recent slices of Security, Microsoft-Windows-Windows Defender/Operational and Sysmon logs if present. DUMP: MiniDumpWriteDump (dbghelp.dll) with MiniDumpWithFullMemory, needing PROCESS_QUERY_INFORMATION|PROCESS_VM_READ. Skip if working set > 2 GB (configurable). Write dumps to the volume with the most free space — default D:\ (6699 GB free) rather than C:\ (88.5 GB free).

**False positives:** A full-memory dump of a browser or game process can be several GB and may contain the user's credentials, session tokens and private data. Store dumps with the same restrictive ACL as the vault, never transmit them (no network egress by default), and offer a retention policy that deletes them after N days.

### [critical] System Restore is NOT available on this machine — probe, never presume
MEASURED ON TARGET: querying root\default SystemRestore returned ZERO restore points; VSS is Stopped/Manual, swprv is Stopped/Manual, and sppsvc is Stopped. SystemRestoreConfig exists with DiskPercent=15 and RPSessionInterval=1, but no points have been created. So the design's assumed OS-level rollback safety net does not currently exist, and calling SRSetRestorePoint would either fail or silently no-op — producing a false sense of safety before a registry or service modification.

**How:** At startup probe with Get-CimInstance -Namespace root/default -ClassName SystemRestore (count of points) and check the VSS service state. If SR is unavailable: do NOT silently continue. Either offer the user a one-click Enable-ComputerRestore -Drive 'C:\' (requires admin) or downgrade the safety posture and REQUIRE explicit confirmation for every rung-5 persistence removal, on the grounds that no OS-level rollback exists. When SR is available, create a point before rung 5 with SRSetRestorePoint (srclient.dll) or Checkpoint-Computer -Description 'Warden {incidentId}' -RestorePointType MODIFY_SETTINGS. Note Windows throttles to one point per 24h via HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\SystemRestore\SystemRestorePointCreationFrequency; only change it with consent. Also note vssadmin requires elevation (verified: refused unelevated).

**False positives:** System Restore does NOT protect user data files and does not roll back quarantine. Never present it to the user as the undo mechanism for file actions — the vault is the only file-level undo. SR covers registry, services and tasks only.

### [critical] Dry-run mode, the action ledger, and undo-last-action
Given that this machine concurrently runs ~28 claude.exe, ~23 cmd.exe, ~22 node.exe and ~30 conhost.exe — a topology behaviourally identical to a RAT with a supervisor and many injected children — shipping with autonomy enabled would produce a false-positive storm on day one. The shakedown period lets the user see exactly what Warden WOULD have done against their real workload before it is trusted to act.

**How:** Every action type implements IReversibleAction with a two-phase contract: ActionPlan Plan() returning {target, rung, predicted side effects, and the fully materialised UndoRecord}, and Execute(ActionPlan). ENFORCE AT THE TYPE LEVEL that Execute cannot be called with a plan whose UndoRecord is null — no undo record, no action, checked by construction rather than by convention. Dry-run runs Plan() only and renders both the plan and the undo record that would have been captured. SHIP WITH DRY-RUN ON BY DEFAULT for the first 7 days, then prompt the user to review the would-have-done list before enabling autonomy. LEDGER: append-only hash-chained JSONL at C:\ProgramData\Warden\Ledger\ledger.jsonl, each entry {actionId, incidentId, rung, target, undoRecord, utc, result, prevHash}. UNDO: tray menu exposes 'Undo last action' for the newest entry; the dashboard exposes per-entry undo across the full history. Every undo is itself ledgered as a new entry, so the log is never rewritten.

**False positives:** The shakedown report is the product's most important artifact. Present it as 'here is what would have happened' with per-item Approve/Never-flag-this buttons, so the user's dev toolchain gets allowlisted through normal use rather than through a settings screen.

### [critical] Autonomy rate limiter and the fail-safe into ask-only mode
A hard cap converts an unbounded failure (a bad rule cascading across dozens of processes) into a bounded one. The counter must be persisted, because otherwise a crash-restart loop resets the budget and the cap becomes meaningless — which is exactly the scenario where it matters most.

**How:** Persisted counters at C:\ProgramData\Warden\State\autonomy.json, updated transactionally with each action. Limits: max 3 autonomous rung->=3 actions per 10 minutes; max 10 per 24 hours; max 1 autonomous rung-5 persistence removal per hour. ADDITIONAL TRIP CONDITIONS, any of which immediately disarms autonomy: more than 2 distinct image paths targeted within 60 seconds (indicates a bad rule, not an outbreak); any action whose target resolves under C:\Windows; any action targeting a binary signed by a publisher already in the user's trusted set; Warden crashing twice within 5 minutes; the ledger failing to write. ON TRIP: enter ASK-ONLY mode — all autonomy disabled, tray icon turns amber, dashboard shows a banner naming the specific trip condition and listing the actions that caused it. Re-arming requires an explicit user click and is NEVER automatic or timer-based. FAIL-SAFE DIRECTION: on any internal exception, any ambiguity, any missing undo record, any failed protected-set check, the answer is always 'do not act'.

**False positives:** The limiter must never block the USER's own manually requested actions — it caps autonomy only. A user clicking 'quarantine this' should always work regardless of counter state.

### [critical] Admin elevation — split broker process, not a requireAdministrator manifest
Shipping requireAdministrator is wrong for three reasons: a tray app that starts with Windows cannot auto-start elevated without a UAC prompt every boot; an always-elevated always-resident process is itself a high-value target; and an always-elevated app that makes mistakes has maximum blast radius, contradicting the entire safety thesis. The split model also delivers the design's most important structural property — the elevated component independently re-validates every protected-set rule, so a scoring bug in the unelevated process cannot produce a catastrophic elevated action.

**How:** Warden.exe: manifest requestedExecutionLevel='asInvoker' with autoElevate false, runs at medium IL, auto-starts via HKCU Run. Handles all observation, scoring, and everything that works unelevated (suspend/kill own-user processes, HKCU registry, user startup folder, user-scope tasks, quarantine of user-writable files). Warden.Broker.exe: separate binary, manifest requestedExecutionLevel='requireAdministrator', launched on demand via ProcessStartInfo{UseShellExecute=true, Verb='runas'}, exits after 60s idle, never resident. IPC over a named pipe created BY THE BROKER at \\.\pipe\Warden-Broker-{sessionGuid} with a PipeSecurity DACL granting only the launching user's SID; the tray authenticates with a nonce passed on the command line and the broker validates with NamedPipeServerStream.GetImpersonationUserName(). The broker exposes a CLOSED, TYPED VERB SET only — SuspendPid, KillTree, QuarantineFile, RestoreFile, RemoveRegValue, DisableTask, DeleteTask, DisableService, AddFirewallBlock, RemoveFirewallBlock, CreateRestorePoint — never arbitrary paths or commands, and EVERY verb re-runs the full protected-set validation internally.

**False positives:** Genuinely admin-only operations: killing/suspending other-user or SYSTEM processes (SeDebugPrivilege), reading other users' Win32_Process.CommandLine, MiniDumpWriteDump on other-user processes, all HKLM writes, service create/delete/config, firewall rule add/delete, WFP filters, root-folder scheduled tasks, MOVEFILE_DELAY_UNTIL_REBOOT, root\subscription WMI writes, System Restore point creation, restoring file owner and SACL, and reading Defender exclusions (verified: returned 'N/A: Must be an administrator to view exclusions').

### [high] Graceful unelevated behaviour and the capability map
Warden will spend most of its life unelevated, so 'needs admin' must be a first-class, visible state rather than a runtime surprise. Silent downgrade is the worst outcome: the user believes a threat was contained when it was not.

**How:** At startup build a CapabilityMap by probing rather than assuming: WindowsPrincipal.IsInRole(WindowsBuiltInRole.Administrator) (verified False in this session); can OpenSCManager succeed with SC_MANAGER_ALL_ACCESS; can a test firewall rule be added and removed; is System Restore enabled; is Controlled Folder Access on; are Defender exclusions readable. Surface the map in the dashboard. Per finding, label each remediation as 'Ready' or 'Needs admin'. If the chosen rung requires elevation and the user declines UAC, record the action as Declined, LEAVE THE INCIDENT OPEN, and fall back to the highest reversible rung achievable unelevated (usually suspend plus a user-scope block) while stating plainly what was not done. Never retry UAC in a loop — one prompt per explicit user gesture. Batch elevated work: if an incident needs three admin operations, request elevation once and send all three verbs over the one broker session.

**False positives:** Do not gate detection on elevation. Warden should still observe, score and report fully when unelevated; only the response ladder is constrained.

Only Warden's own denylist prevents this, which is why the broker must re-validate independently.
- PID reuse is a live catastrophic-action vector. Between enumerating a process tree and terminating it, a PID can be recycled onto an unrelated process, potentially a Tier 0 one. Every parent-child edge and every pre-termination check must be validated against GetProcessTimes creation time, or a job object used instead.
- MEASURED: this machine runs roughly 28 claude.exe, 23 cmd.exe, 22 node.exe, 30 conhost.exe and 5 pwsh.exe concurrently, with ancestry chains like pwsh -> claude -> claude -> sihost. A block on powershell.exe, rundll32.exe or svchost.exe would break Windows Update, the Store and the user's own toolchain, and would be extremely hard to diagnose weeks later. The closed verb set and per-verb protected-set re-validation are load-bearing security controls, not code hygiene.
- Restore is not truly byte-identical without elevation. Reapplying the owner requires SeRestorePrivilege and the SACL requires SeSecurityPrivilege, so an unelevated restore silently produces a file with different ownership and no audit settings unless this is explicitly surfaced to the user.

- WFP persistent filters, if adopted later as the opt-in hard-block path, can black-hole all networking with no user-facing UI to undo them. Only volatile (dynamic) filters tied to a session should ever be considered, and never as the default.
- Suspending a process that holds a global lock (msiexec mid-install, TiWorker during servicing, a Blender or Unreal render holding GPU resources) can hang unrelated applications with no visible cause. The auto-resume timer and a visible list of suspended processes are required mitigations, not niceties.

## Implementation notes
ORDERING CONSTRAINTS THAT ARE NOT NEGOTIABLE.

Restore ordering: content -> alternate data streams -> ACL -> timestamps -> attributes. Each earlier step destroys a later one if reordered: writing content updates LastWrite, so timestamps must follow; setting Hidden or ReadOnly blocks writes, so attributes must be last; applying a restrictive DACL before writing streams locks Warden out of its own restore.

WMI subscription ordering: remove __FilterToConsumerBinding first, then the consumer, then __EventFilter. Recreate in exactly the reverse order — a binding cannot reference objects that do not yet exist. Deleting the binding first is also the single most valuable action because it breaks the trigger while leaving both halves fully restorable.

Kill-tree ordering: suspend the entire validated tree first, re-validate every PID's creation time immediately before terminating, then terminate leaves-to-root so a supervisor parent cannot respawn children.

Write-ahead ordering: the quarantine manifest and the firewall journal entry must be written and flushed to disk BEFORE the corresponding mutation, then updated to 'committed' after. A crash between mutation and record leaves an unattributable blob in the vault and a file the user cannot recover.

Escalation ordering: suspension must precede kill for two independent reasons — it preserves the address space for the forensic dump (a dump of a running process tears), and it is the only fully reversible way to stop exfiltration in-flight.

API QUIRKS THAT WILL BITE.

Registry: read values with RegistryValueOptions.DoNotExpandEnvironmentNames. A normal read of an REG_EXPAND_SZ returns the expanded path, so a naive undo writes 'C:\Users\finla\...' where the literal was '%USERPROFILE%\...'. Capture the raw bytes and the exact RegistryValueKind, and record which WOW64 view (KEY_WOW64_64KEY vs KEY_WOW64_32KEY) was used.

Timestamps: store as raw FILETIME 100-nanosecond ticks, never as DateTime. DateTime round-trips lossily and byte-identical restore is a checked guarantee in this design, verified by re-hashing after restore.

Path canonicalisation: always resolve with GetFinalPathNameByHandleW(VOLUME_NAME_DOS) before any denylist comparison. A raw string compare is bypassable via 8.3 short names, junctions, symlinks and \\?\ prefixes. Protection must require name-in-denylist AND path-under-System32 AND valid Microsoft signature — a dropper named csrss.exe in %TEMP% must not inherit protection.

Signatures: reject 'Microsoft Windows Third Party Component CA' as a system-trust root; it cross-signs third-party code including drivers used in BYOVD attacks. Accept only 'Microsoft Windows Production PCA 2011' and siblings. Verified live: svchost.exe returns Subject 'CN=Microsoft Windows, O=Microsoft Corporation' with that issuer. Because network egress is off by default, configure WinVerifyTrust with WTD_CACHE_ONLY_URL_RETRIEVAL and treat 'revocation unknown' as valid-but-unconfirmed, otherwise every system binary looks untrusted when offline. Cache by (path, SHA-256, lastWriteTime).

Firewall Grouping: use a literal string 'Warden Containment', never an '@dll,-123' indirect resource string — those only resolve for registered resources. Other software already writes this field on this machine (rules grouped as 'Claude' and as bare GUIDs), so also validate that Description parses as Warden JSON before deleting any rule.

Volume identity: record the \\?\Volume{GUID}\ form via GetVolumePathNameW + GetVolumeNameForVolumeMountPointW so restore survives drive-letter reassignment. All four volumes here are NTFS, so a same-volume rename is always available.

ADMIN REQUIREMENTS. Needing elevation: killing or suspending other-user/SYSTEM processes (SeDebugPrivilege), reading other users' Win32_Process.CommandLine, MiniDumpWriteDump on other-user processes, every HKLM write, service create/delete/config, firewall rule add/delete, WFP filters, root-folder scheduled tasks, MOVEFILE_DELAY_UNTIL_REBOOT, root\subscription writes, System Restore point creation, restoring file owner (SeRestorePrivilege) and SACL (SeSecurityPrivilege), and reading Defender exclusions. Batch these: one UAC prompt per incident, all verbs over a single broker session, never a retry loop.

TYPE-LEVEL ENFORCEMENT. Make IReversibleAction.Execute impossible to call with a null UndoRecord — enforce by construction rather than by convention, so 'no undo record, no action' is a compile-time property. This is the single cheapest structural guarantee in the design.

BUILD AND SIZING. net10.0-windows with UseWPF and UseWindowsForms, zero NuGet packages: everything above is in-box .NET 10 plus P/Invoke to kernel32, ntdll, advapi32, wintrust, dbghelp, rstrtmgr and iphlpapi, plus COM interop to HNetCfg.FwPolicy2 and Schedule.Service, plus occasional shelling to powershell.exe for Get-MpPreference and Checkpoint-Computer. Write dumps to D:\ (6699 GB free) rather than C:\ (88.5 GB free); cap the vault at 5 GB and never let it exceed 25% of free space on its volume.

SHIP CONFIGURATION. Dry-run on by default for 7 days. The shakedown report — 'here is what Warden would have done' with per-item Approve and Never-flag-this controls — is the most important artifact the product produces, because it allowlists the user's Unreal, Blender, cargo, node and rooted-BlueStacks toolchain through normal use rather than through a settings screen.

  - **Fix:** Every process-addressed verb carries (PID, creation FILETIME) and the broker re-reads GetProcessTimes and refuses on mismatch. Every file-addressed verb carries the canonical path plus the SHA-256 and the FILE_ID_INFO, and the broker re-verifies before moving.

- **Claim:** 'ENFORCE AT THE TYPE LEVEL that Execute cannot be called with a plan whose UndoRecord is null — no undo record, no action, checked by construction' and 'every destructive action must produce a typed undo record *before* it executes or it is refused at the type level'
  - **Why wrong:** The invariant does not hold for the single most destructive action in the system. KILL TREE has no undo record — the spec says so itself ('destroys volatile state, irreversible for the process'). So either KillTree does not implement IReversibleAction, in which case the type-level guarantee explicitly does not cover the action that most needs covering, or it supplies a placeholder record that satisfies the compiler and the guarantee is decorative. Either way the summary's invariant (1) is overclaimed. Lockdown's mass-suspend has the same problem in a weaker form: its undo record is a list of TIDs held in memory.
  - **Fix:** Split the type hierarchy honestly: IReversibleAction<TUndo> for suspend / net-block / quarantine / persistence-removal, and a separate IIrreversibleAction that cannot be constructed at all without (a) a completed forensic snapshot on disk, (b) a completed suspend of the same target, and (c) an explicit AutonomyGrant token minted by the gate. Then the compile-time property is true as stated for the reversible set, and the irreversible set has its own, stronger, differently-shaped precondition.
- **Claim:** 'ACL each vault via DirectorySecurity: ... add an explicit Deny for Everyone on FileSystemRights.ExecuteFile and Traverse' / 'NTFS Deny-Execute does gate CreateProcess'
  - **Why wrong:** On a directory, FileSystemRights.ExecuteFile and FileSystemRights.Traverse are the same access bit (0x20) — the enum names differ only by context. So this is one ACE, not two, and what it denies on a directory is traverse. In practice it is a no-op, because SeChangeNotifyPrivilege ('Bypass traverse checking') is granted to Everyone by default; and in the environment where it is not a no-op (that privilege removed by policy) it locks Warden's own broker out of reaching vault files by path. The deny-execute claim is true, but only for an ACE on the *file*, and it is redundant once the payload is an AES-GCM blob that is not a valid PE image.
  - **Fix:** Put the Deny-Everyone-ExecuteFile ACE on each vault file, not on the vault directory. Drop the Traverse deny entirely. Keep the encryption as the actual neutralisation, which it already is.
- **Claim:** 'SetAccessRuleProtection(true, false) to kill inheritance, then grant only SYSTEM and BUILTIN\Administrators FullControl'
  - **Why wrong:** Incomplete against the stated threat model. A directory created by the medium-IL Warden process is owned by the user account, and an owner retains implicit READ_CONTROL and WRITE_DAC regardless of the DACL. Same-user malware — the adversary this product exists to stop — can therefore re-grant itself full control of the vault, the ledger and vault.key at will. Because vault.key is DPAPI LocalMachine-scoped, that adversary can also unwrap it and forge the manifest HMAC; and because the ledger's hash chain is unkeyed and entirely local, it can rewrite the ledger and recompute the chain. The 'append-only hash-chained' and 'tamper-evident' properties do not hold against the adversary they are specified for.
  - **Fix:** Create C:\ProgramData\Warden and its subtree from the elevated broker at install time, set the owner to BUILTIN\Administrators, and grant the interactive user read-only on the ledger. - **Claim:** 'treat DriverStore\FileRepository as System32-equivalent for trust purposes' alongside 'EXPLICITLY REJECT Microsoft Windows Third Party Component CA as a system-trust root'
  - **Why wrong:** These two rules contradict each other: DriverStore\FileRepository is precisely where third-party vendor binaries signed under that rejected CA live (the spec's own examples, amdfendrsr.exe and atiesrxx.exe, are AMD's). Granting a whole directory tree System32-equivalent trust also replaces a signature check with a path check, which is the exact error the spec correctly warns against for %TEMP%\svchost.exe.
  - **Fix:** Never grant trust by tree. Verify the signature of the specific file; a valid signature chaining to a pinned Microsoft root grants system trust, a valid signature under the Third Party Component CA grants 'signed by a known vendor' (enough to bar autonomy, not enough to grant Tier 0 protection), and everything else is untrusted. - **Claim:** 'Require Status == Valid AND SignerCertificate.Subject contains O=Microsoft Corporation AND the chain's issuing CA is one of Microsoft Windows Production PCA 2011...'
  - **Why wrong:** Subject and issuer distinguished names are attacker-controlled strings. Anyone who can add a certificate to the machine's Trusted Root store (admin, or a corporate/AV TLS-inspection root the user already has) can mint a cert with subject 'CN=Microsoft Windows, O=Microsoft Corporation' issued by 'CN=Microsoft Windows Production PCA 2011' that chains to their root, and WinVerifyTrust will return Valid. String matching on names is not identity.
  - **Fix:** Pin thumbprints, not names: after the chain builds successfully, assert that the chain's root element thumbprint equals a hard-coded Microsoft Root Certificate Authority 2010/2011 thumbprint. Keep the name checks only as a fast pre-filter.
- **Claim:** 'offer the user a one-click Enable-ComputerRestore -Drive C:\' with 'SystemRestoreConfig exists with DiskPercent=15'
  - **Why wrong:** Acting on that without changing the quota is a disk-exhaustion hazard. DiskPercent applies to volume size, not free space: 15% of C:'s 930 GB is roughly 140 GB, and C: currently has 86.6 GB free (I re-measured; the spec's 88.5 GB is already stale). Shadow storage will grow until the volume is effectively full, on the boot drive, on a machine whose owner builds Unreal projects.
  - **Fix:** Set an explicit cap before enabling — vssadmin resize shadowstorage /For=C: /On=C: /MaxSize=10GB (or Set-CimInstance on Win32_ShadowStorage) — and show the user the number it will consume before the one-click action, not after. Also verify Checkpoint-Computer/Enable-ComputerRestore are reachable from whichever host you shell to: I confirmed both exist in PowerShell 7.6.5 and 5.1 on this machine, so the spec is fine there, but pin the host explicitly rather than relying on it.
- **Claim:** 'Skip if working set > 2 GB (configurable)' as the guard on MiniDumpWithFullMemory
  - **Why wrong:** Working set does not bound a full-memory dump. MiniDumpWithFullMemory writes all committed and mapped readable regions; a process can hold tens of GB of private commit with a modest working set — Unreal Editor, a Blender scene, or a Chromium browser after paging pressure all do exactly that. The guard will pass and then write a dump far larger than intended.
  - **Fix:** Query the actual number: GetProcessMemoryInfo (PROCESS_MEMORY_COUNTERS_EX.PrivateUsage) plus a VirtualQueryEx walk summing committed readable regions, and cap on that. Also check free space on the target volume before starting, and prefer MiniDumpWithPrivateReadWriteMemory + MiniDumpWithIndirectlyReferencedMemory over full memory for a first-pass dump.
- **Claim:** 'open handles via NtQuerySystemInformation(SystemExtendedHandleInformation)' in the pre-action snapshot
  - **Why wrong:** Resolving handle names from that table is a known hang: NtQueryObject(ObjectNameInformation) on a handle to a synchronous named pipe with no waiting client blocks indefinitely in the kernel and cannot be cancelled. Doing this inline in the pre-action snapshot means a hostile (or merely unlucky) process can deadlock the containment path at exactly the moment it matters. On this machine, with dozens of conhost/pwsh/node processes holding pipe handles, hitting one is likely rather than exotic.
  - **Fix:** Do name resolution on a sacrificial worker thread with a hard timeout per handle, abandoning the thread (not the process) on timeout; or skip name resolution for handles whose type is File/NamedPipe and record type+access only. Never let snapshot collection block the response path — snapshot on a timeout budget and record what was collected.
- **Claim:** 'network state via GetExtendedTcpTable(TCP_TABLE_OWNER_PID_ALL) and GetExtendedUdpTable(UDP_TABLE_OWNER_PID)'
  - **Why wrong:** No address family is specified and the default reading is AF_INET only. Every IPv6 connection — which on Windows 11 with a modern ISP or any Teredo/link-local path is a large share of real traffic — is invisible in the forensic snapshot and therefore in any endpoint-based containment derived from it.
  - **Fix:** Call each table twice, AF_INET (2) and AF_INET6 (23), with TCP_TABLE_OWNER_PID_ALL / UDP_TABLE_OWNER_PID and merge. Endpoint firewall rules must likewise be created for both families.

### False-positive risks
- The catalog-signature defect (correction 1) is also the worst false-positive generator in the design: every System32 binary reads as unsigned, which satisfies the autonomy gate's 'binary unsigned or signed by an untrusted publisher' promoting condition. The gate's remaining guard against acting on a system binary is then only the static name+path denylist — whose path half is unobtainable unelevated (correction 2). Two of the three protected-set legs fail at once, and they fail in the direction of acting.
- Developer-root auto-detection by marker files is far too broad and creates a real detection hole. node_modules\, package.json and .git exist inside %LOCALAPPDATA%\Programs (VS Code, Discord, Slack and every other Electron app ship them), inside %APPDATA%, and inside npm/pnpm caches. Promoting any directory containing those markers to 'permanently ineligible for autonomous action' effectively allowlists the single most common infostealer drop location on a Windows machine. bin\Debug\, obj\, target\debug\ and Intermediate\ are directory names, not marker files, and will match enormous swaths of %USERPROFILE%.
- The kill-tree guard 'refuse autonomy if the proposed tree exceeds 8 processes' makes rung 3 autonomy dead on this machine rather than safe: the user's ordinary pwsh -> claude -> claude -> node -> cmd -> conhost chains routinely exceed 8, so the gate fires on essentially every tree, malicious or not. It is either a useless number or a disguised admission that tree-kill autonomy should not ship at all. Say which.
- The lockdown trigger guard ('>=3 corroborated HIGH incidents in 60s involving at least 2 distinct image paths') does not filter what it claims to. A single build step on this machine produces node.exe, cmd.exe and conhost.exe — three distinct image paths, one cause. The guard needs to require distinct *parent lineages* or distinct signal families, not distinct image names.
- Suspension's never-suspend list contains only msiexec.exe and TiWorker.exe. On this specific machine it must also exclude vmwp.exe / vmcompute.exe / vmms.exe (suspending a Hyper-V worker can corrupt guest state), wslservice.exe and the WSL VM, Docker Desktop, and HD-Player.exe / BstkSVC.exe — suspending a rooted BlueStacks Android VM desynchronises its clock and can corrupt its disk image. Add any process holding a VSS writer role during a backup.
- Rung 6 lockdown 'suspend all non-protected, non-allowlisted processes started within the incident window' with a 15-minute TTL, fired while a dotnet build, an Unreal cook, or a cargo build is running, freezes compiler and linker processes mid-write. Partial object files and a corrupted Unreal DDC are the likely outcome, and 'it self-heals in 15 minutes' does not undo a half-written .obj.
- Persistence baselining assumes the legitimate set is static. It is not: Steam and Opera GX rewrite their HKCU Run values on update, and GoogleUpdate / Overwolf / Gigabyte re-register their scheduled tasks on update. 'Only score tasks that appear afterwards' and 'baseline as permanently allowlisted unless its properties change' both fire on every routine update of software the user already trusts. Key the baseline on (publisher signature, target path) rather than on exact value bytes, and re-baseline silently when the signature is unchanged.
- A firewall ApplicationName block is a path block, and a developer's output path is stable across rebuilds. Blocking D:\My projects\...\bin\Debug\Game.exe once blocks every future build of that project from the same path, weeks later, with no visible cause. The spec's TTL mitigates this; the dev-root ban should extend explicitly to firewall rules, not just to kill/quarantine.
- Warden's own behaviour is the composite signature of an infostealer plus ransomware: opening handles to every process, reading process memory, MiniDumpWriteDump on user applications, and mass rename-encrypt-delete of files out of the user's Desktop and Documents. Defender real-time protection and behaviour monitoring are on with Tamper Protection enabled. The most likely first false positive on this machine is Defender quarantining Warden.

### Safety objections
- Protected-set resolution lives in the wrong process. The scorer runs unelevated, and unelevated it cannot obtain a handle, a path, a protection level or a critical flag for any Tier 0 process (re-verified: err 5 for System, Registry, Secure System, csrss, wininit, services, lsass, dwm, svchost, MsMpEng; Get-Process.Path and Win32_Process.ExecutablePath both empty for csrss). The design's compensating control is 'the broker independently re-validates', but the broker only receives what the verb carries — a PID. Protected-set evaluation must be performed by the broker from first principles on its own handle, not re-checked against the tray's conclusions.
- svchost-hosted malicious services have no response path at all. Tier 0 says never act on svchost by image, only ever stop the specific hosted service. The service denylist then refuses to touch any service whose ImagePath resolves under System32 with a valid Microsoft signature — which is every svchost-hosted service by construction, since the ImagePath is svchost.exe. The spec correctly identifies that the payload lives in the Parameters\ServiceDll of such services, and then leaves them unactionable. Either add an explicit carve-out keyed on the ServiceDll's signature and path rather than the ImagePath's, or state plainly that this class escalates to the user only.
- Allowlisting Warden.exe and Warden.Broker.exe through Controlled Folder Access grants ransomware-protection bypass to a path. The binaries are self-built and unsigned (no code-signing certificate anywhere in the stack), and the install directory ACL is never specified. If that directory is user-writable, anything running as the user can overwrite Warden.exe and inherit CFA bypass on Desktop and Documents — the design would have manufactured the exact ransomware primitive it exists to prevent. Make the install directory admin-write-only, verified by the broker, as a hard precondition before the CFA setup card is even offered.
- Suspend state is the only reversible action with no durable undo. Firewall rules get a write-ahead journal plus a reaper plus a startup reconciliation; quarantine gets a write-ahead manifest; suspension gets an in-memory 10-minute timer. If Warden crashes or is killed — which is the first thing a RAT does, and the design has no self-protection — every suspended process stays frozen forever with nothing on disk to reconcile from. The same applies to lockdown's 15-minute TTL, where the blast radius is 'every process started in the incident window'. Persist suspensions to the journal before suspending, and reconcile-and-resume on every start.
- The elevated broker as specified is a same-user privilege-escalation primitive (see correction on nonce/GetImpersonationUserName). This is not a theoretical hardening gap: the product's stated adversary is malware running as this user, and the design hands that adversary an admin-capable verb set — DeleteService, RemoveRegValue, AddFirewallBlock, QuarantineFile — behind a secret it can read with a single WMI query.
- Full-memory dumps of the user's own applications, written by default to D:\ (the projects drive), will contain browser session cookies, password-manager memory, SSH keys and API tokens in plaintext. The spec ACLs them like the vault, but D:\ is the drive most likely to be backed up, synced, or scanned by other tooling, and the retention policy is left as 'offer'. Default to no dump unless the user opts in per-incident, default retention to 7 days with hard deletion, and never dump a process on a credential-holding allowlist (browsers, password managers, ssh-agent, credential providers).
- Job-object assignment is irreversible and, as specced, happens at detection time — before the autonomy gate, and while dry-run mode is supposed to guarantee that nothing is changed. A dry-run that permanently jobs a process is not a dry run, and it silently violates the shakedown period's entire premise.
- The ledger, the vault and vault.key are writable by the same-user adversary (medium-IL creation under ProgramData, owner retains WRITE_DAC). The hash chain is unkeyed and local, so it can be rewritten wholesale; the manifest HMAC key is DPAPI LocalMachine-scoped, so it can be unwrapped and forged. Every tamper-evidence claim in the design collapses against the adversary it names. The mitigation is straightforward (create the tree from the elevated broker, admin-owned, user read-only) but it must be in the design, because 'append-only hash-chained' is currently doing work it cannot do.

### Omissions
- No self-protection whatsoever. Warden auto-starts from HKCU\...\Run — literally the first key it monitors for persistence — runs at medium IL as the user, and can be terminated by any same-user process with a single TerminateProcess. A RAT's opening move is to kill the defender. At minimum: a paired watchdog (each process holds a handle to the other and restarts it), detection of its own Run value being removed or repointed, and an incident raised when the ledger stops advancing.
- No plan for Warden being detected by Defender. Its behaviour profile is an infostealer plus ransomware (see false-positive risks), and it is unsigned. There is no discussion of code signing, of what the user does when Defender quarantines Warden.exe mid-incident, or of which ASR rules would break it. ASR is currently unconfigured on this machine (I verified AttackSurfaceReductionRules_Ids is empty), but 'Block credential stealing from LSASS' and 'Block process creations originating from PSExec and WMI commands' would break the dump path and the WMI path respectively if the user ever turns them on — and a security-conscious user will.
- Hidden scheduled tasks are undetectable by the only API the design uses. The well-known persistence trick is to delete the SD value under HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree\<task>, which makes the task invisible to ITaskService and schtasks while it still runs. The design relies exclusively on Schedule.Service COM, so it is blind to exactly the tasks worth finding. Enumerate TaskCache\Tree from the registry and diff it against the COM enumeration; a task present in one and not the other is a high-confidence signal on its own.
- Whole persistence classes have no capture-or-undo path: COM hijacking (HKCU\Software\Classes\CLSID\{...}\InprocServer32 and TreatAs), AppInit_DLLs, IFEO SilentProcessExit MonitorProcess (the design covers only the Debugger value), Winlogon Notify, Active Setup, netsh helper DLLs, LSA Notification/Security Packages, Print Monitors, HKCU\Environment\UserInitMprLogonScript, and Session Manager BootExecute. Several of these are the ones a competent RAT actually uses once Run keys are being watched. Each needs the same typed undo record treatment as the Run-value case.
- No stated boundary for kernel-mode threats. If the RAT ships a signed vulnerable driver (BYOVD) or a rootkit, every rung of the ladder is inert and the process table Warden reads is lying to it. The product must declare this limit explicitly and route to an offline scan / WinRE, rather than leaving the user believing a green tray icon means clean.
- Removing an HKCU Run value does not clean up HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\StartupApproved\Run, whose binary blob carries the Task Manager enabled/disabled state for that entry. Restoring the value without the StartupApproved entry produces a subtly different startup state than the user had. Capture and restore both.
- No vault-full policy. The 5 GB quota and the 25%-of-free-space rule are specified but not what happens when quarantine hits them mid-incident. Given the stated fail-safe direction ('on any error, do not act'), the answer should be: refuse the quarantine, keep the kill and the suspend, escalate to the user with the reason — but it has to be written down, because the tempting alternative (evict the oldest vault entry) silently destroys the user's only copy of an earlier false positive.
- Runtime volume assumptions are not probed. 'All four volumes are NTFS so a same-volume rename is always available' is a snapshot, and this user is exactly the profile who creates a Windows 11 Dev Drive (ReFS) for source trees. There is also a G: CD-ROM on this machine (verified), which the per-volume vault logic would try to write to. Probe GetDriveType and GetVolumeInformationW before creating <root>\.warden-vault, skip removable/optical/network, and handle a BitLocker-locked data volume at startup (the vault for that volume is simply unavailable until unlock, and restore must say so rather than failing opaquely).
- The restore path has no crash state machine, unlike the quarantine path. Restore performs content write, then ADS writes, then ACL, then timestamps, then attributes — five separate mutations with no journal. A crash after step 6 leaves a file at the original path with wrong ACL, wrong timestamps and wrong attributes, and a manifest that still says the item is quarantined. The quarantine flow has the same gap around the encryption step: the manifest transitions pending -> committed around the *move*, but the encrypt is a second destructive rewrite with no recorded state, so a crash mid-encrypt leaves a half-encrypted blob that the manifest describes as committed and decryptable.
- Alternate data stream capture is unbounded. The manifest stores every ADS as base64 inline in a JSON file. Some installers and download managers attach multi-megabyte streams; one such file turns the write-ahead manifest into something that must be written and flushed before every quarantine can proceed. Cap the inline size, spill larger streams to a sidecar file in the vault, and record the sidecar reference.
- Nothing defines the lifecycle of an open incident across a reboot. Suspensions are gone, TTLs have expired unobserved, the firewall reaper runs and deletes rules whose incidents are still open, and the user comes back to an amber tray icon with no explanation. Specify the reboot reconciliation pass explicitly, alongside the pending-reboot quarantine reconciliation the design already needs.
- The rate limiter must not cap user-initiated actions, but the broker cannot tell the two apart — it receives the same typed verb either way. Given the IPC weaknesses, an 'isUserInitiated' flag in the message is trivially forgeable by the same-user adversary and would let it bypass the only rate limit in the system. Either the broker mints its own user-gesture confirmation in its elevated UI, or user-initiated actions are subject to the same counters.
